# Spatial analysis showcase API audit — 2026-10-24

## Purpose and audit method

This audit maps the public APIs in `@luma.gl/graph/geospatial`, `gpu-spatial-analysis`, `gpu-dataframe`, `gpu-network`, `gpu-raster`, `gpu-terrain`, and `gpu-pointcloud` to the current `examples/deck/spatial-analysis-showcase`. It is intended to guide story selection for a showcase sprint, not to demand one scene per exported symbol. The counts below are an in-progress snapshot measured 2026-10-24 22:28 UTC; rerun the reporter after sprint changes before treating any uncovered symbol as a final gap.

The package entrypoints and their re-exported subdirectory `index.ts` files define the public surface. The coverage reporter parses TypeScript imports and call expressions and counts direct named-import constructors/function calls from both `*.compute.ts` files and non-`.scene.ts` helper files. It distinguishes compute from helper evidence. A mention in a comment, API catalog, `.scene.ts` source-code panel, computation-lens fixture, or example registration is evidence of discoverability or a small contract fixture, but is not counted as runtime call evidence. The API-to-scene matrix is family-level: it avoids implying that every public export or every API overload has been exercised end to end.

## Story proof vs. metadata proof

Use these distinctions when deciding whether a coverage item is already complete:

- **Story runtime proof:** code in `examples/deck/spatial-analysis-showcase/src/scenes/**.compute.ts` or a non-`.scene.ts` helper constructs/runs the operator or recipe and feeds the story. For example, `interpolation/change-of-support.compute.ts` has runtime calls to `addChangeOfSupportRecipe`, `GPUArealInterpolation` and `GPUPycnophylactic`; `flows/bixi-communities.compute.ts` runs graph algorithms; `joins/topological-relations.compute.ts` constructs prepared spatial joins; and `weights/b4-weights-core.ts` builds `GPUContiguityWeights` for the weights stories.
- **Lens/operator proof:** `modules/graph/src/computation-lenses/scenarios/**` includes many focused API fixtures. Those are excellent places to borrow deterministic fixtures, parameter patterns and expected output contracts. They are compact operator examples, not a deck story. The lens catalog already includes a large proportion of the public spatial-statistics, geometry, raster, network and terrain surface. Recheck point-cloud lens/examples alongside the in-progress LiDAR story before assessing that surface.
- **Metadata proof:** `gpu-spatial-analysis/ontology`, docs/api-reference, the showcase scene registry, and source-panel snippets tell us a name is discoverable or documented. They do not prove the showcase actually executes it.
- **Recipe proof:** calling a recipe is valid runtime coverage of that workflow, but it does not imply every constituent low-level API or every recipe option is independently shown. For deeper pedagogy, pair one recipe story with small low-level lenses instead of duplicating every pass in the scene.

The API catalog can be useful for navigation and domain naming, but its capability labels are not an execution trace and should not be used as the coverage metric.

For a mechanically repeatable public-class/recipe inventory, run `node scripts/report-showcase-coverage.mjs` (or pass `--format=json`). It resolves public named exports and uses the TypeScript AST to match direct named package imports to constructor/function call sites in showcase `.compute.ts` files and non-`.scene.ts` helper files. The output labels evidence as `compute` or `helper` and lists `.scene.ts`/computation-lens imports as secondary references. It intentionally does not count property calls, namespace imports, dynamically selected function values, comments, strings or text in catalogs/docs; treat uncovered entries as “no direct static call found”, then inspect wrappers or recipe composition before calling them a behavior gap.

## Shared implementation and teaching constraints

1. **Respect capacity helpers as contracts.** Public APIs expose maximum counts, planners, strides, overflow/status fields, and iteration limits because GPU buffers and dispatches are bounded. A successful constructor or compiled graph does not necessarily mean every desired input was admitted. Put selected and effective capacities in advanced controls and surface overflow/unresolved status.
2. **Preserve identifiers and alignment.** Spatial weights, rates, classes, covariates, geometries, temporal rows and returned scores are meaningful only when their row IDs remain aligned. Stories that join separate API results should display/validate key contracts, not assume equal array positions without evidence.
3. **Name coordinate and measurement assumptions.** Every distance story should state planar/projected vs spherical/geodesic vs network distance, units, CRS and earth model. Every raster/terrain story should state cell size, transform, row orientation, vertical units and nodata policy.
4. **Distinguish descriptive outputs from inference.** Density surfaces, smoothed rates, local clusters and coefficient maps answer different questions. Show null model, edge correction, permutation count, multiple-testing policy, validation or residual diagnostics where the API supports them.
5. **Keep big-data stories truthful.** Use tile/cache/halo/global-merge APIs for regional imagery, chunked/streaming data paths for observations, and bounded network/neighbor queries for graphs. Benchmark panels should report the actual admitted rows/edges/cells and precision mode.
6. **Prefer an analyst question over a symbol tour.** A strong story can demonstrate several APIs in an interpretable sequence and reuse existing lens fixtures for contract depth. P0/P1 above are ordered by absent or weak story coverage and by how much users learn from seeing the APIs composed.

## Focused lens starting points

Lens fixtures live under `modules/graph/src/computation-lenses/scenarios`. The most reusable spatial analysis groups are:

- Statistics and inference: `gpu-spatial-analysis/statistics-coverage-*`, local Moran/Geary/Pearson, permutation tests, multiple testing, spatial weights, hot spots, emerging hot spots, transition diagnostics/Markov and scan statistics.
- Regression and regionalization: OLS, spatial lag/error, 2SLS, spatial regression diagnostics and recipes, GWR-related examples, SKATER/Ward/AZP/max-p regions and partition evaluation.
- Geometry and cells: validity/make-valid, coverage validity/dissolve/simplification, noding/shared paths, overlay, triangulation/Voronoi, measures, geometry predicates, H3/S2 indexing/topology/cover/pyramid.
- Point patterns and interpolation: point process, Ripley/envelope/indices/variograms, interpolation validation, kriging/IDW, areal interpolation, change of support, dot density.
- Dataframe and networks: dataframe query/aggregation/join/lookup and statistics; network construction, map matching, reachability, cost matrix/weights, isochrones, K and point-process, optimization and recipes.
- Raster/terrain: raster coverage tranche, tile/reprojection/halo/global stats and regions; terrain processing, hydrology, illumination, point horizon and geomorphometry scenario sets.

Lens files should be consulted for the actual fixture limits and result-field layouts before stating numeric capacities in showcase copy. This audit intentionally cites API family names and their exported helper pattern rather than duplicating mutable numeric constants.
