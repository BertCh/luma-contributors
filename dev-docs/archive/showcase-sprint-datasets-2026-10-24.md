# Spatial analysis showcase dataset sprint (2026-10-24)

## Research status

This is a source and portfolio review to guide implementation. None of the candidate data below was downloaded, parsed, or visually checked for this note. Counts and sizes are estimates unless explicitly tied to the checked-in manifests. Before a dataset is promoted, preserve the source snapshot/date, licensing evidence, preprocessing script, input checksums, manifest, and rendered QA preview under `examples/deck/spatial-analysis-showcase/scripts/data/<id>/`.

## Existing portfolio audit

At the initial review, the catalog had 64 first-party definitions: 62 with a checked-in `public/data/<id>/manifest.json`, while `ny-taxi-trips` and `sf-bike-parking` were remote definitions backed by synthetic fallbacks. Since then, the active sprint has added a bounded `chicago-buildings` snapshot and `lidar-ground` point sample. Their source artifacts were audited below; lidar now has a dataset definition and standard manifest columns, with final browser results recorded in the [sprint verification ledger](./showcase-sprint-2026-10-24.md). Existing manifests declare EPSG:4326 for their row/feature coordinates; raster manifests also retain the source projection/geotransform where needed. Sizes below are the definitions' `approxBytes` values where present, rather than a measured transfer or unpacked source size. Several manifests have no `approxBytes`; the files in `public/data` are the shipping authority.

The portfolio already covers plenty of algorithms and several kinds of source data. Its main opportunity is coherent, well-sampled observations that let readers compare a few dimensions of one place through time. It has a strong Chicago cluster (tracts, community areas, parks, roads, walking graph, facilities, crashes, 311 rats, nature, taxi/LODES OD and CTA summaries), global movement and network examples (airlines, flights, ships, animals, drifters, earthquakes, NL GTFS, BIXI), and diverse terrain/event rasters (Alps, Grand Canyon, Dixie, California wildfire, GFS, Sentinel cloud repair, NDVI). Current NDVI is a 256², 100 m EPSG:32610 stack of 16 irregular Sentinel-2 dates over the Dixie Fire window (2017–24); preserve it as a distinct recovery story. Chicago tracts already carry CDC/ATSDR SVI 2022, selected ACS 2020–24, CDC PLACES 2023, 2023 iNaturalist and 2021 LODES indicators. The examples do not yet provide a regularly sampled urban imagery series or explicit transit/street accessibility attributes. The active sprint is adding bounded Chicago building footprints and a lidar story; it should validate those sources as separate work before choosing another city/building dataset.

### Active-sprint source audit: `chicago-buildings`

The current shared checkout has `public/data/chicago-buildings/buildings.geojson`, its manifest/source note, the acquisition script, catalog entry and street-enclosure scene. The current artifact has 1,706 ACTIVE MultiPolygon features and 15,268 vertices. All coordinates are finite; actual bounds are `[-87.64999945, 41.87000876, -87.62002131, 41.89495562]`, within the declared bbox. All 1,706 `bldg_id` values are unique and non-null. The GeoJSON is 2,248,014 bytes and its SHA-256 is `1b34ed8229854d188b84fa61f1e165acfb1bebefa3dfdab979781053f82f2705`, matching `payloadSha256` in the manifest and the 2.3 MB catalog estimate. City of Chicago catalog metadata independently confirms `syp8-uezg` is Building Footprints (`https://catalog.data.gov/dataset/building-footprints`).

All records currently have `bldg_statu='ACTIVE'`. The feature collection has `stories` and `year_built` properties, but 533 story values and 721 build-year values are `"0"`; treat zero as missing/unknown in any height or vintage analysis. Its address fields are components such as `f_add1` and `t_add1`, not a generic `address` property. Replaying the live query timed out during this read-only audit, so the checked snapshot could not be compared against current source IDs; its manifest's `downloadedAt` also means manifest bytes differ across builds, although the payload hash is stable for identical GeoJSON. Chicago Data Portal records remain subject to posted terms and require city attribution. These findings were reported to the implementation author.

### Active-sprint source audit: `lidar-ground`

`public/data/lidar-ground/{manifest.json,metadata.json,position.bin,elevation.bin,classification.bin}` and `src/data/datasets/lidar-ground.dataset.ts` are present, and the previous duplicate `points.bin` has been removed. The manifest follows the loader's standard column schema: 116,213 rows of interleaved EPSG:4326 longitude/latitude `float64` positions, NAVD88-metre `float32` elevations, and `uint32` LAS classes. It declares exact observed bounds `[-122.34098606, 47.59506453, -122.33873238, 47.59671148]`; an independent parse reproduces them exactly. Source is USGS 3DEP King County 2021 tile 2282 (USGS source item `619ce206d34eb622f694418b`), collected 2021-04-01 to 2021-04-24. The downloaded 32,196,969-byte LAZ hashes to `cfceeda5525b335ba523613b9837c650d72d7cc40b8c32d22c18ff7344124ab3`, matching the script and metadata. The source has 6,373,072 points; its CRS is EPSG:6597 horizontal (NAD83(2011), Washington North, US survey feet) with EPSG:6360 vertical (NAVD88/Geoid18, US survey feet). The recorded source XY and Z ranges agree with the LAS header audit. USGS 3DEP products are public domain; preserve source/item links and cite USGS.

The three data files total 2,789,112 bytes, matching `approxBytes`; each matches the manifest's element count and dtype byte length. `position.bin` is float64 to preserve sub-metre horizontal precision. SHA-256 values are `position.bin` `50effd406a52bdab0576957b7de025f5ff839268078c51d564222885c38eaf3b`, `elevation.bin` `202dfe5206b1aac4bca2a44f75f4318202838727bbb53437de8d31053f71c94b`, and `classification.bin` `ab20d3287279d734d61534623ec67c68eda880a94c5461a4d2fe66602b9000f4`. Independent parsing found all positions and elevations finite, exact agreement between observed and declared bounds, and class counts matching metadata (class 1: 72,567; class 2: 43,619; classes 7/9/18/20: 27 combined). All 116,213 serialized position pairs are unique after the author retained source projected coordinates at float64 through reprojection. The preprocessing script records the 180 m crop, seeded one-original-return-per-occupied-0.5 m-cell procedure, CRS/unit conversion and source checksum. Final integration passed all six story steps on native WebGPU, and the 9,489-voxel GPU reduction matched an independent CPU reference. See the [sprint verification ledger](./showcase-sprint-2026-10-24.md) for scope and remaining repository-wide checks.

## Portfolio recommendation

Build around two linked places rather than ten unrelated demos: Chicago for continuity with the existing analysis geography, and New York City for dense built-form, trees, transit access, and bike movement. Keep each derived asset to roughly 5–20 MB compressed for the published site; tolerate a larger one-time source download only in a reproducible preparation script, not in browser runtime. Apply spatial clipping, field projection, and stable feature ordering before serialization. Store all original source CRSs and transformations in each dataset README/manifest.

## Next-wave proposal (separate from the active contributor sprint)

The current contributor sprint is validating Chicago building footprints and a lidar-ground story. Keep those real-source acquisitions as their own datasets/stories. The following work starts after those artifacts have passed their source, CRS, license, bounds and reproducibility checks:

1. **First next-wave deliverable:** add a sibling `chicago-monthly-vegetation` stack with equal-season Chicago Sentinel-2 composites, documented cloud masking, valid-pixel QA and a repeatable Earth Search query. Preserve the existing Dixie Fire `ndvi-timeseries` unchanged.
2. **Second next-wave deliverable:** add EPA PM2.5 monitor observations, then tell an exposure story using the SVI/ACS attributes already present in `chicago-tracts`; do not add a duplicate SVI baseline.
3. **Third next-wave deliverable:** compare the current Chicago buildings, tree observations and walking graph with NYC buildings, street trees and MTA GTFS accessibility. Track no-data and unknown-accessibility separately.
4. **Stretch:** either OSM tag enrichment or aggregated Citi Bike flows. Treat Citi Bike license rules as a hard acceptance gate. Use iNaturalist only after per-observation licenses and sensitive taxa handling are automated. Keep 3DEP source validation with the active lidar contributor and do not create a second lidar dataset while that work is in progress.

For every accepted source, record the human-readable release/version, retrieval date, geography and temporal slice, exact upstream URL/query, attribution/license statement, input checksums, field transformations, coordinate transform, row/pixel counts before and after filters, missingness, source and output byte sizes, and a reproducible QA command. Keep raw credentialed or restricted data out of the repository. Keep current source manifests/attributions intact when extending a dataset. A dataset is “validated” only after the acquisition and preprocessing run succeeds, the output manifest is loader-compatible, joins/counts pass explicit assertions, and a preview is checked; all candidates in this plan remain **research candidates** until then.
