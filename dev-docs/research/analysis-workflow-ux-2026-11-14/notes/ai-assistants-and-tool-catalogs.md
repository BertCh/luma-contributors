# AI assistants and typed tool catalogs for spatial and data analysis (as of 14 November 2026)

Method note: web search plus direct fetches of primary pages where reachable. Esri, npm and the Blender manual returned HTTP 403 to the fetcher, so claims about them come from search-result summaries and are marked "(search summary, unverified)". Several model and product names below (for example Gemini 3.8 Flash, gpt-5.4, Claude Opus 4.5 and later) are as written on the cited pages.

## 1. Kepler.gl AI assistant and OpenAssistant (GeoDa.AI, Xun Li)

### Takeaway
The kepler.gl assistant is a browser-side, bring-your-own-key chat panel built on OpenAssistant and SQLRooms. Its tools are typed with Zod and register in a flat object. Results come back as `llmResult` for the model and `additionalData` for the host to render. It has no approval step and no saved-workflow concept, and its newer harness (`@openassistant/kepler-assistant`) moves towards namespaced tools (`data.*`, `geoda.*`, `geo.*`, `chart.*`, `map.*`) plus skill-discovery meta-tools. That design is close to what a 280-operation catalog needs.

### Cited Findings
- The assistant first shipped in kepler.gl 3.1 (29 January 2025). It "can edit the map, including filters, base map customization, and a variety of layer configurations", is "accessible via text chat, voice chat, and screenshot", and "can also produce SQL from natural language, which can be passed to DuckDB". — [kepler.gl release notes](https://docs.kepler.gl/release-notes)
- 3.1.1 (10 March 2025) sends messages to a local 127.0.0.1 Ollama. 3.2 (21 August 2025) added "Generate idea buttons from the LLM to speed up workflows" (LLM-generated suggestion chips) and a TypeScript configuration. The page lists no AI changes for 3.3. — [kepler.gl release notes](https://docs.kepler.gl/release-notes)
- The 3.3.0 alpha line includes "fix: ensure AI Assistant restart clears conversation history (#3442)". The npm `@kepler.gl/ai-assistant` latest was 3.3.0-alpha.8, about three weeks before this search. (search summary) — [kepler.gl changelog](https://docs.kepler.gl/changelog); [npm @kepler.gl/ai-assistant](https://www.npmjs.com/package/@kepler.gl/ai-assistant); bug report [kepler.gl #3261](https://github.com/keplergl/kepler.gl/issues/3261)
- A kepler.gl discussion describes the module as integrating "50+ geospatial tools that operate directly within the browser". The documented providers are OpenAI, Google Gemini and Ollama. (search summary) — [kepler.gl Discussion #2843](https://github.com/keplergl/kepler.gl/discussions/2843)
- OpenAssistant packages include `@openassistant/plots` (histogram), `@openassistant/maps` (a `keplergl` tool), `@openassistant/keplergl` (`KeplerGlComponent`), `@openassistant/assistant` (the `Assistant` chat component), `@openassistant/core` (`createAssistant`), `@openassistant/utils` (`convertToVercelAiTool`), and `@openassistant/ai` ("a wrapper of `@sqlrooms/ai`"). Its feature list includes GeoDa tools ("spatial statistics, LISA, Moran's I, spatial regression"), DuckDB-WASM SQL, OSM geocoding, routing and isochrones, and H3. — [GeoDaCenter/openassistant](https://github.com/GeoDaCenter/openassistant)
- How tools are registered: an `OpenAssistantTool` has a `name`, a `description` and `parameters: z.object(...)` (Zod), a `context` object for callbacks the app supplies, and an `execute` that returns `llmResult` and `additionalData`. Tools go in `tools: { histogram: convertToVercelAiTool(histogramTool) }` for the Vercel AI SDK, or in `options.ai.tools` for the React `Assistant`. An `onToolCompleted(toolCallId, additionalData)` callback lets the app "render a histogram component". v1.0.0 "is framework-agnostic". — [GeoDaCenter/openassistant](https://github.com/GeoDaCenter/openassistant)
- Providers in the OpenAssistant table are OpenAI, Google, Anthropic, DeepSeek, xAI and Ollama, through `@ai-sdk/*` packages. — [GeoDaCenter/openassistant](https://github.com/GeoDaCenter/openassistant)
- `@openassistant/kepler-assistant` describes itself as "the analysis engines (`data.*`, `geoda.*`, `geo.*`, `chart.*`)". It lists the tool namespaces `data.run-sql`, `geoda.analysis` (weights, LISA, clustering), `geo.*` (buffer, join, centroid, routing, isochrone, geocode, roads, us-boundary), `chart.histogram` and `map.add-layer`. It also has the harness tools `executeApi`, `runSkill`, `discoverSkill` and `query`, plus SQLRooms `execute_command`. — [geodaai/kepler-assistant](https://github.com/geodaai/kepler-assistant)
- Host integration point: "spread `createKeplerAssistantTools(store)` alongside the default tools into the `aiSlice` `tools` config", add renderers through `toolRenderers`, and register commands with `registerCommandsForOwner`. MCP is "an optional transport". The planner is "a pluggable `Planner`", and "a real LLM planner" is listed as remaining work. — [geodaai/kepler-assistant](https://github.com/geodaai/kepler-assistant)
- Release v0.0.17 (September 2026) publishes `@openassistant/kepler-assistant@0.0.17`. PR #6, "send anthropic's browser-access header from the chat transport", bumped the package to 0.0.18 so that Anthropic works directly from the browser. — [kepler-assistant PR #5](https://github.com/geodaai/kepler-assistant/pull/5); [kepler-assistant PR #6](https://github.com/geodaai/kepler-assistant/pull/6)

### Inferences
- A host can add its own tools in three ways: as OpenAssistant tools (Zod schema plus `execute` plus a renderer through `onToolCompleted` or `toolRenderers`), as commands registered in the SQLRooms command registry, or over MCP. A machine-readable binding can probably be compiled straight into Zod or JSON Schema tool definitions.
- The `discoverSkill` / `runSkill` / `executeApi` meta-tools suggest the kepler assistant is itself moving to a list, describe and run pattern rather than one tool per operation.
- The "idea buttons" in 3.2 are an existing precedent in kepler.gl for proactive suggestions.

### Gaps
- No primary source lists the full current tool names in `@kepler.gl/ai-assistant` 3.3 (npm returned 403). No source describes an approval or confirmation step. It is unclear whether `@kepler.gl/ai-assistant` 3.3 already depends on `@openassistant/kepler-assistant`. The relationship is implied, not documented.

## 2. GIS vendor assistants and MCP servers

### Takeaway
By late 2026 the pattern has split in two. (a) Assistants inside the product (ArcGIS Pro, Kue for QGIS) mostly open a tool with parameters pre-filled for the user to run, or write code. (b) Vendors publish MCP servers (CARTO, Felt, Wherobots, Mapbox) so that outside agents (Claude, ChatGPT, Gemini) can act. CARTO is the only vendor found whose *curated, reusable workflows* become tools. No vendor documents an editable plan that the user approves before a multi-step run.

### Cited Findings
- **ArcGIS Pro assistant**: in beta with ArcGIS Pro 3.7 (released 14 May 2026), and open to all eligible ArcGIS Online named users from 3.7. It can open geoprocessing tools, suggest next tools and create custom toolboxes. When a task needs a tool, "it opens that tool with preset parameters from your current project", though it may ask for more input first. It also writes ArcPy, SQL query layers and OpenCypher. Esri describes its actions as "a limited subset" of Pro, and generated code usually needs edits for dataset paths. (search summary, unverified; Esri pages returned 403) — [Esri: try the ArcGIS Pro assistant 3.7 beta](https://www.esri.com/arcgis-blog/products/arcgis-pro/announcements/try-the-arcgis-pro-assistant-3-7-beta-and-get-more-done-in-arcgis-pro); [ArcGIS Pro Assistant (Beta) documentation PDF](https://www.esri.com/content/dam/esrisites/en-us/media/products/arcgis-pro-issues-addressed/ai-assistant-pro.pdf); [What's new in ArcGIS Pro (May 2026)](https://www.esri.com/arcgis-blog/products/announcements/announcements/whats-new-and-improved-in-arcgis-pro-may-2026); [ArcGIS Pro roadmap May 2026](https://community.esri.com/t5/arcgis-pro-documents/arcgis-pro-roadmap-may-2026/ta-p/1701657)
- Esri's November 2026 GeoAI post covers ArcGIS Pro 3.8 additions (a foundation model, an embeddings dataset, "Detect Objects In 3D Space"). The search found no details on assistant changes in 3.8. Esri also publishes monthly "What's new in AI assistants" posts for ArcGIS Online (June 2026, February 2026). (search summary) — [Esri: what's new in geospatial AI, November 2026](https://www.esri.com/arcgis-blog/products/arcgis/geoai/whats-new-in-geospatial-ai-november-2026); [What's new in AI assistants, June 2026](https://www.esri.com/arcgis-blog/products/arcgis-online/geoai/whats-new-in-ai-assistants-june-2026)
- **QGIS**: Kue is an embedded assistant that can "edit symbology, run geoprocessing, share web maps, add basemaps" for a $19/month subscription. IntelliGeo is a free plugin that uses LLMs "to automate geospatial workflows". QGIS MCP (jjsantos01) is a socket-server plugin that needs a separate Python MCP server, and it has the most votes (255). QGIS Agent pairs natural-language control of QGIS tools with an optional local MCP server for Claude Desktop or Cursor. (search summary) — [Kue plugin](https://plugins.qgis.org/plugins/kue-ai/); [IntelliGeo](https://plugins.qgis.org/plugins/intelli_geo/); [QGIS MCP plugin](https://plugins.qgis.org/plugins/qgis_mcp_plugin/); [QGIS Agent](https://plugins.qgis.org/plugins/qgis_agent/)
- **CARTO for Agents** has three parts: the hosted CARTO MCP Server, CARTO Agent Skills (playbooks in `CartoDB/agent-skills`) and a CLI (`@carto/carto-cli`). The agent "creates and edits Builder maps, authors and runs Workflows, renders maps inline". Separately, Builder has "in-product agents bound to a map's data and tools". — [CARTO for Agents overview](https://docs.carto.com/carto-for-agents/carto-for-agents)
- CARTO Workflows as MCP tools: each tool is backed by a workflow that defines the spatial logic, inputs and outputs. Once a workflow has a description, inputs and outputs, it "can be enabled as an MCP tool from the workflow editor". The team decides which workflows are published, and the tool must be re-synced when the workflow changes. Clients include Claude.ai (OAuth), Gemini CLI (API token) and ChatGPT. (search summary across CARTO docs) — [CARTO: workflows as MCP tools](https://docs.carto.com/carto-user-manual/workflows/workflows-as-mcp-tools); [CARTO MCP Server](https://docs.carto.com/carto-mcp-server); [CARTO workflow tools reference](https://docs.carto.com/carto-for-agents/mcp-server/tools-reference/workflow-tools); [CARTO AI Agents: working with tools](https://docs.carto.com/carto-user-manual/ai-agents/working-with-tools)
- **Felt MCP Server** (28 April 2026): "One endpoint, 30 tools, every major model provider." The tools fall into Make maps (5), Bring in data (5), Write SQL (6) against Snowflake, BigQuery, Databricks, Postgres and Redshift, Run spatial analysis (5: query, join, filter, generate layers), Style (2) and Collaborate (7). The output is a live, editable Felt map at a shareable URL. Agents inherit the user's permissions, and the post describes no separate approval step ("humans stay in the loop because the map is right there"). It says no pre-built UI workflows are needed. It is available on Business and Enterprise workspaces. A later third-party listing shows 34 tools. — [Felt: introducing Felt MCP Server](https://felt.com/blog/introducing-felt-mcp-server); [Felt AI information](https://felt.com/ai-information)
- **Wherobots MCP**: an agent explores the catalog, writes spatial SQL and generates a notebook that runs on Wherobots Cloud. A blog post shows an agent finding Overture places data without help. (search summary) — [Wherobots MCP docs](https://docs.wherobots.com/develop/mcp/mcp-server-automating-geospatial-workflows); [Wherobots blog](https://wherobots.com/blog/ai-agents-spatial-analytics-15-minute-train-ride/)
- **Mapbox MCP Server**: an official server, hosted at `https://mcp.mapbox.com/mcp`, that needs a Mapbox token. (search summary) — [Mapbox MCP](https://www.mapbox.com/forms/mcp); [listing](https://llmbase.ai/mcp-servers/mapbox)
- **Google Earth AI Geospatial Reasoning Agent (GRA)**: a Gemini-powered system that "organizes these into modular domain skills and pairs them with upfront geospatial planning". The paper ablates the planning and execution guidance. It was evaluated with Gemini 3.1 Pro and 3.8 Flash on GeoExpertQueries, GeoKTools, CBGB and UnivEARTH ("saturated"). With basic tools, a strong model satisfies "only a small fraction of the expert workflows" on open-ended problems. The largest gain comes from skills and tools, and planning lets Flash match or beat Pro "at lower cost". — [Google Research publication](https://research.google/pubs/google-earth-ai-geospatial-reasoning-agent-capabilities-and-a-systematic-evaluation/); [arXiv 2510.18318](https://arxiv.org/abs/2510.18318v3)
- Secondary reports put GRA at 62.7 on GeoExpertQueries, against 3.3 with basic tools and 0.0 for the model alone. They also report an October 2026 early-access expansion (deep analysis in Ask Google Earth, an agent-to-agent service, user uploads of CSV and GeoJSON). (search summary, unverified against the primary report) — [Google Research blog: putting Earth AI to work](https://research.google/blog/putting-earth-ai-to-work-geospatial-agents-for-our-planets-biggest-challenges/)

### Inferences
- Of all the vendor patterns, CARTO "workflow as tool" is the closest match to the drafted JSON workflow DAG. A saved workflow becomes one typed, curated tool that an agent can call, which limits the agent's freedom where accuracy matters.
- "Open the tool with parameters pre-filled" (ArcGIS Pro) is a conservative, review-friendly pattern: the human runs the step.
- Felt's model (the agent acts, and the result lands in an editable artifact) treats the output map as the review surface, with no approval of the plan.

### Gaps
- Not researched or not found: Foursquare Spatial Agent and FSQ Spatial H3 Hub (only community Foursquare Places MCP servers appeared), Microsoft (Azure Maps or Planetary Computer agents), AWS geospatial agents, Atlas AI, and ArcGIS Online Map Viewer assistant capabilities (the Esri pages returned 403). The search found no evidence that any vendor saves an assistant session as a reusable workflow, except CARTO in reverse (a workflow becomes a tool).

## 3. Research and benchmarks: multi-step spatial analysis success and error types

### Takeaway
Measured success varies widely with how much scaffolding the system has. With a plain agent and 23 tools, the best frontier model solved about 55% of multi-step geospatial tasks (GeoBenchX). Systems with curated tools and planning report 75–96% on their own benchmarks. General data-science agent benchmarks sit at 34% (DSBench, older models) to around 50–73% (Spider 2 variants). The common errors are not wrong-tool picks but silent wrong answers: inventing filter values and thresholds, solving a modified task, and answering tasks that cannot be solved.

### Cited Findings
- **GeoBenchX**: 202 tasks (123 solvable, 79 unsolvable), a deliberately simple agent with 23 geospatial functions plus `reject_task`. On solvable tasks the best were Claude Sonnet 4 (0.55) and o4-mini (0.51), "only slightly more than half". On unsolvable tasks, o4-mini correctly rejected 0.90 and Claude Sonnet 4 only 0.17. In the Spatial operations group, o4-mini reached 0.56. The error types include inefficient manipulation (merging without prefiltering), "using internally known spelling of names rather than dataset values for filtering", "attempting to solve with partial data", "modifying tasks to make them solvable", "hallucinating unjustified data processing steps" (invented thresholds), misreading geometric relations (centroid instead of an average over the polygon), and outdated world knowledge. — [GeoBenchX, arXiv 2503.18129](https://arxiv.org/html/2503.18129)
- **GeoAnalystBench**: 50 tasks with 3–10 subtasks each. Proprietary LLMs reach "higher success rates (>90%)" and workflows "more aligned with human-designed implementations" than smaller open-source models. This is self-reported. — [GeoDS/GeoAnalystBench](https://github.com/GeoDS/GeoAnalystBench)
- **GIS Copilot** (QGIS, Penn State; International Journal of Digital Earth): about 86% overall success across more than 100 tasks, by the lead author's account. Per tier, summaries give basic 92% (60 tasks), intermediate 80–83% (30) and advanced 75% (20), and the per-tier figures conflict between sources. The authors write "full autonomy is not yet achieved". — [Penn State GIScience](https://giscience.psu.edu/gis-copilot-towards-an-autonomous-gis-agent-for-spatial-analysis); [arXiv 2411.03205](https://arxiv.org/abs/2411.03205v1)
- **ShapefileGPT**: a planner and worker multi-agent design with a 27-function library and 42 tasks. It reports 95.24% task success (secondary summary). — [arXiv 2410.12376](https://arxiv.org/html/2410.12376v2)
- **GeoAgent**: a code interpreter, static analysis and RAG inside Monte Carlo tree search, with its own benchmark. The search returned no numbers. — [arXiv 2410.18792](https://fugumt.com/fugumt/paper_check/2410.18792v2_enmode)
- **GISclaw** reports up to 96–100% on GeoAnalystBench. Different versions of the paper disagree, and the figures are self-reported. — [arXiv 2603.26845](https://arxiv.org/html/2603.26845)
- **DSBench** (466 data-analysis tasks): the best agent, AutoGen with GPT-4o, reached 34.12% task-level accuracy (vanilla GPT-4o 23.39%), against human 64.06%. — [DSBench, arXiv 2409.07703](https://arxiv.org/html/2409.07703v1)
- **InsightBench**: evaluates multi-step insight generation, and its AgentPoirot baseline beats Pandas Agent. The search returned no headline number. — [InsightBench, arXiv 2407.06423](https://arxiv.org/pdf/2407.06423)
- **Spider 2.0**: o1-preview originally solved 21.3% of the agentic tasks, against 91.2% on Spider 1.0. Third-party snapshots from May 2026 show top entries around 52.9% (Spider 2.0-Lite) to around 73% (variant unclear). — [Spider 2.0 site](https://spider2-sql.github.io/); [Spider2 GitHub](https://github.com/xlang-ai/Spider2); [BenchLM Spider2-Lite](https://benchlm.ai/benchmarks/spider2Lite)

### Inferences
- The GeoBenchX error list maps directly onto guards a typed catalog can enforce. Enumerated parameter values taken from the data (rather than free strings) block invented filter values. Declared units and ranges block invented thresholds. A first-class "cannot do this" outcome in the router addresses the 0.17 rejection rate.
- Higher scores track curated tools and planning scaffolds (GRA, ShapefileGPT, GIS Copilot). A model with a raw, large catalog and no plan does worst.

### Gaps
- No benchmark found reports CRS or unit errors as a separate category with a rate. DABench (InfiAgent-DABench) numbers were not found, and neither were LLM-Geo (Li and Ning 2023) measurements. Error-type rates (rather than lists) are mostly unpublished.

## 4. General data-analysis assistants: constraining and exposing the work

### Takeaway
The commercial BI and data assistants converge on one recipe. They constrain the model with a curated semantic layer, verified queries and benchmark questions, show the generated code or cells, and mark answers that came from verified logic. Vendors measure the semantic-layer lift at about 20 points.

### Cited Findings
- Snowflake Cortex Analyst claims "90%+ SQL accuracy on real-world use cases" with a semantic model (internal evaluation). On BIRD-SQL, Snowflake reports 57% without a semantic model and 78% with one, and that single-shot GPT-4o "plummeted to 51%" on its internal set. — [Snowflake engineering: Cortex Analyst text-to-SQL accuracy](https://www.snowflake.com/en/blog/engineering/cortex-analyst-text-to-sql-accuracy-bi/); [Snowflake: agentic semantic model improvement](https://www.snowflake.com/en/blog/engineering/agentic-semantic-model-text-to-sql/)
- Databricks Genie: a response is marked **Trusted** when it comes from the exact text of a parameterized example query or SQL function the author has verified. The best-practice docs favour a "limited, focused set of instructions" and example SQL over long text. Benchmark questions are for scoring a space, not for training it (up to 500 per space, per a community source). (search summary) — [Databricks Genie best practices](https://docs.databricks.com/gcp/genie/best-practices); [Genie agents concepts](https://docs.databricks.com/aws/en/genie-agents/concepts)
- Hex: the Notebook Agent uses the data connections and semantic models a user can access, keeps code cells in the notebook, and leaves visualizations explorable. Threads "heavily prioritizes semantic models and endorsed data sources". "Hex Magic" is the former name. Context Studio (28 January 2026) monitors agent conversations with "confusion warnings". — [Hex notebook agent](https://learn.hex.tech/docs/explore-data/notebook-view/notebook-agent); [Hex Threads](https://learn.hex.tech/docs/explore-data/threads); [Hex: introducing Threads](https://hex.tech/blog/introducing-threads/); [Hex AI overview](https://learn.hex.tech/docs/getting-started/ai-overview)
- Power BI Copilot depends on "Prep data for AI" on the semantic model, and legacy Q&A is reported to retire by December 2026. — [Microsoft Learn: prep data for AI](https://learn.microsoft.com/power-bi/create-reports/copilot-prepare-data-ai)

### Inferences
- For an analysis catalog, the counterpart of the semantic layer and trusted assets is the curated workflows plus the typed bindings. A "trusted" badge could be shown when the assistant runs a curated workflow unchanged, as opposed to a plan it composed itself.

### Gaps
- Not covered with sources: ChatGPT data analysis, Claude analysis and artifacts, Julius, Observable AI, Tableau Agent and Pulse (only consultancy sources were found), and Deepnote. No measured study was found on "explain this result" or on proactive suggestions at data load.

## 5. Tool-catalog engineering for hundreds of tools

### Takeaway
Both major model providers now publish guidance and APIs for large catalogs. Expose only a few tools up front (OpenAI: fewer than 20; Anthropic: accuracy degrades past 30–50). Defer the rest behind tool search, namespace tool names, enforce schemas with strict mode, and add worked input examples. A browser host can implement its own tool search (for example embeddings over the bindings) and return tool references. MCP Apps and WebMCP give standard routes for in-chat UI and tools registered by the page.

### Cited Findings
- Anthropic: "Claude's ability to pick the right tool degrades once you exceed 30–50 available tools". Tool search "typically reduces [definition tokens] by over 85 percent, loading only the 3–5 tools Claude needs". There are regex and BM25 variants, and they search names, descriptions, argument names and argument descriptions. A search returns 5 tools by default (`limit` up to 10,000). The maximum is 10,000 deferred tools per request. "Keep your 3–5 most frequently used tools non-deferred". "Use consistent namespacing in tool names". Use tool search when there are "10 or more tools" or more than 10k tokens of definitions. — [Claude docs: tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- Anthropic custom tool search: a custom tool can return `tool_reference` blocks, so hosts can use "embedding-based retrieval". `input_examples` expand along with a discovered tool, and strict mode works with `defer_loading`. — [Claude docs: tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- Anthropic measurements (24 November 2025): tool search raised MCP-eval accuracy for Opus 4 from 49% to 74% and for Opus 4.5 from 79.5% to 88.1%. Programmatic tool calling (the model writes code that calls tools) cut average tokens from 43,588 to 27,297 (−37%) and raised GIA from 46.5% to 51.2%. Tool use examples raised complex-parameter accuracy from 72% to 90%. — [Anthropic engineering: advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- OpenAI: "Aim for fewer than 20 functions available at the start of a turn". "Use namespaces to group related tools by domain". `tool_search` defers tools ("Only `gpt-5.4` and later models support `tool_search`"). Strict mode "ensure[s] function calls reliably adhere to the function schema" (it requires `additionalProperties: false` and every field required, with nullable types for optional fields), and "We recommend always enabling strict mode". `allowed_tools` restricts calls to a subset while keeping the prompt cache. — [OpenAI function calling guide](https://developers.openai.com/api/docs/guides/function-calling)
- Counterpoint: one team found BM25-style tool retrieval accuracy of about 60%, "not production-ready". This is a single blog with its own tools. — [Unity Horizon blog](https://unity-horizon.com/blog/how-many-tools-ai-agent-accuracy)
- MCP Apps (`io.modelcontextprotocol/ui`) adds `ui://` resources, links tools to UI through metadata, and passes JSON-RPC between the iframe and the host. It was proposed as SEP-1865 in November 2025 and stable as of 26 January 2026, as the first official MCP extension. A folding into a 2026-07-28 extensions framework is reported but unverified. — [MCP blog: MCP Apps](https://blog.modelcontextprotocol.io/posts/2025-11-21-mcp-apps/); [SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp.md); [WorkOS on MCP Apps](https://workos.com/blog/2026-01-27-mcp-apps)
- WebMCP: pages register typed tools through `navigator.modelContext.registerTool`. It was in Chrome 146 Canary preview (February 2026), with reports of a Chrome 149 origin trial (about May 2026) and a move to `document.modelContext` (secondary sources, unverified). MCP-B is a polyfill. — [W3C CG WebMCP technical notes](https://w3c-cg.github.io/aikr/webMCP/webmcp-technical-notes.html); [VentureBeat](https://venturebeat.com/infrastructure/google-chrome-ships-webmcp-in-early-preview-turning-every-website-into-a); [eWeek](https://www.eweek.com/news/google-webmcp-chrome-ai-web-standard-preview/)

### Inferences
- For about 280 operations, the evidence favours either (a) per-operation tools deferred behind a host-side search over the bindings, with namespaced names such as `raster_slope` or `network_isochrone` and 3–5 always-loaded tools, or (b) meta-tools (search, describe, propose workflow). Option (b) has the model emit a workflow document checked by JSON Schema rather than calling operations directly. Option (b) also fits providers without tool search and fits plan review.
- Strict schemas cannot express cross-parameter rules or units. Units and ranges in the binding still need host validation and should be stated in parameter descriptions, because the search indexes argument descriptions.
- Worked `input_examples` per operation (a 72% to 90% gain in Anthropic's test) are cheap to generate from binding defaults.

### Gaps
- No Google (Gemini) published guidance on tool-count limits was retrieved. MCP elicitation semantics were not verified from the spec.

## 6. Plan-then-approve UX, over-trust and verification burden

### Takeaway
The evidence argues against relying on approval alone. Plausible-looking plans draw miscalibrated trust in both directions. Better trace displays make reviewers faster and more confident but not more accurate. Frequent approvals decay into rubber-stamping. Plan review works best when the plan is short, typed and checked by the machine, and when users stay involved during execution.

### Cited Findings
- Plan-Then-Execute (N = 248, six daily tasks of varying risk): agents did well "when they had a high-quality plan and users were sufficiently involved in execution". Users "could easily mistrust" agents whose plans looked plausible, and "LLM agents can be a double-edged sword". Designers should calibrate trust. — [He, Demartini, Gadiraju, arXiv 2502.01390](https://arxiv.org/abs/2502.01390)
- In "Overseeing Agents Without Constant Oversight" (Microsoft Research, 18 February 2026, three studies), basic action traces are "cumbersome, limiting their efficacy". A new design "reduced the time participants spent finding errors" and raised confidence, but "final accuracy was not meaningfully improved". — [arXiv 2602.16844](https://arxiv.org/abs/2602.16844)
- In a lab study (13 participants), users revised plans that had planted errors, and the study measured success, completeness and time. — [Human-LLM collaborative planning, arXiv 2605.23023](https://arxiv.org/pdf/2605.23023)
- A study of over-reliance (77 participants, LLM seeded with misinformation) found that heavy over-reliers copied output without careful review. — [arXiv 2602.11567](https://arxiv.org/pdf/2602.11567)
- "Approval fatigue" (from a Hugging Face and Data & Society paper): repeated approval prompts turn into habitual approval. (secondary press only) — [GovInfoSecurity](https://www.govinfosecurity.com/ai-agents-make-human-oversight-less-reliable-a-32768)
- Unverified secondary claim: Claude Code plans were rejected 39% of the time against 3% for individual permission requests. No primary Anthropic source was found. — [uxcel lesson](https://uxcel.com/lessons/real-oversight-vs-approval-theater-827)

### Inferences
- Whole-plan approval before execution, with per-step approval only for costly or irreversible steps, is better supported than approving every step. The host's current per-operation approval risks approval fatigue once the assistant composes multi-step plans.
- Checks the system runs itself (unit and CRS compatibility, typed input and output edges in the DAG, row-count or extent sanity checks) should carry the load that human review cannot.

### Gaps
- No published measurements were found on diff-style plan proposals, undo, cost or time estimates, or provenance markers for AI-generated steps in analysis tools.

## 7. Non-LLM natural interfaces: palettes and natural language to form

### Takeaway
Little measured evidence was found. Palette practice centres on fuzzy matching over titles, grouping, recent items and inline argument chips. The ArcGIS Pro assistant's "open the tool with preset parameters" is a shipping example of natural language to form.

### Cited Findings
- Palette mechanics in the documented examples: fuzzy matching (capped at 50 results), ranking that favours title matches, grouped results with sub-menus and recent items, and inline argument chips that turn a multi-step command into one input. — [angr Management command palette](https://www.mintlify.com/angr/angr-management/features/command-palette); [21st.dev palette with argument chips](https://21st.dev/@moumensoliman/components/command-palette.md); [Nuxt UI command palette](https://ui.nuxt.com/components/command-palette)
- Natural language to form in a GIS product: the ArcGIS Pro assistant opens a geoprocessing tool "with preset parameters from your current project" instead of running it. (search summary) — [Esri ArcGIS Pro assistant beta](https://www.esri.com/arcgis-blog/products/arcgis-pro/announcements/try-the-arcgis-pro-assistant-3-7-beta-and-get-more-done-in-arcgis-pro)

### Inferences
- With typed bindings, a palette can do most of what a chat would at the step of finding an operation: fuzzy search over names, synonyms and description keywords, then a form generated from the binding. An LLM adds value mainly when a request spans several steps or when parameters must be chosen from the data. A palette with an optional "fill this form from my sentence" step avoids silent wrong answers, because the user sees every parameter.

### Gaps
- Primary sources for Blender F3 search, VS Code, Linear, Raycast and Figma quick actions were not retrieved (the Blender manual returned 403). No usability study comparing a palette with chat for analysis tasks was found.

## 8. Privacy and deployment for a static client-side app

### Takeaway
A browser-only, bring-your-own-key setup is already proven in kepler.gl and OpenAssistant (a local Ollama option, the Anthropic browser-access header). The schema-and-summary-only pattern is how warehouse-backed agents (Felt) avoid putting data in context.

### Cited Findings
- kepler.gl 3.1.1 routes Ollama to 127.0.0.1, which allows a fully local model. — [kepler.gl release notes](https://docs.kepler.gl/release-notes)
- OpenAssistant supports OpenAI, Google, Anthropic, DeepSeek, xAI and Ollama through `@ai-sdk/*` providers. — [GeoDaCenter/openassistant](https://github.com/GeoDaCenter/openassistant)
- kepler-assistant added Anthropic's browser-access header to its chat transport so that Anthropic calls work from the browser. — [kepler-assistant PR #6](https://github.com/geodaai/kepler-assistant/pull/6)
- A kepler.gl bug report: restarting the chat still sent the earlier conversation history to the LLM provider, fixed in the 3.3 alpha line (#3442). This was a real privacy leak in a browser assistant. — [kepler.gl #3261](https://github.com/keplergl/kepler.gl/issues/3261); [kepler.gl changelog](https://docs.kepler.gl/changelog)
- Felt agents "write SQL against the source data, so large warehouse datasets can be analyzed without being loaded into the model's context window". — [Felt MCP Server blog](https://felt.com/blog/introducing-felt-mcp-server)
- Anthropic's server-side tool search is ZDR-eligible, with tool definitions "searched in memory per call and nothing is stored after the response". — [Claude docs: tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)

### Inferences
- Sending only column schemas, binding metadata and aggregate summaries (never rows) is workable, because tools run locally and return compact `llmResult` summaries while the full results stay in `additionalData` for the map. The history-leak bug shows that the context the host sends needs explicit tests.
- Client-side tool search over the bindings (BM25 or small embeddings) keeps the catalog off any third-party search service and works with every provider.

### Gaps
- No sources were gathered on in-browser LLMs (WebLLM, Chrome built-in AI) and how well they call tools, or on CORS and key-storage best practice for bring-your-own-key static apps.
