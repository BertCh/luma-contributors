# CPU suitability of the contributors and mixed CPU/GPU execution (2026-11-11)

Written in this repository. Basis of [roadmap section 13](../../roadmap.md) and of section 14 of the [contributor contract](../../contributor-contract.md).

The question: which contributors are better served by the CPU, and how can a CPU implementation run in one graph with GPU contributors using what published luma.gl (`10.0.0-alpha.12`) already has.

## 1. What luma.gl provides

Read from `node_modules/@luma.gl/graph/src/gpu-core`. Every symbol below is exported from `@luma.gl/graph/gpu-core` or `@luma.gl/graph/gpu-data`.

- `GPUGraph` is a program of operations over named logical values (scalars, vectors, textures). `graph.compile(device, {outputs, outputLocations, lowerings})` returns a `CompiledGPUGraph`; `run({inputs})` accepts each input as a `GPUVector` or a `CPUVector`.
- `GPUCPUOperation({id, inputs, outputs, execute})` is a CPU stage. `execute` receives packed `Float32Array`, `Int32Array` or `Uint32Array` rows and returns arrays. luma.gl's own example is `CPUProjectionOperation` in `gpu-project`.
- `GPUCPUExecution` runs a graph that has a CPU operation, a `CPUVector` input or an output with location `'cpu'`. It turns each GPU operation into its own compiled stage, reads a value back the first time a CPU stage needs it, and uploads a CPU result the first time a GPU stage needs it. `outputLocations` says where each output is returned.
- A GPU operation needs a `contract` (the values it reads and writes, by name, with output shapes) and a `GPUOperationLowering` that turns it into command nodes. The lowering receives `resolveVector(name)`, which returns the views the graph bound for a value.
- Limits of the mixed executor, all asserted in `gpu-cpu-execution.ts`: no textures in the program; no state vectors; vector formats `float32`, `sint32`, `uint32` with one to four components; no null bitmaps or list offsets on CPU inputs; outputs of a mixed run are owned by the invocation (no caller-provided targets).

## 2. Why the contributors could not use it, and the bridge

All 466 contributors are `GPUCommandNodeProducer`s: they take `GraphDataView`s when constructed and emit command nodes into a caller's `GPUCommandGraph`. `GPUGraph` accepts a producer as an operation, but a producer has no contract, so the graph cannot plan its values and the mixed executor rejects it. Nothing in `modules/*/src` used `GPUGraph` before this work.

The bridge is `GPUContributorOperation` (`analysis-core/operations`): it declares a contributor's ports as a contract over named values, and one lowering, `GPU_CONTRIBUTOR_OPERATION_LOWERING`, resolves the ports to views and builds the contributor. No luma.gl change and no private import is needed. A CPU twin is a `GPUCPUOperation` subclass with the same named values.

## 3. Measurements

Headless Chromium on the development Mac (Apple GPU), best of four or five runs.

| What | Result |
| --- | --- |
| Variogram model fit (20 bins, 3 models) between two CPU stages, GPU contributor as the fit stage | 1.6 to 2.5 ms per run |
| The same graph with the CPU twin as the fit stage | 0.5 ms per run |
| One CPU stage boundary (readback, identity callback, upload), 1,000 rows of `float32x2` | 0.7 ms |
| The same, 100,000 rows | 10.7 ms |
| The same, 1,000,000 rows | 90 ms |
| The same, 4,000,000 rows | 352 ms |

The boundary costs about 11 ns per byte, several times a raw readback. `readCPUVector` and `getCPUView` in `gpu-cpu-execution.ts` copy row by row (one `Uint8Array` per row) even when the rows are already packed, and the upload snapshots the data again. This is an upstream improvement (roadmap UPS-CPU-1), not something to work around here. Until it lands, a CPU stage pays off when the vectors that cross it are small or when it replaces many dispatches.

## 4. The survey

Seven read-only agents (Codex CLI, `gpt-6.1-sol`) each read one slice of `modules/analysis/src` and recorded one row per contributor and per recipe: the shape of the GPU algorithm, documented caps, whether I/O is vectors or textures, an existing CPU reference, and a verdict. The rows are in [survey.json](./survey.json). Coverage: 463 of the 466 contributor files (the two `computation-record` taps and `quantile-lisa-recipe.ts` were outside the slices) and the recipes. The caps cited for `GPUNetworkLouvain`, `GPURadiationFlowModel`, `GPUAlternativeRoutes` and `GPUNetworkStructure` were checked against the source by hand; the rest of the rows are leads to verify when a twin is written.

Signals that favour the CPU: (1) serial by nature, (2) rounds unrolled into command nodes, (3) small by construction, (4) needs precision the shader lacks, (5) a CPU reference already exists.
