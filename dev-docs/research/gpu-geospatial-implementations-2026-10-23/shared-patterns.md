# Shared GPU patterns for geospatial contributors

Research: 2026-10-23. Scope: analytical contributors and the shared machinery they need; no rendering recommendations. Evidence is the current dirty working tree plus primary upstream source/docs. No repository files changed, kernels run, or performance claims certified. The three requested roadmaps and AGENTS.md were read; historical roadmap status is subordinate to current code.

## Existing substrate and actual seams

The project already has most foundational algorithms. [modules/graph/src/gpu-core/gpu-scan.ts](../../../modules/graph/src/gpu-core/gpu-scan.ts) implements hierarchical inclusive/exclusive uint32 scan, segmented flags, logical scans across independently chunked `GraphVectorView`s, and a capability-selected subgroup path. Segmented scans force the portable path. Arithmetic explicitly wraps modulo 2^32. The October 14 “subgroups later” roadmap language is stale.

[gpu-sort.ts](../../../modules/graph/src/gpu-core/gpu-sort.ts) already provides stable out-of-place key/payload uint32 sorting, small-input bitonic selection, four/eight-bit radix digits, configurable keys/thread (default eight), chunk-aware machinery and separate dispatches without inter-workgroup spinning. [gpu-compaction.ts](../../../modules/graph/src/gpu-core/gpu-compaction.ts) composes scan/scatter and returns a GPU count. These are improvement targets, not missing algorithms. Their public props lack GPU live-count/condition inputs; compaction requires output capacity at least the full input length. A downstream sort still processes allocation capacity after filtering.

[gpu-segmented-reduction.ts](../../../modules/graph/src/gpu-core/gpu-segmented-reduction.ts) offers scalar sum/min/max with one workgroup per CSR segment. [modules/graph/src/utils/load-balanced-for-each.ts](../../../modules/graph/src/utils/load-balanced-for-each.ts) already supplies merge-path traversal and tiled segment sums, including carry fixup. [gpu-adaptive-spmv.ts](../../../modules/graph/src/gpu-core/gpu-adaptive-spmv.ts) and [gpu-spmv-strategy.ts](../../../modules/graph/src/gpu-core/gpu-spmv-strategy.ts) offer scalar, subgroup, workgroup and split-long-row CSR multiplication with independent chunks and optional caller-known row statistics. [gpu-conjugate-gradient-program.ts](../../../modules/graph/src/gpu-core/gpu-conjugate-gradient-program.ts) builds a semantic GPU-controlled CG program. Therefore “add sparse operations/CG/load balancing” is the wrong backlog item: consolidate contracts and extend difficult cases.

The older `modules/gpgpu/src/operations/{dot,segmented-map}.ts` are deferred evaluator operations; `dot` is a per-row vector dot, not a global analytical reduction. Prefer graph-native primitives for new contributors rather than adding a competing evaluator route.

[gpu-data/gpu-vector.ts](../../../modules/gpgpu/src/gpu-data/gpu-vector.ts) already preserves data chunks and ownership. [GPURecordBatch](../../../modules/graph/src/gpu-tables/table/gpu-record-batch.ts) records source batch identity. Do not repack streams implicitly to accommodate algorithms. [gpu-tables/utils/gpu-table-buffer-planner.ts](../../../modules/graph/src/gpu-tables/utils/gpu-table-buffer-planner.ts) is predominantly shader/draw binding planning and is not the analytical scheduling abstraction to expand.

Shared numerical/status contracts also exist: `analysis-core/contracts/{status,capacity-planning,model-result}.ts`, [utils/fixed-point-accumulator.ts](../../../modules/graph/src/utils/fixed-point-accumulator.ts) (96-bit, power-of-two quantization and a documented error bound), and exact orientation/lattice/geometry WGSL. Kriging currently performs bounded per-invocation Gaussian elimination with partial pivoting and rejects unreliable pivots. Regression reports conditioning. New solves should reuse these semantics rather than introduce anonymous booleans.

## Eight primary reference entries

1. **WGSL specification**, especially [memory model](https://www.w3.org/TR/WGSL/#memory-model), [atomic builtins](https://www.w3.org/TR/WGSL/#atomic-builtin-functions), and [uniformity](https://www.w3.org/TR/WGSL/#uniformity). Atomics use relaxed ordering; an atomic flag does not publish unrelated ordinary writes. Barriers have workgroup scope, and collective operations require uniform control flow. Consequently use dispatch boundaries for cross-workgroup phases, keep tail lanes participating in barriers, and never treat a subgroup as a fixed CUDA warp. These are normative constraints on every proposed kernel, including frontier queues and staged reductions.

2. **GPUPrefixSums**, actual WGSL [reduce-then-scan](https://github.com/b0nes164/GPUPrefixSums/blob/main/GPUPrefixSumsWebGPUapis/SharedShaders/rts.wgsl) and [decoupled-fallback scan](https://github.com/b0nes164/GPUPrefixSums/blob/main/GPUPrefixSumsWebGPUapis/SharedShaders/csdldf.wgsl). They demonstrate per-thread vectorized loads, subgroup aggregation and fallback recomputation when predecessor progress stalls. Critical incompatibility: `csdldf.wgsl` stores two state bits in the same uint32 as its sum (`sum << 2`, read `>> 2`), leaving 30 payload bits; directly copying it would violate luma's uint32 scan contract. Treat fallback scan as an opt-in experiment after a memory/progress proof, preserving hierarchical scan. The [license](https://github.com/b0nes164/GPUPrefixSums/blob/main/LICENSE) verifies MIT, Thomas Smith; the README itself warns its fallback version is dated.

3. **FidelityFX Parallel Sort**, actual [FFX_ParallelSort.h](https://github.com/GPUOpen-Effects/FidelityFX-ParallelSort/blob/master/ffx-parallelsort/FFX_ParallelSort.h) and [algorithm description](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/parallel-sort/). It separates count, count reduction, hierarchical prefix and scatter; it supports indirect execution. Use it to study live-count dispatch setup, digit-width and block scheduling, since luma already implements the basic algorithm. Its wave operations and RDNA tuning are not portable defaults. The source header verifies AMD's MIT terms; retain attribution if adapting code.

4. **ModernGPU**, [segmented reduction explanation](https://moderngpu.github.io/segreduce.html) and actual [kernel_segreduce.hxx](https://github.com/moderngpu/moderngpu/blob/master/src/moderngpu/kernel_segreduce.hxx). Merge-path/load-balancing search separates work assignment from segment boundaries and handles carry combination. Extend luma's existing utility toward generic reduction states and independently chunked descriptors; compare against one-workgroup-per-row when segment sizes are homogeneous. Licensing is version-specific: the historical documentation has NVIDIA BSD-3-Clause, whereas current [LICENSE.md](https://github.com/moderngpu/moderngpu/blob/master/LICENSE.md) has Sean Baxter's two-clause BSD terms. Pin the file/version before adaptation.

5. **CUB/CCCL**, actual [device_segmented_reduce.cuh](https://github.com/NVIDIA/cccl/blob/main/cub/cub/device/device_segmented_reduce.cuh). Its API distinguishes segment descriptors, initial values, operation and temporary storage; inspect empty-segment behavior and alias constraints as contract examples. Its source explicitly declares `BSD-3` and Merrill/NVIDIA copyright. CUDA implementation policies are comparative evidence, not a WebGPU dependency. This helps define portable grouped reductions for PC02 voxels, RS01 coverage summaries, EC01 class metrics and ST11 sparse OD marginals.

6. **CCCL determinism contract**, [official documentation](https://nvidia.github.io/cccl/unstable/cccl/determinism.html). It distinguishes unspecified, same-device repeated-run and cross-GPU reproducibility, with type/operator limits and version/tuning qualifications. Adopt this precision of documentation; do not equate a fixed f32 reduction tree with cross-adapter bitwise equivalence. Luma's integer fixed-point accumulator is already a stronger tool for sums, but its quantization cannot restore precision lost when forming each f32 product or squared distance.

7. **MAGMA**, actual [tiny batched LU kernel](https://github.com/icl-utk-edu/magma/blob/master/magmablas/zgetrf_batched_smallsq_noshfl.cu) and [batched interface](https://icl.utk.edu/projectsfiles/magma/doxygen/group__batched.html). The kernel retains matrix entries in registers, communicates pivots through shared memory, and reports per-matrix failure. It also uses warp synchronization and CUDA/HIP specialization, which need redesign for uniform WGSL workgroup barriers. Study fusion and size bucketing, not literal translation. The repository [COPYRIGHT](https://github.com/icl-utk-edu/magma/blob/master/COPYRIGHT) verifies University of Tennessee BSD-style three-clause terms. No claim that MAGMA is available in browsers.

8. **Shewchuk**, [adaptive precision predicates paper and code](https://www.cs.cmu.edu/~quake/robust.html). Fast filters followed by certified exact work are the relevant pattern for topology. Existing luma exact-orientation code deliberately uses integer significands because shader compilers may reassociate floating error-free transforms. Keep the exact sign separate from approximate intersection coordinates and construction precision. Shewchuk explicitly puts the predicate C code in the public domain; this does not cover Triangle, which the same page says is copyrighted.

## Proposed shared contracts, in priority order

**P0 — GPU cardinality and gating.** Extend existing scan/sort/compaction descriptions with `rowCount: number | GraphDataView<'uint32'>`, an explicit allocation capacity, and the established GPU node condition. The count is a logical prefix, checked against capacity; output cardinality/status must be deterministic for zero rows and disabled execution. Stable sort guarantees equal-key order across chunks; unused tails must never enter later scans/reductions. Preserve full-width uint32 semantics. Bounded compaction should distinguish accepted requirement from stored count and candidate overflow. These contracts unblock filtering-heavy PC02, PP05 and MV03 and make repeated GE repairs stop doing full-capacity work. Allocation remains caller-owned, without control-flow readback.

**P1 — Segment-state reductions and sparse traversal.** Build on the existing merge-path utility: explicit CSR offsets plus item capacity/live extent, source chunk topology, reduction identity, deterministic tie rule, and typed state merge. Start with count/sum/min/max/argmin, then stable centered moments (count, mean, covariance state) for PC01/PC06 and weighted statistics for RS01/TE05. Empty segments must return identity plus validity rather than fabricated means. Expose strategy diagnostics and scratch estimates; benchmark the existing adaptive SpMV before introducing another implementation. GPU-derived row statistics must select via gated kernels, not CPU readback.

**P1 — Reusable bounded frontier phases.** [gpu-network/network-reachability/network-frontier.ts](../../../modules/graph/src/gpu-network/network-reachability/network-frontier.ts) already implements compact queues, marks and indirect round control. Extract enqueue/deduplicate/advance only where a second contributor needs identical semantics; relaxations/objectives remain domain-specific. Define duplicate policy, capacity overflow, current/next counts, iteration count and convergence. NW02 residual flow, NW04 coarsening, PP04 ordering and TE02 branching transport need different correctness certificates. GPU gating eliminates work after convergence but does not automatically eliminate an unrolled graph's construction/encoding cost; measure both.

**P1/P2 — Small batched numerical kernels.** Reuse existing kriging/GWR code as baselines and define matrix stride, size buckets, right-hand sides, mask, optional regularization, pivot/rank status and residual evidence. Use SPD Cholesky only for proven SPD systems; augmented ordinary/universal kriging is generally indefinite. Offer pivoted LU for general square systems and QR for least squares; PC01 needs a symmetric 3×3 eigensolve, PC05 a rigid-transform decomposition, and MV01 covariance updates. Those are distinct kernels sharing layout, scratch and diagnostic conventions. Avoid inverse-matrix APIs as the default solve path. Compare private per-invocation matrices with cooperative workgroup/storage scratch to expose register-spill cliffs.

**P2 — Numeric certification adapters.** Keep exact predicate behavior, coordinate construction precision, fixed-point summation error and solver conditioning separate. Local-frame origin/scale metadata should cross contributor boundaries, especially projected coordinates, terrain bias fits and 3D covariance. Surface invalid/non-finite, ill-conditioned, uncertain and iteration-limited outcomes using existing status vocabulary. Benchmark subgroup f32 paths against the selected accuracy/reproducibility contract; integer scan/sort optimizations should remain exact.

## Benchmarks and promotion gates

Run same-session A/Bs against current primitives, then complete contributor pipelines. Include sizes 0/1, workgroup boundaries, chunk seams, and 10³–10⁷ elements within adapter limits. Scan/sort datasets need all-equal, sorted/reversed, narrow/wide keys, uint32-wrap cases and 1/10/100% live prefixes. Segment/CSR cases need empty rows, uniform short rows, power-law degrees and a single million-entry hub. Frontier cases need long chains, grids, dense fronts and disconnected graphs. Solves need 3/4/8/16/32-variable buckets, multiple RHS, near-duplicate samples, ill-conditioning, singularity and indefinite kriging systems.

Report cold pipeline compilation, graph construction/node count, warm GPU timestamps when supported, submission/encoding, end-to-end latency, scratch/peak bytes, useful rows/edges per second, convergence and error. Compare Apple, Intel, AMD and NVIDIA adapters; force portable paths and test subgroup paths separately. Baseline limits must work before optional raised-limit results. Oracle/property gates include stable permutations, exact integer counts, chunk-invariance where promised, residuals/backward error, covariance symmetry, conservation and explicit incomplete results. External CUDA throughput is algorithm evidence, never a browser speedup claim. No tests/build/install were run for this read-only research; future code changes must follow AGENTS.md formatting and build/test gates.
