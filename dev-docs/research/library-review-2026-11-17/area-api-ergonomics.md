# Consumer ergonomics and API consistency across `@luma-contributors/analysis`

## What I checked

The first changes I would make are to fix a `validity` output that rejects successful rows when used as a mask, and to fix two prepared spatial handles that mark their indexes clean before submission. Both are reachable through ordinary public APIs. The broad contributor calling convention is already quite consistent.

I reviewed the working tree read-only. I parsed **1,710 source files**, followed the barrels for all **11 package entry points**, traced six consumer workflows, and sampled 30 distinct error sites. I ran small JavaScript probes against extracted CPU logic and typed-array representations. I did not run a compiler, build, test, browser, GPU workload, package install, or tree-shaking benchmark.

I read both READMEs, the contributor contract, the public operation guide, package manifest, build and export-verification scripts, the operation bridge, mixed-execution test helper, raster grid/band helpers, population alignment CPU twin, and class-break GPU wrapper in full. I sampled all six families’ docs, implementations and specs. For size and recency, I examined the public contracts and validation of `GPUDelaunayTessellation`, the largest contributor implementation by source bytes, the larger ontology annotation file, and the spacing contributor from the most recent analysis commit, `69305eb4`. I checked the roadmap and earlier library, workflow, CPU and correctness reviews for overlap. I used examples only to inspect consumer code.

For example, these are the two ends of the spatial workflow. `view` in my notes creates the buffer, imports its handle, derives row count from the format, and tracks the backing buffer for readback and destruction. It is local example code.

```js
const device = await luma.createDevice({type: 'webgpu', adapters: [webgpuAdapter]});
const graph = new GPUCommandGraph(device);
graph.add(new GPUPointDensity({
  positions: view('positions', 'float32x2', Float32Array.of(0.5, 0.5)),
  bounds: [0, 0, 2, 2],
  gridSize: [2, 2],
  output: {values: view('values', 'float32', new Float32Array(4))}
}));
const compiled = await graph.compileAsync();
compiled.encode(device.commandEncoder, {parameters: undefined});
device.submit();
const bytes = await valuesBuffer.readAsync();
const values = new Float32Array(bytes.buffer, bytes.byteOffset, 4);
```

## Findings

### ERG-01 Population alignment publishes the inverse of the library’s validity convention [P0] [correctness]

- **Evidence.** The contract says “`validity` (`uint32`, nonzero is valid).” `GPUPopulationSupportAlignmentOutput.validity` instead means **0 matched, 1 missing, 2 ambiguous**. The CPU twin and tests preserve those codes deliberately. A downstream quantile operation keeps a row when `mask[row] !== 0`. An extracted CPU probe with source ID `[7]` and targets `[7, 8]` produced validity `[0, 1]`. Using it as the mask for target-aligned values `[10, 99]` kept **only `99`**, the unsupported row. [Contract:42](../../../dev-docs/contributor-contract.md#L42) · [output:27](../../../modules/analysis/src/gpu-spatial-analysis/landscape-ecology/gpu-population-support-alignment.ts#L27) · [CPU encoding:67](../../../modules/analysis/src/gpu-spatial-analysis/landscape-ecology/cpu-population-support-alignment-operation.ts#L67) · [mask consumer:69](../../../modules/analysis/src/dataframe-analysis/column-classification/cpu-column-quantiles-operation.ts#L69) · [existing fixture:39](../../../modules/analysis/test/gpu-spatial-analysis/urban-ecology/cpu-population-support-alignment-operation.node.spec.ts#L39)
- **Why it matters.** The ports have compatible types. A consumer following the package-wide rule gets an inverted selection with no error. The family reference describes the legacy codes, but generic composition and editor completion expose `validity`. [Family reference:382](../../../docs/api/gpu-spatial-analysis/landscape-ecology.md#L382)
- **Proposed change.** Add `alignmentCode` for the diagnostic and an optional boolean `matchedMask` on the contributor, both operations, CPU result and recipe. Deprecate the legacy `validity` spelling. Preserve its bytes during migration. Add a composition test that passes `matchedMask` to a second operator and checks selected IDs. **M, additive initially.**
- **Confidence.** High. The selection reversal was verified on the CPU. `KNOWN(CPU-04)` records the operation conversion as done. This is a separate composition defect in that completed path.

### ERG-02 Discarding an encoder can consume a prepared-index rebuild [P0] [correctness]

- **Evidence.** Both `GPUSpatialJoinPrepared` and `GPUStudyWindowPreparation` set `this.dirty = false` when the last node’s CPU condition is evaluated. luma.gl evaluates it during `encode`. Submission is a separate application action. In a probe of both extracted latch bodies, the first two-node encoding returned `[true, true]`. With no submission, the next encoding returned `[false, false]`. The join documentation explicitly describes a moved feature being missed when queries use old boxes. [Join latch:567](../../../modules/analysis/src/gpu-spatial-analysis/spatial-join/gpu-spatial-join-prepared.ts#L567) · [window latch:767](../../../modules/analysis/src/gpu-spatial-analysis/study-window/gpu-study-window-preparation.ts#L767) · [luma.gl condition evaluation:1673](../../../node_modules/@luma.gl/graph/src/gpu-core/gpu-command-graph.ts#L1673) · [submission contract:263](../../../docs/api/gpu-spatial-analysis/concepts.md#L263) · [stale-index consequence:287](../../../docs/api/gpu-spatial-analysis/operators-joins.md#L287)
- **Why it matters.** A host can invalidate a prepared index, encode a frame, discard it, then submit the next frame. The second encoding skips the rebuild even though the persistent buffers still contain the earlier generation. The host followed the documented invalidation procedure.
- **Proposed change.** Reuse the requested/applied-generation design already used by conditional Gaussian simulation. Commit the applied generation as part of executed GPU work. Add a discard-then-submit case for each handle, using a moved polygon or changed study window. Preserve `encodedBuildCount` as an encoding metric if callers use it. **M, nonbreaking.** [Existing design:108](../../../modules/analysis/src/gpu-spatial-analysis/spatial-interpolation/gpu-conditional-gaussian-simulation.ts#L108)
- **Confidence.** High for the skipped rebuild. **UNVERIFIED** for the numerical GPU output of the discard sequence.

### ERG-03 `GPUParameterBuffer<'float32'>` accepts integer arrays and writes their bits unchanged [P0] [correctness]

- **Evidence.** The public generic controls the graph view format, while both `values` and `write()` accept all three array types. The constructor sends `props.values` straight to `buffer.write`; WebGPU writes the underlying bytes. `new Uint32Array(Float32Array.of(1).buffer)[0]` is `1065353216`. In the other direction, integer `1` becomes float `1.401298464324817e-45`. These are host-verifiable byte representations. The constructor also bypasses the range check used by `write`, and `write` permits fractional `firstElement` values through its own check. [Props:28](../../../modules/analysis/src/analysis-core/kernels/gpu-contributor-utils.ts#L28) · [constructor:57](../../../modules/analysis/src/analysis-core/kernels/gpu-contributor-utils.ts#L57) · [write:85](../../../modules/analysis/src/analysis-core/kernels/gpu-contributor-utils.ts#L85) · [byte write:93](../../../node_modules/@luma.gl/core/src/webgpu/adapter/resources/webgpu-buffer.ts#L93)
- **Why it matters.** A type-correct call can change a numeric threshold or index by orders of magnitude. This helper appears in all five landing-page code examples.
- **Proposed change.** Introduce `GPUParameterValues<Format>` mapping each scalar format to its array type. Validate the array representation, logical length, and integer offset before allocation or upload. Use the same checks for initial values and updates. If raw-bit writes have consumers, give them an explicitly named method. **S, type-tightening for mismatched callers.**
- **Confidence.** High. No GPU result is needed to establish the representation mismatch.

### ERG-07 Class breaks accepts a different input contract when switched to its CPU twin [P1] [consistency]

- **Evidence.** The shared operation props require `rowCount` and optionally specify `valuesFormat`. The GPU wrapper resolves `values` with a three-format union. The contributor accepts all three formats and derives its row count from `props.values.length`. The CPU twin chooses a reader from `valuesFormat`, defaults to float32, and rejects `values.length !== props.rowCount`. Thus a real `uint32` input with omitted `valuesFormat` passes the GPU contributor’s format check and fails the CPU reader. [Shared props:10](../../../modules/analysis/src/dataframe-analysis/column-classification/gpu-class-breaks-operation.ts#L10) · [GPU factory:52](../../../modules/analysis/src/dataframe-analysis/column-classification/gpu-class-breaks-operation.ts#L52) · [GPU validation:297](../../../modules/analysis/src/dataframe-analysis/column-classification/gpu-class-breaks.ts#L297) · [CPU reader:345](../../../modules/analysis/src/dataframe-analysis/column-classification/cpu-class-breaks-operation.ts#L345) · [reader format check:23](../../../modules/analysis/src/analysis-core/operations/cpu-operation-rows.ts#L23)
- **Why it matters.** The public guide tells users to switch execution by changing the operation class. Here the same logical values and props can require a second change. This difference concerns input schema, independently of documented numerical or algorithmic differences.
- **Proposed change.** Derive the actual format on both paths. Treat an explicitly supplied `valuesFormat` or `rowCount` as an assertion on both. For future wrappers, describe permitted input formats and shape constraints once and use them when resolving CPU and GPU ports. Add parity cases for omitted format on an integer input and an explicitly inconsistent row count. **M, additive for inferred CPU formats; tightening for inconsistent GPU declarations.**
- **Confidence.** High for the divergent host-side checks.

## Future

1. **Introduce entry-qualified operator and port metadata incrementally.** Start with visibility, class breaks and population alignment. Record import, available forms, port direction, shape, polarity, ownership and status layout. Use it for catalog checks and documentation before generating any implementation. The cost is maintaining descriptors; shared CPU/GPU validation and unambiguous lookup give that maintenance an immediate return.
2. **Pilot one domain-level array-to-result facade.** Point density exercises coordinates, gridding, allocation and readback with a small result contract. Accept an existing device and return typed values plus status. Keep the producer available for repeated frames. Measure adoption before adding facades to other families. This avoids committing to hundreds of high-level wrappers.
3. **Take generic graph conveniences upstream.** A typed raw-buffer view import and a typed-array constructor for CPU graph vectors would benefit every luma.gl consumer. Reuse the existing public GPU-data import path wherever it fits. Analysis should own raster bands, compact result interpretation and domain-specific decoding. This keeps the dependency boundary intact at the cost of coordinating upstream releases.
4. **Make the release fixture a real consumer.** Install the packed artifact, exercise promised Arrow-free imports, check documented import names and README destinations, and run the six short workflows in the existing headless release environment. The slower release job buys coverage that source-relative specs and workspace export checks cannot provide.
