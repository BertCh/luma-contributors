# GPU network contributors

The highest-priority fixes are at boundaries between working algorithms. A partial cost table can become an authoritative “no route” in map matching. Two public centrality helpers disagree on the type and meaning of `reset`. Isochrones can accept the same writable range for two different promised results. Each has a small regression case that the lead can assign independently.

### Network model and input inventory

The common routing representation is outgoing CSR. Vertex `u` owns slots `[offsets[u], offsets[u+1])`. Offsets and neighbors are packed `uint32`, costs are aligned `float32`, and optional node positions are `float32x2`. `neighbors.length` is capacity. The final offset can be smaller. Parallel slots and self-loops are permitted. Undirected consumers generally expect reciprocal slots for non-loop edges. The topology validator checks formats and lengths without reading GPU data. [Topology definition and validation](../../../modules/analysis/src/analysis-core/network-topology.ts:12)

**22 of 41 classes require top-level CSR**, including the centrality schedule step through inheritance. Two more accept top-level CSR optionally or as one branch, flow and Louvain. Path extraction accepts it inside `edges`. The other 16 consume geometry, an edge or transition list, a cost matrix, or an upstream result. The claim that this is “the one network input of every `gpu-network` contributor” overstates an otherwise useful contract. Five classes declare `directed?: boolean`. Analytics columns infer direction from the presence of `reverseTopology`. [Topology claim](../../../modules/analysis/src/analysis-core/network-topology.ts:12) · [Analytics direction rule](../../../modules/analysis/src/gpu-network/network-analysis/gpu-network-analytics-columns.ts:62)

## Findings

### NET-01 Map matching treats an unfinished cost table as exact [P0] [correctness]

- **Evidence.** The table publishes partial rows when its round budget runs out. Its docs explicitly tell consumers to reject a table that overflowed **or did not converge**. The matcher reads only `routeTable.status?.overflow`. A missing table entry yields `-1.0`, the row is marked resolved, and A* returns immediately. The existing nine-node chain fixture specifies the important combination: one round, capacity 81, `overflow=0`, `iterationLimitReached=1`. The end-to-end matcher fixture wires only `overflow`. [Producer contract](../../../modules/analysis/src/gpu-network/network-cost-table/gpu-network-cost-table.ts:71) · [Consumer guard](../../../modules/analysis/src/gpu-network/map-matching/gpu-map-matching.ts:829) · [A* bypass](../../../modules/analysis/src/gpu-network/map-matching/gpu-map-matching.ts:1783) · [Lookup and resolution](../../../modules/analysis/src/gpu-network/map-matching/gpu-map-matching.ts:1915) · [Chain fixture](../../../modules/analysis/test/gpu-network/network-cost-table/network-cost-table-stopping-status.spec.ts:44) · [Matcher fixture](../../../modules/analysis/test/gpu-network/map-matching/gpu-map-matching.spec.ts:236)
- **Why it matters.** A reachable transition more than one hop down that chain can look impossible. A finite incumbent can also make a transition look more expensive. Both can change the matched track without a route-overflow warning.
- **Proposed change.** Add a one-word `usable` output to the table, computed as `converged && !overflow`, and accept it in `GPUMapMatchingRouteTable` and its operation form. Use that word in place of the existing overflow binding to preserve the eight-binding path. Test two encodings of the same graph, first with an exhausted table and then a complete one, against A*-only matching. **M, additive.**
- **Confidence.** High on the missing guard. `UNVERIFIED` end-to-end GPU result.

### NET-02 The centrality schedule’s reset value discards earlier batches when forwarded to continuation [P0] [correctness]

- **Evidence.** The public planner emits `reset: Number(pivotOffset === 0)`. The public continuation explicitly recommends combining the two helpers, but `runBatch` takes a boolean and publishes `Number(options.reset !== false)`. For the planner’s sequence `[1, 0, 0]`, that expression produces `[1, 1, 1]` in JavaScript. The merge reads the previous total only when the word is zero. The continuation test constructs batches with boolean resets. [Planner](../../../modules/analysis/src/gpu-network/network-centrality/gpu-network-centrality-schedule-step.ts:74) · [Composition instructions](../../../modules/analysis/src/gpu-network/network-centrality/network-centrality-continuation.ts:640) · [Conversion](../../../modules/analysis/src/gpu-network/network-centrality/network-centrality-continuation.ts:696) · [Merge](../../../modules/analysis/src/gpu-network/network-centrality/network-centrality-continuation.ts:584) · [Fixture type](../../../modules/analysis/test/gpu-network/network-centrality/network-centrality-continuation.spec.ts:39)
- **Why it matters.** `runner.runBatch(step)` is rejected by TypeScript. In JavaScript it silently requests replacement every time, losing earlier betweenness totals and failure flags.
- **Proposed change.** Narrow the planner field to `0 | 1`, accept `boolean | 0 | 1` in `runBatch`, and normalize with `Number(Boolean(options.reset ?? true))`. Feed actual planner descriptors to a two-batch continuation test where both batches contribute to the same vertex. **S, backward-compatible.**
- **Confidence.** High. The host conversion was verified with a pure Node expression. `UNVERIFIED` GPU accumulation.

### NET-03 Isochrones can overwrite their own published node costs [P0] [correctness]

- **Evidence.** With `startNodes`, `costs` is a promised output. The constructor puts it and `raster.output.values` in `geometryOutputs`, then compares those outputs with **inputs**. The shared validator never compares two outputs. Reachability writes `props.costs`; later, raster decode writes `raster.output.values`. The cell-outline path subsequently reads `props.costs` again. [Output contract](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:259) · [Validation](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:599) · [Validator implementation](../../../modules/analysis/src/analysis-core/kernels/gpu-contributor-utils.ts:167) · [Search destination](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:697) · [Raster destination](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:712) · [Decode write](../../../modules/analysis/src/gpu-network/network-isochrones/network-isochrones-passes.ts:336) · [Later cell read](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:847)
- **Why it matters.** Four nodes, a 2×2 raster and one four-row float view supplied for both fields are sufficient. The two meanings cannot survive in the same four words. With both geometry paths enabled, this can also change which nodes enter the cell outline.
- **Proposed change.** Apply `validateNetworkWritableViews` to the complete named bag of logical outputs, with per-dispatch checks where required. Include search results only when the contributor writes them. Test identical ranges, overlapping subviews, and disjoint ranges in a shared allocation. **S, rejects previously accepted destructive aliases.**
- **Confidence.** High on ownership and write order. `UNVERIFIED` device outcome.

### NET-04 Travel-time percentiles can select the adjacent observation [P0] [correctness]

- **Evidence.** The public definition is nearest rank `ceil(p / 100 * n)`. Both implementations subtract `1e-9` before taking the ceiling. For two departures and the accepted percentile `50.00000001`, the documented rank is 2 and both implementations select rank 1. The earlier math review recorded the guard and that the spec repeated the expression. This counterexample establishes its observable effect. [Public definition](../../../modules/analysis/src/gpu-network/network-time-geography/gpu-network-travel-time-percentiles.ts:63) · [GPU rank, calculated on host](../../../modules/analysis/src/gpu-network/network-time-geography/gpu-network-travel-time-percentiles.ts:276) · [CPU rank](../../../modules/analysis/src/gpu-network/network-time-geography/cpu-network-travel-time-percentiles-operation.ts:117) · [Earlier review](../../../dev-docs/research/math-correctness-review-2026-11-10/network-paths.md:365)
- **Why it matters.** On travel times `[5, 90]`, this returns 5 instead of 90. The input interval is narrow, but the output error is unbounded by the percentile tolerance.
- **Proposed change.** Use one host-side nearest-rank helper for both implementations. Pin hand-selected ranks immediately below, at, and above 50%, plus integer percentages whose binary quotient rounds near a boundary. **S, changes results in the erroneous boundary interval.**
- **Confidence.** High. Verified with `node -e 'const r=50.00000001/100*2; console.log(Math.ceil(r),Math.ceil(r-1e-9))'`, which prints `2 1`.

### NET-05 The CPU flow operation ignores a declared input that determines GPU validity [P1] [correctness]

- **Evidence.** The GPU operation declares `topologyOffsets` and `topologyNeighbors`. The parallel solver checks row membership, target identity, monotonicity and the terminal offset. The CPU twin copies `operation.inputs`, then passes only edges, capacities, costs and parameters to its solver. An existing GPU fixture supplies the valid edge list `0→1→2` alongside malformed offsets and expects zero flow and `invalidCount=1`. [Operation inputs](../../../modules/analysis/src/gpu-network/network-optimization/gpu-network-flow-operation.ts:48) · [GPU checks](../../../modules/analysis/src/gpu-network/network-optimization/network-flow-parallel.ts:271) · [CPU execution](../../../modules/analysis/src/gpu-network/network-optimization/cpu-network-flow-operation.ts:225) · [Existing counterexample](../../../modules/analysis/test/gpu-network/network-optimization/network-flow-parallel.spec.ts:281)
- **Why it matters.** Switching execution backend can turn a rejected network into an apparently valid solution. It also defeats the use of the CPU operation as an oracle for pipelines that supply both representations.
- **Proposed change.** Extend `CPUNetworkFlowInput` with optional adjacency, read both declared ports, and mirror the parallel solver’s invalid-data result when they disagree. Reuse the existing malformed-offset fixture and add a matching-length wrong-neighbor case. Preserve the documented CPU differences in precision and budgets. **S, corrects behavior for inconsistent inputs.**
- **Confidence.** High on the CPU omission and fixture expectation. `UNVERIFIED` mixed-executor run.

### NET-06 The structure CPU twin declares SCC status values it never returns [P1] [correctness]

- **Evidence.** The GPU operation extends the shared props with `strongComponentsStatus` and adds its three requested outputs. The CPU constructor accepts the narrower base type, then constructs the GPU operation from the same object and copies **all** its output declarations. Its `execute` returns only `Object.entries(props.output)`. The three status names live outside that bag. [GPU-only extension](../../../modules/analysis/src/gpu-network/network-structure/gpu-network-structure-operation.ts:26) · [Output declarations](../../../modules/analysis/src/gpu-network/network-structure/gpu-network-structure-operation.ts:61) · [CPU declarations](../../../modules/analysis/src/gpu-network/network-structure/cpu-network-structure-operation.ts:201) · [CPU returned values](../../../modules/analysis/src/gpu-network/network-structure/cpu-network-structure-operation.ts:236)
- **Why it matters.** A typed variable containing GPU props can be passed structurally to the CPU constructor. Downstream graph stages can then depend on status values the CPU stage promises but never produces.
- **Proposed change.** Share the extended props type and return all requested status values from the exact Tarjan operation. Document the CPU meaning of `iterationCount`, and test that every declared output name is present in the execution result. **S, additive.**
- **Confidence.** High on the missing return values. `UNVERIFIED` executor response to the missing outputs.

### NET-07 A caller-owned isochrone cell table can make a valid facility outline fail [P1] [correctness]

- **Evidence.** `tableCapacity` is documented as applying when `table` is omitted. `cellFacilities` is documented as having `table.cells.length` rows. The implementation instead computes `capacity = cellOutline.tableCapacity ?? nodeCount` even for a supplied table, then uses that number for its default facility and minimum-cost buffers. The outline constructor requires `groups.length === cells.length`. [Public table contract](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:171) · [Capacity selection](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:854) · [Derived buffers](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:895) · [Outline check](../../../modules/analysis/src/gpu-spatial-analysis/cell-set-outline/gpu-cell-set-outline.ts:249)
- **Why it matters.** With 100 nodes, a caller-supplied 10-row cell table, `byFacility: true`, and omitted `cellFacilities`, the composer creates 100 group rows for 10 cell rows. This is a host-side shape error before dispatch.
- **Proposed change.** Resolve capacity once as `cellOutline.table?.cells.length ?? cellOutline.tableCapacity ?? nodeCount`. Validate supplied facility rows against that value in the outer constructor. Add a declaration-only test with a table smaller than the node count. **S, nonbreaking.**
- **Confidence.** High.

### NET-08 No lane count fits the advertised 100,000-node cost table on a 128 MiB binding at default rounds [P1] [ergonomics]

- **Evidence.** The class describes a target of roughly `1e5` nodes. With 64 rounds and no optional stopping outputs, its own estimate is `2 + 70 * ceil(nodeCount / laneCount)`. The 32,768-command cap requires **at least 214 lanes** at 100,000 nodes. The frontier check requires `8 * laneCount * nodeCount` bytes, permitting **at most 167 lanes** on a 128 MiB binding. At 167 lanes the estimate is still 41,932 commands. The default lane recommendation can be 32 or lower. [Scale claim](../../../modules/analysis/src/gpu-network/network-cost-table/gpu-network-cost-table.ts:134) · [Command calculation](../../../modules/analysis/src/gpu-network/network-cost-table/gpu-network-cost-table.ts:221) · [Frontier check](../../../modules/analysis/src/gpu-network/network-cost-table/gpu-network-cost-table.ts:248) · [Shared cap](../../../modules/analysis/src/analysis-core/kernels/gpu-contributor-utils.ts:495)
- **Why it matters.** Increasing lanes to satisfy the first error eventually triggers an error advising the caller to lower them. Lowering rounds can sacrifice table completeness, which is particularly consequential for NET-01.
- **Proposed change.** Add a pure `planNetworkCostTableBatches` that intersects command and binding constraints and reports when the interval is empty. Document the feasible envelope now. Support reusable source-row windows for callers that need all rows at the original round budget. **S for diagnostics/docs, M for windowed execution, additive.**
- **Confidence.** High. These are host formulas, independent of GPU performance.

### NET-09 The line graph’s turn penalties cannot be passed to snapped point routing [P1] [ergonomics]

- **Evidence.** `GPUNetworkLineGraph` produces CSR arc weights equal to the following edge’s cost **plus the turn cost**. `GPUNetworkPointRouting` takes allowed turn pairs and one cost per **base edge**. Its scalable path rebuilds CSR and assigns `weights[slot] = costs[outgoing]`. The terminal candidate adds only the destination fraction times its base-edge cost. The reference kernel uses the same cost model. [Line-graph output](../../../modules/analysis/src/gpu-network/network-line-graph/gpu-network-line-graph.ts:117) · [Point-routing inputs](../../../modules/analysis/src/gpu-network/network-optimization/gpu-network-point-routing.ts:49) · [Scalable arc cost](../../../modules/analysis/src/gpu-network/network-optimization/network-point-routing-scalable.ts:155) · [Terminal cost](../../../modules/analysis/src/gpu-network/network-optimization/network-point-routing-scalable.ts:265) · [Reference path](../../../modules/analysis/src/gpu-network/network-optimization/network-point-routing-reference.ts:55)
- **Why it matters.** A left turn and a straight movement into the same road can have different delays. One value per outgoing road cannot express that distinction. Flattening the line graph to allowed pairs retains bans but loses the preference that may determine the winning route.
- **Proposed change.** Accept a prepared turn graph with explicit per-turn penalties and separate base-edge costs. Charge the full turn penalty on entry to a partial destination. Preserve the current pair-list form as the zero-penalty case. Test two incoming roads to one destination edge with different penalties. **M, additive.**
- **Confidence.** High. This is an input-model gap.

### NET-10 The public flow-demand adapter still enforces the old reference solver’s limits [P1] [ergonomics]

- **Evidence.** `prepareGPUNetworkFlowDemands` enforces 126 input vertices, 1,024 expanded edges and a 24-bit total capacity. Its comments attribute those bounds to `GPUNetworkFlow`. The new solver automatically selects a parallel path above the reference caps and accepts up to 30 million vertices/edges subject to device and schedule limits. [Adapter limits](../../../modules/analysis/src/gpu-network/network-optimization/prepare-flow-demands.ts:12) · [Enforcement](../../../modules/analysis/src/gpu-network/network-optimization/prepare-flow-demands.ts:88) · [Current solver envelope](../../../modules/analysis/src/gpu-network/network-optimization/gpu-network-flow.ts:152)
- **Why it matters.** A 127-vertex supply/demand problem is rejected by the public preparation helper even though its 129-vertex transformed problem qualifies for the parallel solver. Users must reproduce the super-source/sink transformation to access the feature.
- **Proposed change.** Resolve solver limits against the **expanded** shape, share the integral bounds with the solver, and return the selected solver when capacity or cost requires parallel execution even on a small graph. Retain an explicit reference mode. Test 126 and 127 input vertices. **M, additive.**
- **Confidence.** High. `KNOWN(NW02)` understates the solver’s capabilities and misses this remaining adapter limit. Keep path decomposition as separate unfinished work.

### NET-11 The isochrone storage preflight baseline covers a real allocation gap [P1] [correctness]

- **Evidence.** The outer raster validation permits `width * height` up to `0x7fffffff`. `getCommandNodes` checks graph membership and can declare a search before creating its own `uint32[pixelCount]` raster. An 8,192² raster needs **256 MiB for `encoded` alone**. The equivalent cell branch creates two-word cell rows from a caller-selected capacity. The baseline rationale records integration ownership, without identifying a check that makes these sizes safe. [Shape check](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:518) · [Entry and search declaration](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:647) · [Raster scratch](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:712) · [Cell scratch](../../../modules/analysis/src/gpu-network/network-isochrones/gpu-network-isochrones.ts:854) · [Baseline rationale](../../../scripts/contributor-contract-baseline.json:193)
- **Why it matters.** A shape the constructor accepts can exceed a device binding before the caller gets a useful contributor-specific error. In this composer, discovering the problem late can follow earlier graph declarations.
- **Proposed change.** At the start of `getCommandNodes`, call `validateNetworkViewBindings` with named caller views and all selected scratch byte lengths, using the corrected table capacity from NET-07. Extend the existing no-allocation preflight spec to assert that a 128 MiB device rejects the 8,192² case before creating scratch or declaring search nodes. Remove the baseline entry. **S–M, earlier failure for unsupported configurations.**
- **Confidence.** High. `KNOWN(STD-14)` is under-prioritised for this remaining named exception. `UNVERIFIED` device-specific failure behavior.

### Round budgets and completion

| Path | Budget and dispatch | What a consumer can conclude |
|---|---|---|

## Future

1. **Publish a road-network preparation recipe with identity maps.** Accept stable external node and edge IDs, forward/reverse cost and optional edge geometry. Return outgoing CSR, its transpose, original-edge IDs and reciprocal slot IDs. Use published sort/COO primitives where applicable and keep the prepared views independently usable. OSMnx users bring keyed `(u, v, key)` edges and geometry; pgRouting users bring `id, source, target, cost, reverse_cost` and expect stable edge IDs in a route. A keyed adapter would remove more friction than another shortest-path class. The trade-off is extra mapping storage, which should be optional. [OSMnx conversion contract](https://osmnx.readthedocs.io/en/stable/user-reference.html#osmnx.convert.graph_from_gdfs) · [pgRouting input and output example](https://access.crunchydata.com/documentation/pgrouting/latest/pgr_dijkstra.html)
2. **Provide a source-row window for cost tables and other many-origin searches.** Compile one bounded graph, vary the source range per submission, and expose completion for each window. Centrality already demonstrates reusable submissions, caller-owned persistent outputs and explicit lifecycle. The trade-off is coordinating output offsets between windows; retaining independent per-window CSR blocks is a simpler first API than promising one contiguous global allocation. [Centrality schedule](../../../modules/analysis/src/gpu-network/network-centrality/gpu-network-centrality-schedule-step.ts:41)

Local centrality computes outward, reachable-only closeness. NetworkX defaults to inward distance on directed graphs and offers disconnected-graph scaling. igraph users can select traversal direction and request vertices, edges or both. A worked table and a helper for selecting the forward/reverse views can cover these expectations without duplicating algorithms.
