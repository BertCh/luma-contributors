# Fine-option audit for the earth showcase

Current review of candidate controls against source and graph contracts. Source readiness is distinguished from numerical acceptance below.

| Area | Current scene and contract | Recommendation | Independent oracle |
| --- | --- | --- | --- |
| Curvature estimator | `src/scenes/terrain/landforms.scene.ts` already exposes `curvatureMethod`: Evans–Young 3×3 least squares, Zevenbergen–Thorne 3×3 partial quartic, and Florinsky 5×5 polynomial. The help text distinguishes window size and Florinsky smoothing. `GPUTerrainCurvatureMethod` in `modules/graph/src/gpu-terrain/terrain-curvature/gpu-terrain-curvature.ts` confirms these are different derivative estimators. | No additional fine option is needed. Keep this as a compile-time method choice; do not describe the methods as interchangeable smoothing presets. Existing curvature kind and border controls cover adjacent choices. | Feasible on a small analytic DEM (plane, paraboloid, and quantized surface) with independent CPU derivative fits; useful only if a later implementation change alters formulas or edge behavior.
| Horizon / LOS height reference | `src/scenes/terrain/horizon.compute.ts` converts observer height above sampled terrain into eye elevation. `src/scenes/terrain/viewshed.compute.ts` similarly supplies ground-relative observer and target heights. The point-horizon, line-of-sight, and viewshed APIs support `ground` and `absolute` observer references, while target height remains above local ground. Absolute observer heights can carry a vertical datum contract. | Keep the existing ground-relative controls. Do not add an “absolute” toggle to the Swiss DEM stories: the DEM sources do not declare one shared vertical datum, and the peak catalogue has a separate datum caveat. If a future story has a matched datum, add a clearly labeled absolute observer elevation control there; retain ground-relative target height and pass the datum explicitly. | Feasible when the source and test observer share a declared vertical datum: a flat DEM gives exact ground/absolute ray-height comparisons. For this mixed-datum showcase, an oracle would only verify the ground-relative path already used, not justify absolute values.
| Extrema-pyramid footprint | `src/scenes/terrain/horizon.compute.ts` and `src/scenes/terrain/viewshed.compute.ts` explicitly build the pyramid with `footprint: 'bilinear'`. `gpu-raster-extrema-pyramid.ts` defines `cell` as exact pixel-block support and `bilinear` as that block plus one extra row/column, which bounds bilinear ray samples. | No selector. The footprint is a correctness precondition of the bilinear ray traversal, not an analyst preference. Keep `firstBlockSize` as the performance/precision tradeoff and retain the explicit bilinear declaration. | Straightforward CPU oracle: enumerate valid source samples touched by each bilinear query and assert each enclosing pyramid cell’s min/max bounds it. Existing dimensions are enough; no new data is needed.
| Convolution normalization | `src/scenes/raster/spectral-texture.compute.ts` already normalizes positive smoothing kernels and Gaussian/box blur. The selected `GPURasterConvolution` filters are signed zero-sum derivatives (Sobel/east/south), passed with `normalize: false`. `gpu-raster-neighborhood.ts` confirms normalization divides by participating coefficient sum and rejects zero-sum normalized kernels; missing-data renormalization also requires nonnegative coefficients. | Do not expose `normalize` on the derivative selector: it is invalid for the current zero-sum kernels and would obscure their signed derivative meaning. Positive normalized smoothing is already available through neighboring operations. A generic positive-kernel mode would duplicate those paths without improving the story. | Feasible by hand-calculating a constant and impulse raster. Constant input should remain constant under normalized smoothing and yield zero signed derivative under the current filters; no code change is indicated.
| Rank filter missing-data / border behavior | `src/scenes/raster/missing-observations.scene.ts` exposes median preparation, `preparationNoData` (`ignore`/`propagate`), and `preparationBorderMode` (`clamp`/`nodata`). `src/scenes/raster/missing-observations.compute.ts` forwards both settings to the preparation recipe. `src/scenes/raster/missing-surface-preparation.ts` forwards the recipe, whose filter contract supports rank quantile, radius, `clamp`/`nodata` border, and `propagate`/`ignore` missing-data policy. | Implemented the bounded border control on the existing median-preparation step. Clamp repeats edge samples; nodata treats out-of-grid samples as missing. Ignore omits missing neighbors; propagate invalidates an output when any source or out-of-grid neighbor is missing. The readout names both active settings. | The independent 64×64 CPU oracle now covers both borders, policies, radii, fill distances, and scenarios (48 cases). It checks support, changed counts, selected values, and holdout error only for withheld observed July pixels; September real gaps have no error score.

The grid-support diagnostic says “five option cases” but “four distinct support decisions”: the 13 July nearest strict/renormalize pair reports the same support discrepancy, while the 13 July bilinear-renormalize case and both 21 September nearest cases match. Aggregate counts still do not identify the GPU cell that differs.
