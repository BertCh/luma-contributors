# Upstream workarounds register

Status date: 2026-11-10. Baseline: published `@luma.gl/*@10.0.0-alpha.10`.

This repository imports luma.gl only through published entry points (see [upstream-first-plan.md](./upstream-first-plan.md)). Where the published release is missing a capability or a fix that the pre-split branch had, we either dropped the capability, wrote a small local workaround, or accepted a regression. This file lists every one of them, so that each `@luma.gl` bump can retire the ones the release fixes.

Since the math correctness review of 2026-11-10 ([luma-official.md](./research/math-correctness-review-2026-11-10/luma-official.md)) it also lists, in section 4, every local kernel that computes what a published class computes, with the reason it cannot delegate today. The matching luma.gl pull requests are drafted in [upstream-proposal-math-review.md](./upstream-proposal-math-review.md). Section 6 lists the shader-compiler behaviour found in the same pass, which is not luma.gl's but which its kernels meet too. Sections 4 and 6 were brought up to date after the independent review of the fixes (all eighteen Resolution sections and their "Review follow-up" subsections read).

Paths are relative to the repository root; paths that start with a source directory (`analysis-core/`, `gpu-network/`, ...) are under `modules/analysis/src`. All were checked on the date above. The source tree is still changing, so re-grep before deleting anything.

## How to read the table

| Status | Meaning |
| --- | --- |
| dropped | The capability no longer exists here. Callers get an error or a smaller limit. |
| workaround | Local code stands in for a missing luma.gl API. Delete it when the API ships. |
| accepted regression | We use the published primitive as is and live with a performance or scale loss. No local code. |
| local kernel | Local code computes what a published class computes, because the class lacks an option the contributor needs (section 4). The convention is kept equal to the published one where the row says so. Delegate and delete when the option ships. |

The "what luma.gl needs" column says what would let us restore or delete. These are suggestions for luma.gl pull requests. This repository never waits on them (rule 3 of the plan).

## 5. Upgrade procedure for each `@luma.gl` alpha bump

1. Read the luma.gl release notes and diff the public `.d.ts` files. Compare `node_modules/@luma.gl/graph/dist/**/index.d.ts` before and after, not individual files, since only index exports are public.
2. For each row above, check whether the release provides the "what luma.gl needs" item. Search for the symbol in the new `index.d.ts` files, for example `GPUJacobiPCG`, `GPUSegmentedReduction`, `getSpatialOperationNodes`, `makeGeometryGPUVectors`.
3. Delete the local workaround, switch callers to the public API, and move the row to a "Retired" list at the bottom of this file with the release version. For a section 4 row, write a parity spec on at least one non-trivial input before delegating.
4. Run `node scripts/check-upstream-first.mjs`. It must report no violations. It rejects every `@luma.gl/*` specifier with an `_internal` segment, whatever the package `exports` map lists.
5. Bump all `@luma.gl/*` versions together in the root `package.json`, `modules/*/package.json` peer ranges and `yarn.lock`.
6. Run the pin specs on the new release: `yarn vitest run --project node modules/analysis/test/analysis-core/official-wgsl-copies.node.spec.ts` and the five per-copy pin specs it names. A failure means the published kernel text changed under a private copy: read the new published function, decide whether the copy follows it (it must when the kernel reads state the published class built), and update the copy and this file together.
7. Run `yarn typecheck`, `yarn typecheck-tests`, `yarn build`, `yarn lint`, `node scripts/verify-package-exports.mjs`, then `yarn test-node` and `yarn test-headless`.
8. Investigate numerical drift in oracle and parity tests. Accept it with a note in the test, or fix it in the analysis code. Do not loosen tolerances silently.
9. Re-run the benchmarks that guard section 3 (`LUMA_CONTRIBUTORS_BENCHMARKS=true`) and record the numbers next to the row.
10. Add any new workaround or dropped capability to this file in the same change.

## 6. Shader-compiler behaviour that kernels work around

These are not luma.gl regressions and no luma.gl release retires them. They were measured in this repository on one adapter (headless Chromium WebGPU on an Apple GPU, Metal). The cause inside the compiler was not found for any of them: the generated Metal source was not inspected, so each may be a defect of the browser's shader translation or of the driver, to be reported there. The closing pass (2026-11-11) inspected it and found the causes ([shader-compiler-findings.md](./research/math-correctness-review-2026-11-10/shader-compiler-findings.md), pinned on plain WebGPU by `modules/analysis/test/analysis-core/shader-compiler-fast-math.spec.ts` and `shader-compiler-table-fill.spec.ts`): the first, second and fourth rows are Metal fast math, which Chromium 151 gives no switch for, and the third is a miscompile in the Apple GPU back end of Metal source that Tint generates correctly, with fast math on or off. A bug report for the third is drafted there and not filed. The library audit of 2026-11-11 (the last section of that report, and the specs in `modules/analysis/test/analysis-core/table-audit/`) ran the kernels that hold an integer table filled by constant-count loops and found none that loses it today. They are listed because every WGSL author here and in luma.gl meets them, and because the local cures look like needless code to a reader who does not know why they exist. The rules are in [contributor-contract.md](./contributor-contract.md), section 11; the report to luma.gl is drafted in [upstream-proposal-math-review.md](./upstream-proposal-math-review.md), section 13. Re-run the specs after every browser, operating-system or luma.gl upgrade: a cure may become unnecessary, and a shape that passes today may fail.
