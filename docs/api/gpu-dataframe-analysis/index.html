GPU Dataframe analysis contributors

Overview

The @luma-contributors/analysis/dataframe-analysis entry point exports analysis contributors for GPU-resident columns: column profiles, quantiles and class breaks, color scales, group statistics, key joins, composite scores, inequality measures, calendar buckets, period indices, cube layout transposes, relative times, time-window filters, temporal reductions, and pair-statistics tools (variograms, correlograms, Ripley's K, point-pattern indices). Each is an algorithm or workflow that declares resources and command nodes into a caller-owned GPUCommandGraph through getCommandNodes(graph) (GPUCommandNodeProducer). A contributor never compiles, submits, encodes, or reads back.

Execution and ownership of wide numeric operations

The entry point also exports one-shot functions. These create a separate graph on every call and await a summary on the CPU; use the contributor when the result must compose into an existing graph.

API Execution and transfer cost Ownership
GPUWideNumericScan Declares nodes in the caller's graph over resident word vectors; no implicit upload, submission or readback. Caller owns input vectors, initialized output words, compilation, encoding, submission and optional readback.
runWideNumericKernel Allocates and initializes a result buffer, compiles a new graph, encodes, submits, and awaits readback of max(16, resultWordCount * 4) bytes; returns resultWordCount words. Borrows resident inputs; destroys its compiled graph and result buffer in finally.
aggregateInteger64OnGpu, aggregateInteger64Range Resident-vector one-shot aggregation through runWideNumericKernel; reads 44 bytes and returns a CPU summary. Borrows input vectors and validity; releases its graph and result buffer.
scanWideNumericColumnOnGpu Resident-vector one-shot narrowing diagnostics; reads 24 bytes and returns a CPU report. Borrows input vectors and validity; releases its graph and result buffer.
aggregateDecimal128OnGpu Resident-vector one-shot decimal aggregation; reads 76 bytes and returns a CPU summary. Borrows word vectors and validity; releases its graph and result buffer.
makeDecimal128WordVectors Uploads an Arrow Decimal128 column's words and, when needed, validity. Does not submit a scan or read back. Caller must invoke the returned destroy() to release the uploaded vectors.
aggregateDecimal128Column Uploads an Arrow Decimal128 column, performs the one-shot decimal aggregation, and awaits its summary readback. Releases the uploaded vectors in finally as well as the scan's graph and result buffer.

A graph-resident count of present nonzero values can feed another node without a CPU wait:

import {Buffer, type Device} from '@luma.gl/core';
import {GPUCommandGraph} from '@luma.gl/graph/gpu-core';
import type {GPUVector} from '@luma.gl/graph/gpu-data';
import {GPUWideNumericScan} from '@luma-contributors/analysis/dataframe-analysis';

declare const device: Device;
declare const words: GPUVector<'uint32x2'>;
const resultBuffer = device.createBuffer({
  data: new Uint32Array(4),
  usage: Buffer.STORAGE | Buffer.COPY_SRC | Buffer.COPY_DST
});
const graph = new GPUCommandGraph(device);
const output = graph.createDataView(
  graph.importBuffer({id: 'present-count', byteLength: 16, usage: resultBuffer.usage}, resultBuffer),
  {format: 'uint32', length: 4}
);
graph.add(new GPUWideNumericScan({
  id: 'present-count', words, resultWordCount: 1, output,
  phaseBodies: ['if (present && any(pair != vec2u(0u))) { atomicAdd(&result[0], 1u); }']
}));
// Add downstream nodes reading output before compiling.
const compiled = graph.compile();
const encoder = device.createCommandEncoder();
compiled.encode(encoder, {parameters: undefined});
device.submit(encoder.finish());
// Before reusing this graph, reset resultBuffer to zero, then encode and submit again.
// Once all consumers have finished: compiled.destroy(); resultBuffer.destroy();

For an explicit CPU summary, use the one-shot path and await its readback:

import type {Device} from '@luma.gl/core';
import type {GPUVector} from '@luma.gl/graph/gpu-data';
import {aggregateInteger64OnGpu} from '@luma-contributors/analysis/dataframe-analysis';

declare const device: Device;
declare const words: GPUVector<'uint32x2'>;
const summary = await aggregateInteger64OnGpu({device, words, signed: true});
// summary.sum is a bigint on the CPU. The caller still owns words.

When to use it

Use these contributors for the fixed analyses that map and dashboard applications repeat every frame, where inputs are packed graph views and results must stay on the GPU. Use the GPUDataFrame query API when the question is a general expression, filter, or aggregation plan.

  • GPUGroupStatistics groups by a 32- or 64-bit key and computes many statistics per group (moments, median, percentiles, mode, unique count). Use GPUDataFrameGroupedAggregationQuery for dense categorical keys and standard aggregations.
  • GPUKeyJoin joins a left table to a right table by key and supports 1:n aggregates and 64-bit keys. Use GPUDataFrameJoinQuery for a unique right-side key lookup between dataframes.
  • GPUColumnProfile fuses count, nulls, moments, histogram, distinct estimate, and top categories into one statistics panel. Use GPUDataFrameHistogramQuery when you only need an explicit histogram.
  • GPUTimeWindowFilter publishes compacted source rows, optional caller IDs, masks, and fade weights for a window that moves every frame, including exact Int64 time words. Express a fixed time predicate as a dataframe filter expression instead.

Quick start

Use the complete GPU walkthrough for device creation, buffer imports, submission, typed readback and cleanup. A time-window filter uses a compact output object rather than a single output view:

Import Float32Array.of(0, 10, 20) as a three-row float32 timestamps view. Times and window bounds share an epoch and units. Allocate the output views below, then add the filter with this checked function.

import type {Device} from '@luma.gl/core';
import {GPUCommandGraph, type GraphDataView} from '@luma.gl/graph';
import {GPUParameterBuffer} from '@luma-contributors/analysis/analysis-core';
import {
  GPUTimeWindowFilter, getGPUTimeWindowFilterParameterValues,
  GPU_TIME_WINDOW_FILTER_PARAMETER_LENGTH
} from '@luma-contributors/analysis/dataframe-analysis';

export function addTimeWindowExample(
  device: Device, graph: GPUCommandGraph, timestamps: GraphDataView<'float32'>,
  rows: GraphDataView<'uint32'>, count: GraphDataView<'uint32'>,
  overflow: GraphDataView<'uint32'>, requiredCount: GraphDataView<'uint32'>
) {
  const window = new GPUParameterBuffer(device, {
    id: 'time-window-example-parameters',
    format: 'float32',
    length: GPU_TIME_WINDOW_FILTER_PARAMETER_LENGTH,
    values: getGPUTimeWindowFilterParameterValues({start: 5, end: 15})
  });
  graph.add(new GPUTimeWindowFilter({
    timestamps, window: window.importToGraph(graph),
    output: {rows, status: {count, overflow, requiredCount}}
  }));
  return window;
}

Keep the returned window buffer until the compiled graph has been destroyed.

Output port Format and rows Expected readback
rows uint32, capacity 3 First count[0] source-row indices only: [1]
status.count uint32, 1 [1], clamped to capacity
status.requiredCount uint32, 1 [1], accepted count before capacity truncation
status.overflow uint32, 1 [0]; 1 means accepted rows were dropped

The inclusive window accepts only timestamp 10. Spare row slots have no result meaning; use the count rather than reading the entire capacity as accepted rows. Submit and read the buffers with the walkthrough's lifecycle, reading overflow alongside IDs. When overflow is nonzero, resize and rerun or propagate incompleteness. Rewrite the window buffer with the packer to move the window without recompiling. Destroy the compiled graph before the window and other caller-owned buffers.

Conventions

  • Graph views in, graph views out. Inputs and outputs are GraphDataView, GraphVectorView, or GraphTextureView objects created on the target graph. Outputs are always caller-owned; scratch storage is graph transients that die with compiled.destroy(). Contributors never compile, encode, submit, or read back.
  • Per-frame values never recompile. Viewports, thresholds, radii, observer positions, budgets, and region shapes are read from storage views, usually a GPUParameterBuffer that the application rewrites with write(). Lengths, capacities, grid sizes, and which optional views exist are compile-time topology; each prop's TSDoc says which category it belongs to.
  • Bounded results report overflow on the GPU. Compact ID lists use GPUCompactOutput (ids and a status with count, overflow and optional requiredCount). status.count is clamped to ids.length and can be an indirect draw instance count; status.overflow is rewritten every encoding.
  • Rows and IDs. GPUTimeWindowFilter.output.rows always contains zero-based source rows; optional output.ids contains caller identities from sourceIds. Node and transient IDs are ${id}-<step>, so two instances in one graph need different id props.
  • One import per buffer. Import a buffer once (for example with graph.importGPUData() or GPUParameterBuffer.importToGraph()) and pass the returned view to every contributor that reads it, so the graph tracks hazards on one logical handle.
  • Shared contracts. Four shapes mean the same on every analysis page:
    • Status. Every GPU-written status word sits in the status member of the bag that owns it: output.status.overflow, output.status.converged, and output.status.code for model fits.
    • Grid. Raster and terrain contributors take grid: GPURasterMetadata, and their packers read the cell size from it (see GPU Terrain conventions).
    • Network. Network contributors take topology: GPUNetworkTopology (offsets, neighbors, weights, optional nodePositions). Its CSR part can be passed as GPUSpatialWeights (see GPU Network conventions).
    • Polygons. Polygons use the four-level GPUPolygonGeometryPort: kind: 'polygons', positions, featureOffsets, polygonOffsets and ringOffsets. Contributors with a single geometry take the same fields flat, without kind (GPUPolygonGeometryFields). See Shared ports.

GPUTimeWindowFilter

Filter timestamped rows against an inclusive time window, producing a row mask and compact accepted source-row indices in output.rows. Use rows as gather indices. Optional sourceIds and output.ids must be supplied together: the latter maps each retained row to its opaque caller identity. Both destinations have the same capacity and must use separate buffers. For times [0, 10], source IDs [1, 0], and window [0, 0], the result is rows = [0], ids = [1]; gathering attributes [10, 20] by rows returns [10].

Optional output.status.candidateOverflow is rewritten to zero: this exact filter has no candidate stage. It is a writable output and must be disjoint from the compact rows and IDs, all other outputs and every input, including application sourceIds.

The time filter, key join and temporal reduction capture declared input, output and nested status bindings once at construction, including inherited getters. Later edits to those JavaScript maps do not redirect writes. Buffer contents remain per-frame values.

Filters timestamped rows (instants) or time intervals (trail segments) against a per-frame window and publishes stable compacted rows, optional caller IDs, a clamped count, and optional mask, fade weights, segment clip fractions, per-track visible counts, and an indirect instanceCount. All outputs live in one output prop (GPUTimeWindowFilterOutput: compact rows and status, optional mapped ids, plus outputMask, fadeWeights, clipFractions, trackVisibleCounts, drawInstanceCount); trackIds is an input. The per-frame settings object is GPUTimeWindowFilterSettings (GPUTimeWindowFilterWordSettings for Int64 words), packed by getGPUTimeWindowFilterParameterValues or getGPUTimeWindowFilterWordParameterValues. Timestamps come in three forms, chosen by the view format:

  • float32 relative to an application epoch, the cheapest path;
  • float32 plus timestampsLow (double-single, from splitTimestamps) for inputs that arrive as float64;
  • exact Int64 words: a uint32x2 view holding each value's little-endian (low, high) words, for example Arrow Int64 or Timestamp epoch milliseconds uploaded without a CPU pass (getInt64TimeWords). The window is then a uint32 parameter buffer written with getGPUTimeWindowFilterWordParameterValues, whose start and end are a number (with a sub-unit fraction for a smooth playhead) or a bigint. Kernels order times lexicographically on the words and subtract with a borrow before converting to float32, so acceptance is exact for every Int64 value, including an INT64_MIN/INT64_MAX "unbounded" window over pre-1970 rows, with no epoch to choose; fade and clip differences have the right sign for any two values and are exact below 2^24 units.
  • The window is inclusive. A reversed window (end < start) accepts nothing, interval rows that span it included, and NaN timestamps are never accepted (edge-policy table TIME_WINDOW_EDGE_POLICY in the tests).

Sorted range mode

When the instants are sorted by time (the usual layout of a recorded track or event log), set sorted: true. The accepted rows are then one contiguous range, found by two binary searches in a single one-thread kernel: O(log n) per frame for any row count, with no mask pass, scan or compaction. The range is written to output.rowRange ([firstRow, rowCount], rowCount unclamped), output.drawFirstInstance (the draw record's firstInstance, so the instance index is the row index) and the usual status words and output.drawInstanceCount; output.rows receives only its first min(count, rows.length) source-row indices from a kernel that returns early past the count. An optional gather maps these rows through sourceIds into output.ids. A caller that reads only the range passes a small rows view. Acceptance uses the same comparison helpers as the mask path (double-single timestampsLow and Int64 words included), so the rows are exactly those the mask path accepts.

  • Precondition: timestamps (with timestampsLow) is non-decreasing in row order and has no NaN. The default path does not scan for this. Set validateOrder: true with output.orderViolations (one uint32) to count adjacent descents on every encoding; it is an O(n) pass, as expensive as the mask path, so use it while developing or after an upload, not per frame.
  • Instants only: endTimestamps, additionalPredicates, trackIds, output.trackVisibleCounts and output.clipFractions are refused, and views must be single packed (unchunked).
  • output.outputMask and output.fadeWeights are still allowed and still cost O(n), so leave them out when scrubbing very large data.
  • A reversed window (end < start) gives an empty range.
graph.add(new GPUTimeWindowFilter({
  sorted: true,
  timestamps: sortedInstants,
  window: window.importToGraph(graph),
  output: {...compactOutput, rowRange, drawInstanceCount}
}));
graph.add(new GPUTimeWindowFilter({
  timestamps: segmentStarts, endTimestamps: segmentEnds,
  window: window.importToGraph(graph),
  // `output` is a `GPUTimeWindowFilterOutput`: the compact list plus the optional views.

  }
}));
window.write(getGPUTimeWindowFilterParameterValues({start: now - trailLength, end: now, startFadeDuration: trailLength}));

GPUColumnQuantiles, GPUClassBreaks, GPUColorScale, and GPUBivariateClassification

Choropleth classification on the GPU, every frame, with no readback: exact quantiles and percentile filters, class breaks, and colour scales that write a packed rgba8 column a deck.gl layer can bind as an attribute. Each output can feed the next contributor as a graph view, so a brush or filter change recolours the map without a CPU round trip.

graph.add(new GPUColumnQuantiles({
  values, mask, quantileCount: 3,
  parameters: quantileParameters.importToGraph(graph),
  output: {quantiles, validCount, outputMask, filterBounds} // outputMask may be a transient
}));
graph.add(new GPUClassBreaks({
  values, mask: outputMask, maximumClassCount: 9,
  methods: ['quantile', 'natural-breaks', 'head-tail'], // default: every method
  parameters: breakParameters.importToGraph(graph),
  output: {breaks, classCount, classCounts}
}));
graph.add(new GPUColorScale({
  values, mask: outputMask, domain: breaks, domainCount: classCount, palette,
  parameters: scaleParameters.importToGraph(graph),
  maximumDomainCount: 10, maximumPaletteCount: 9,
  output: {colors, classIndices, classCounts}
}));
quantileParameters.write(getGPUColumnQuantilesParameterValues({quantiles: [0.25, 0.5, 0.75], filterRange: [0.05, 0.95]}));
breakParameters.write(getGPUClassBreaksParameterValues({method: 'natural-breaks', classCount: 7}, 9));
scaleParameters.write(getGPUColorScaleParameterValues({scale: 'threshold', domainCount: 8, paletteCount: 9}));
// Any of these writes takes effect on the next encoding, with no recompile.
  • Class rule shared by all four contributors: breaks are edges e[0..k] (e[0] the smallest and e[k] the largest finite value). A value is in class i when i inner edges e[1..k-1] are at or below it (d3 scaleThreshold/bisectRight), compared on order-preserving u32 keys, so -0 sorts below +0. Values outside [e[0], e[k]] clamp to the end classes. NaN and masked rows are skipped (class 0xffffffff, the no-data colour). Colours are r | g << 8 | b << 16 | a << 24.
  • GPUColumnQuantiles: exact order statistics by four 8-bit radix-select passes over the ordered keys (no sort): up to 64 per-frame probabilities, 'lower' | 'higher' | 'nearest' | 'linear' | 'midpoint' (numpy names; 'linear' is d3 and R-7). The rank is fround(fround(n - 1) * p) and every interpolation step is rounded separately (no fused multiply-add), so results match a sorted CPU column bit for bit. filterRange gives deck.gl/kepler lower/upper percentile filtering: bounds x[floor(n * lower)] and x[ceil(n * upper) - 1], and a outputMask of the rows inside them. At most 2^24 rows. About 1.8 ms at 1M rows and 3.5 ms at 4M rows for 9 quantiles plus the filter (Apple M-series, headless Chromium).
    • Which rank is exact. The default rank fround(fround(n - 1) * p) is a float32 product and is not exact: its fraction is lost from rank 2^23 (16,777,216 rows at p = 0.95: linear returns x[lo], numpy interpolates by 0.25), and the float32 p can put floor(h) one rank from numpy's at any size (101 rows at p = 0.59). The optional rationalProbabilities view (getGPUColumnQuantilesRationalProbabilityValues([[19, 20], [1, 2]]), uint32 pairs numerator, denominator) replaces the float32 probabilities: the rank floor((n - 1) numerator / denominator) and its remainder come from a 64-bit integer product and division, exact for every row count, and the linear fraction is the correctly rounded float32 of remainder / denominator. It agrees with numpy.quantile 2.5.4 for linear everywhere tested, and for the other methods except where numpy's own float64 product (n - 1) * q lands just below or just above an integer the exact product equals: just below, lower and midpoint are one rank off (101 rows, q = 0.29: numpy lower returns x[28], the exact rank is 29); just above, higher and midpoint are (101 rows, q = 0.55: numpy higher returns x[56], the exact rank is 55). With it the column may exceed 2^24 rows (up to one storage binding, 2^25 rows at the default limit) when no filter output is requested; the filter ranks stay float32. GPUClassBreaks and GPUGroupStatistics use the float32 rank only. Fixture and generator: modules/analysis/test/oracles/dataframe-quantile-rational-rank.py.
  • One order-statistic policy for GPUColumnQuantiles, the GPUClassBreaks quantile and box-plot methods, and the GPUGroupStatistics medians and percentiles: the sample is the finite unmasked values (NaN and ±Infinity are missing), -0 equals +0, and a probability that is NaN or outside [0, 1], or an empty sample, gives NaN. The result is numpy.quantile(x[numpy.isfinite(x)], p); numpy itself keeps infinities and raises on an invalid p. When x[high] - x[low] overflows f32 the convex form x[low] (1 - t) + x[high] t keeps the result finite.
  • GPUClassBreaks: per-frame method and classCount among the compiled methods: 'equal-interval', 'quantile' (exact linear quantiles at i / k), 'standard-deviation' (classes of interval sample standard deviations centred on the mean, as mapclassify StdMean and R classInt 'sd'), 'head-tail' (Jiang's breaks with a per-frame head ratio, default 0.4; 1 gives mapclassify's rule), 'box-plot' (six classes, per-frame hinge), 'maximum-breaks' (midpoints of the k - 1 largest gaps between distinct sorted values), 'natural-breaks' (Fisher-Jenks, see below), and 'custom'. Head/tail and maximum breaks may return fewer classes; classCount reports k (0 with no finite values, 1 when they are all equal). Infinities are missing for every edge, so e[0] and e[k] bound the inner edges. Kernels of unselected methods return at once, except the two radix sorts of 'maximum-breaks', which run every frame when compiled. Natural-breaks layers and refinement rounds and head/tail rounds read their index from a GPU state word and are dispatched indirectly, so the pipeline count does not grow with maximumClassCount and finished rounds launch no workgroups. Moments use a fixed-order Chan merge, so every output is bitwise reproducible. About 3 to 4 ms per frame at 1M rows with six methods compiled. Every closed-form method is checked against mapclassify 2.11 and natural breaks against the exact Fisher-Jenks partition (an f64 dynamic program, agreeing with jenkspy 0.4.1) by the committed generator test/oracles/dataframe-class-breaks.py.
    • naturalBreaksMode: 'exact' explicitly selects a full Fisher–Jenks dynamic program for 'natural-breaks'; the default 'approximate' retains the histogram/refinement path below. Exact mode accepts at most 8192 source rows (including masked/missing rows), with the existing capacity of 64 classes. Construction rejects larger columns; it never falls back to an approximate method. naturalBreaksExactStorage defaults to 'auto': up to 1024 rows it materializes interval costs; larger inputs recompute the same backward Welford recurrence during each DP layer. Explicit 'materialized' retains the 1024-row cap; 'recompute' can also be selected for small inputs to minimize storage. A radix sort places selected finite values first. Equal numeric values (including signed zeros) cannot be split; the produced count is min(requested, distinct finite values). Each inner edge is the first value of the upper class, included in that class. This matches GeoDa's < break assignment contract, pinned to GeoDa 37510860, CatClassification.cpp. GeoDa's randomized natural-break search itself is not the exact reference; the independent reference is jenkspy 0.4.1. The objective is total within-class squared deviation. Exact means the global optimum of the documented GPU arithmetic recurrence: divide values by the largest power of two at or below max(abs(min), abs(max)) (the magnitude itself for subnormal scales, one for zero), subtract each interval's scaled last value, then compute each interval's centered sum of squares by backward Welford updates in f32, then enumerate every eligible split using f32 score addition. Division decomposes both operands with frexp, divides bounded mantissas, then applies their exponent difference with ldexp; no extreme reciprocal is formed. Arithmetic ties retain the lowest last split, recursively within the prefix. This is not an f64 or real-arithmetic guarantee: normalization can underflow tiny values and close objectives can round together; device multiply-add contraction can also affect close partitions. Work is O(k n²) and scratch is O(n² + k n) when materialized, or O(k n) when recomputed (two score rows and the partition backpointers). Recomputation eliminates the quadratic allocation but repeats the Welford arithmetic; it does not promise lower latency. The 8192-row cap is a bounded-work contract, not a measured interactive-performance guarantee. Scratch bindings are checked against the actual device limit. There is no CPU solve, submission or readback. NaNs/masked rows are omitted; infinities are omitted from the objective and counted in the end classes, as in the approximate mode.
    • naturalBreaksMode: 'monotone' selects a separate approximate full-data dynamic program, for up to 262144 source rows and 64 classes. It sorts the finite selected values and uses full distinct source-value boundaries with monotone pruning, avoiding the histogram mode's restricted initial boundaries and subsequent single-cut local search. It is useful when a full-column partition search is wanted and exhaustive f32 recurrence optimization is too expensive. Normalized positions are quantized onto [0, 1048575] (20 bits); exact 64-bit integer prefix moments avoid raw floating-point prefix cancellation. Interval costs and DP score additions are still f32, and divide-and-conquer pruning assumes mathematical monotonicity. Neither real-arithmetic optimality nor parity with exact mode is guaranteed. Widely separated outliers can collapse small distinctions under quantization; this is not a universal accuracy improvement over the histogram/refinement mode. Edges remain actual source values, equal numeric values (including signed zero) are indivisible, and arithmetic ties prefer the lowest split. Each breadth-first search level distributes endpoints and candidate scans across workgroups; pipelines are reused and inactive levels dispatch no work. Normal search work is O(k n log n) with O(k n) storage. If rounding leaves a feasible endpoint without a valid candidate in its pruned interval, that endpoint falls back to exhaustive search to preserve a valid partition, so worst-case work remains O(k n²). This fallback does not certify optimality. Device binding limits are checked before scratch allocation. No GPU-to-CPU readback or CPU solve is performed.
    • With the default approximate mode, 'natural-breaks' seeks the partition into k classes of least total within-class squared deviation. A coarse dynamic program over naturalBreaksBinCount equal-width bins of [min, max] (2 to 2048, default 2048) sums count, position and squared position of each bin as exact 64-bit integers, so the class cost is evaluated without the cancellation of S2 - S1^2 / n in f32 and without a bin-by-bin cost table. A layer of the dynamic program is one workgroup that exploits the monotone split points of the cost (the quadrangle inequality) over log2(bins) barrier-separated levels: O(k B log B) work in all, against O(k B^2) before. The bins cannot see structure finer than range / bins, so the breaks are then refined on the rows, and no longer snap to bin edges: red-black coordinate descent in which each break, with its two neighbours fixed, takes the best split of the values in its two adjacent classes (odd breaks and then even breaks, so a pass never moves two interacting breaks and the cost only falls). The first window of a break covers the data extent of its two classes, so a heavy outlier cannot hide the structure, and the window then shrinks around the chosen cell boundary until a cell is below an f32 ulp. If empty classes show that the bins collapsed the most populated class (one extreme outlier puts the whole bulk into one bin), the coarse stage runs again over the range of that class with the classes the empty ones would have held. Rounds end once no cut moved with every break zoomed twice, at most eight; a column usually settles in two rounds, that is five passes over the rows (one for the class extents, two per round). Every inner edge e[i] is an actual data value, the smallest value of class i; mapclassify and jenkspy report the largest value of each class (b[i-1]), so e[i] is the smallest data value above b[i-1] and the classes are the same. A class count above the number of distinct values (which mapclassify and jenkspy refuse) yields one class per distinct value, like 'maximum-breaks'; the produced count is classCount.
    • Accuracy: on the 34 reference cases (10 columns from lognormal and cluster mixtures to heavy ties, an extreme outlier of 1e6 times the spread, an outlier pair and a Pareto tail, k from 2 to 10) 32 equal the exact partition, bit for bit in the edges. The other two stop in a neighbouring local optimum of the coordinate descent (a goodness of variance fit within 2e-6 of the optimum; one of them is the partition mapclassify 2.11 itself returns, which is not optimal). On random well-scaled columns about 1 in 300 does. On 180 random heavy-tailed columns (Pareto tails, outliers, clusters beside an outlier) 179 were exact and the other was within a fit of 4e-8. Structure narrower than a bin that is not the most populated class (for example several clusters in one bin beside an outlier, when a lighter class also collapses) keeps the coarse allocation and is refined locally only. The previous implementation snapped breaks to bin edges (an error up to range / 1024) and cost O(k B^2) for the cost table and the layers.
  • GPUColorScale: linear, sqrt, pow, log (kepler's logFloor for v <= 0), symlog, quantize, threshold/quantile (binary search over the active edges), and ordinal (a uint32 code column). Scale, domain, palette, clamp, and 'step'/'linear' interpolation are per frame. A multi-stop domain with as many stops as palette entries is piecewise linear, like a d3 multi-stop scale.   • Exactness: counts, the fixed-point sums words, minimum, maximum, median, percentiles, mode and unique counts are bit-identical to a CPU reference. sumValues is the exact sum rounded once to float32 and means is that divided by the count (a few float32 units in the last place), at any magnitude: values 1.0e-4, 1.2e-4, 1.4e-4 have mean 1.2e-4. A value keeps all its bits in the sum while its magnitude is at least max * 2^(h - 71), where max is the largest value of the column in a kept group and h the bit length of the row count. Percentiles use the numpy linear rule (h = (n - 1) p, lo + (hi - lo) * (h - floor h) in f32) and the order-statistic policy shared with GPUColumnQuantiles, with p read per frame; a fraction that is NaN or outside [0, 1] gives NaN (it is no longer clamped).   • Moments are corrected two-pass: d = v - mean is summed in a fixed order (a binary tree over sorted row blocks), so a second encode is bitwise identical. The signed first and third powers are scaled by a power of two chosen from each group's extremes before reduction and restored afterwards, preventing same-sign branches from overflowing before opposite signs cancel. Values with binary exponent at most 30 use no scaling. Even powers retain their float32 range limits. Each level merges only the group crossing each block midpoint; the work is O(rows), the depth is O(log rows), and a dominant group spreads across workgroups. The four power sums use separate scalar scratch bindings (16 bytes per input row in total); each binding must fit the device storage limit. The row count is also bounded by the published sort maximum of 2^31. estimatedCommandNodeCount includes the merge levels and conservative allowances for published sorts, scans and gathers, checked against the shared command-node budget. Central moments about the true mean come from the shifted power sums. Oracle specs require relative tolerances of 1e-6 for means, 2e-5 for variance, and 1e-4 for skewness, kurtosis and z-scores, with small absolute tolerances near zero. Skewness is Fisher-Pearson g1, kurtosis is excess g2; both are NaN for constant groups, a group whose variance is under 2^-19 of its shifted sum of squares is treated as constant (the shift mean is rounded to float32). Sample variance of one value is NaN; the z-score is (v - mean) / sd with the same corrected mean the variance uses, and is 0 when the deviation is 0 or a sample group has one value, NaN for masked, invalid-key, non-finite or capacity-dropped rows.
  • Dense mode: keyCount (compile-time) requires uint32 keys in [0, keyCount). output.keys.length and every per-group output hold exactly keyCount rows, and row k is key k (output.keys[k] = k, output.status.count and status.requiredCount are keyCount, status.overflow is 0). Keys with no rows keep a row: counts 0, sums and uniqueCounts 0, and NaN for mean, minimum, maximum, variance, standard deviation, skewness, kurtosis, median, percentiles and mode. Keys outside the range and the reserved all-ones key are skipped like masked rows and are not reported as overflow. It costs one binary search per key instead of a group scan, and suits region IDs or other small dense key spaces (the choropleth recipe uses it so empty polygons keep a row). The default compact table of occupied keys is unchanged.
  • Cost: one stable key sort (two 32-bit radix sorts for 64-bit keys); each column that asks for median, percentiles, mode or unique count adds a value sort plus a key re-sort. Chunked reducible inputs use fixed tile scratch; exact order statistics still require device-bound packed scratch. Approximate distinct counts (HyperLogLog) are not included.

  • aggregates run over all matching right rows: count, count-distinct, sum, mean, minimum, maximum. sum is the exact sum of the finite values in a 96-bit fixed-point accumulator whose unit follows the largest value among the valid right rows, rounded once to float32; mean divides it by the finite count. GPUVariogram, GPUSpatialCorrelogram, GPURipley, GPURipleyDistanceFunctions, and GPUPointPatternIndices

Every contributor here accepts at most getGPUPairStatisticsMaximumRowCount(device) (11,184,810 on a default device, never above 2^24 - 1) positions rows: the cell-sorted points table holds 12 bytes per row and must fit one 128 MiB storage binding.

Pair statistics over planar points share one deterministic pair-histogram pass: rows are sorted into a per-frame lattice whose cells are at least the per-frame maximumDistance wide, one thread per included row visits the 3x3 cell neighbourhood, and each pair adds integer amounts into per-workgroup shared-memory 64-bit accumulators that are then added into global 64-bit accumulators. Float terms are fixed point (a bounded term such as a distance maps its maximum to 2^24; the variogram and correlogram unit comes from the typical term, see below, never from the maximum), so every result is exact or has a documented fixed-point bound, independent of scheduling, and bitwise reproducible. A 64-bit sum that would wrap raises an overflow word (readPairOverflow) instead of wrapping silently, and pair counts saturate at 0xffffffff. When maximumDistance covers the extent the pass is a plain all-pairs loop. A row is included when its mask is nonzero, its value (if any) finite and its position finite and inside the per-frame bounds. Parameters ([minX, minY, maxX, maxY, maximumDistance, ...]) are per-frame, packed from a GPU<Class>Settings object (GPUVariogramSettings, GPUSpatialCorrelogramSettings, GPURipleySettings, GPURipleyDistanceFunctionsSettings, GPUPointPatternIndicesSettings) by getGPU<Class>ParameterValues(settings); bin counts and the set of outputs are compile-time. Every caller-owned output view goes in one output prop (GPUVariogramOutput, GPUSpatialCorrelogramOutput, GPURipleyOutput, GPURipleyEnvelopeOutput, GPURipleyDistanceFunctionsOutput, GPUPointPatternIndicesOutput), including the overflow status word.

All five classes (and GPURipleyEnvelope) take an optional spatialContext and are planar only: distances and window areas are Euclidean in the units of positions. Omitting it means native planar coordinates; a longitude-latitude context throws at construction ("project positions to a planar frame first"), because degrees give latitude-dependent distances, wrong areas and biased indices. The resolved context is exposed as spatialContext. By default the window is the bounds rectangle. GPURipley, GPUVariogram and GPUSpatialCorrelogram also accept a compile-time studyWindow prepared by GPUStudyWindowPreparation from @luma-contributors/analysis/gpu-spatial-analysis. Add the preparation to the same graph before the consumer and use bounds: 'study-window' (GPUPairStatisticsBounds) in the per-frame settings. The GPU copies the parameters and replaces the bounds with the prepared polygon's bbox; the original buffer is unchanged. The window and points must share a planar spatial context. Windows may contain holes and disjoint components, but must be valid, without self-intersections or overlapping polygons; consider GPUGeometryValidity before preparation. studyWindow exposes the resolved handle or 'rectangle'. Passing bounds: 'study-window' to a rectangle-mode operator produces NaN statistics; unusable polygon windows exclude every row. For an irregular study area, using its bbox as the observation window instead of the polygon overstates the area and can make a pattern look clustered. GPUVariogram and GPUSpatialCorrelogram measure distance and reject local-lambert-equal-area frames. Ripley statistics (including distance functions and envelopes) and point-pattern indices combine distance and window area, so neither local frame is exact: use an azimuthal-equidistant frame only where its area distortion is negligible, or use a projected CRS.

  • GPUVariogram: polygon windows filter rows only; no area or edge correction is applied. Matheron semivariance, pair count, mean lag distance and Cressie-Hawkins robust semivariance per lag and optional azimuth sector (directionCount equal sectors over [0, pi) from a per-frame azimuthOffset; a pair of coincident points has no direction and is counted in sector 0). The robust estimator is (mean |z_i - z_j|^(1/2))^4 / (2 (0.457 + 0.494 / N + 0.045 / N^2)), the Cressie and Hawkins (1980) correction that scikit-gstat evaluates; the 0.045 / N^2 term lowers a one-pair bin by 4.7 % against the two-term form. Matheron precision: a term (z_i - z_j)^2 / 2 is scaled by 2^24 / u and rounded to an integer, where u is the robust variance (IQR / 1.349)^2 of the included values (exact quartiles), clamped to at most the population variance, so the absolute error of a bin mean is at most u * 2^-25 (never more than variance * 2^-25, itself below the former (max - min)^2 * 2^-26) plus f32 rounding of the term. The former unit 2^24 / (0.5 * (max - min)^2) rounded every typical term to 0 once one outlier or sentinel stretched the range (-83% at an isolated outlier of 2e4 standard deviations on 4000 points, -100% at 1e5) with no status. Terms above 256 u (a difference beyond 22 standard deviations) are added exactly in a second 64-bit channel at 2^12 units, with relative error at most 2^-21; the worst-case relative error of gamma per bin is max(u * 2^-25 / gamma, 5e-7 + 2^-24). Capacity is 2^40 u for the first channel and 2^52 u for the second. The optional overflow output is 1 when a sum, a clamped term (2^51 u) or a pair count (saturated at 0xffffffff; previously the count wrapped modulo 2^32 and became the N_h weight of the fit) left its range. The Cressie-Hawkins channel scales with sqrt(max - min). The pass uses 4 channels per bin (5 with robustSemivariances), so lagCount * directionCount is at most 512 (409 with the robust channel). Model fitting is CPU post-processing: fitVariogramModel runs on the CPU over the read-back bins, fits spherical, exponential or Gaussian models (practical-range convention) with Cressie, pair-count or uniform weights, and should be skipped when output.status.overflow is 1. The Matheron and Cressie-Hawkins bins, pair counts and mean distances are checked against scikit-gstat 1.0.24 (including an embedded 2e4 sentinel) by the committed generator test/oracles/dataframe-variogram.py, with tolerances derived from the bounds above.

Variances lost to f32 cancellation (for example a band holding every pair) are NaN. Pair products use the same typical-term unit as the variogram, 2^24 / u with u the robust variance (the former 2^24 / max|c|^2 rounded every product to 0, so I was 0, once one outlier or sentinel dominated), so |I| errs by at most 2^-25 * u / variance plus 2^-21 of the contribution of products above 256 u, which are summed exactly in a second channel. The isotropic rectangle formula is exact at every radius (checked against brute-force circle sampling), so there is no radius guard; the practical limits are variance and the weight cap, which biases K low once less than 1% of a circle is inside, so keep maximumDistance well below the shorter window side (spatstat's default rmax is a quarter of it).   • GPURipleyDistanceFunctions: the distance functions next to GPURipley (spatstat Gest, Fest, Jest). Outputs (output.g, output.f, output.j, output.radii; at least one of g, f, j) hold NaN where a value is undefined. 'hanisch' is spatstat han for G and Chiu-Stoyan style weights for F, with 14-bit fixed-point weights (relative error about 1e-4); a point with no neighbor within maximumDistance but a border distance of at least maximumDistance enters the denominator at d = maximumDistance. That is too little weight when the point is uncensored (G too high) and too much when it is censored (G too low: two such points beside one close pair give 0.44 where the Hanisch estimator is 1). The estimate is exact when every point has a neighbor in range, so set maximumDistance to at least the largest nearest-neighbor distance when it matters. GPUInequality

Parallel and reference routes support at most 2,147,483,648 rows, subject to sort and device limits. mode: 'reference' preserves the serial oracle.

Parallel reductions are the default; mode reference retains the serial per-zone oracle. Lorenz knots and output bindings retain their existing limits.

Computes weighted Gini and other inequality indices per zone from a value column, with Lorenz knots and a pooled summary.

::lens{scenario=gpu-dataframe.inequality rung=result caption="Within community areas the income Gini runs from 0.01 (area 37, two tracts) to 0.31 (area 28); pooled it is 0.33 (CPU check)."}

GPUInequality computes per-zone income inequality indices from a column of non-negative values: Gini, Theil T and L, Atkinson, Hoover, Palma, Lorenz curve knots, plus the between/within-zone decomposition of Theil T and pooled statistics.

Inputs: values (float32), zoneIds (uint32; 0xffffffff or any id >= zoneCount skips the row), zoneCount (at most getGPUInequalityMaximumZoneCount(device), 3,050,402 on a default device) and lorenzKnotCount (compile-time; zoneCount * lorenzKnotCount at most getGPUInequalityMaximumLorenzKnotTotal(device), 2^25 on a default device), optional population weights (float32) and mask (uint32), and a parameters view written with getGPUInequalityParameterValues({epsilon, palmaTopShare, palmaBottomShare}). Changing the parameters never rebuilds or recompiles the graph. A row is included when its mask is non-zero, its zone is valid, its value is finite and non-negative and, with weights, its weight is finite and positive. With w the weight (1 without weights), W = sum w, S = sum w x and mu = S / W:

Output Definition
gini 1 - sum (P_i - P_(i-1)) (L_i + L_(i-1)), trapezoid area under the Lorenz curve of the value-sorted rows; equals 2 sum i x_(i) / (n S) - (n + 1) / n for unit weights, (n - 1) / n for one holder of everything
theilT (1 / W) sum w r ln r, r = x / mu, 0 ln 0 = 0
theilL -(1 / W) sum w ln r; NaN when the zone contains a zero (zeros are never silently dropped)
atkinson 1 - ((1 / W) sum w r^(1 - e))^(1 / (1 - e)), 1 - exp(mean ln r) at e = 1; zeros are fine for e < 1, NaN for e >= 1; e in [0, 32] per frame
hoover sum w abs(x - mu) / (2 S)
palma (1 - L(1 - top)) / L(bottom), cuts per frame (0.1 and 0.4 by default); NaN when L(bottom) = 0
mean, counts weighted mean, included row count per zone (counts is uint32)
lorenzKnots L(k / (K - 1)), row-major zone * K + k, L(0) = 0, L(1) = 1
globalSummary slots GPU_INEQUALITY_GLOBAL_SUMMARY: TOTAL_THEIL_T, BETWEEN_THEIL_T, WITHIN_THEIL_T, GINI, COUNT, MEAN, TOTAL_WEIGHT, TOTAL_INCOME

The Lorenz curve is linear inside each row (a row's income spreads over its population share), so a Palma cut or knot inside a row takes a fractional share of that row. Empty zones, and zones with zero total income, report NaN for every index (zero-income zones keep mean = 0). The Theil decomposition is between = sum_g s_g ln(s_g / p_g) and within = sum_g s_g T_g with income share s_g and population share p_g; the pooled Theil T is computed independently from all included rows, so total = between + within is a real check.

Algorithm and cost: rows are sorted by value, re-keyed by zone and stably sorted, so each zone is a value-ordered segment. The default parallel route builds bounded 256-row Lorenz prefixes, computes row-parallel terms and reduces them by segment. mode: 'reference' preserves the two serial per-zone walks and their rounding order; a dominant zone serializes that route. The parallel summation order can change the last float32 bits; sums and published statistics remain float32. Pooled and global reductions use fixed-order tiles.

GPUPeriodIndex

Turn calendar columns or Int64 word times into a uint32 period per row: whole calendar steps from an origin, or a fixed width.

The period index is the adapter between GPUCalendarBuckets (or raw Int64 words) and a (cell, period) cube. It is the code that addSpaceTimeHotSpotsRecipe runs between its calendar decode and its cube, extracted so that other space-time pipelines share it and the recipe's slices are exactly these periods. It reads the temporal context of the times, never converts units, and writes one uint32 per row with no readback.

// Calendar axis: 52 weeks from Monday 2024-01-01, from the calendar columns of the same times.
graph.add(
  new GPUCalendarBuckets({temporalContext, timestamps, parameters, output: {year, month, dayOfMonth}})
);
graph.add(
  new GPUPeriodIndex({
    temporalContext, // 'int64-words' counted from the Unix epoch
    columns: {year, month, dayOfMonth},
    periods: {
      kind: 'calendar',
      step: {calendarUnit: 'week'},
      origin: {year: 2024, month: 1, day: 1},
      count: 52
    },
    output: {periods, status: {invalidCount}}
  })
);

// Fixed axis: 24 one-hour bins of nanosecond words from 2024-01-01T00:00:00Z.
graph.add(
  new GPUPeriodIndex({
    temporalContext: nanosecondContext,
    timestamps,
    periods: {kind: 'fixed', width: 3_600_000_000_000n, origin: 1_704_067_200_000_000_000n, count: 24},
    output: {periods}
  })
);
  • temporalContext: resolved with {encodings: ['int64-words'], unixEpoch: true}, so Arrow uploads pass their own context. An unsupported encoding or an epoch other than the Unix epoch throws at construction. The unit is the unit of a fixed width and origin; a calendar axis only reads the decoded columns, whose unit GPUCalendarBuckets already handled.
  • Calendar axis: step is {calendarUnit, interval?} with calendarUnit one of 'year', 'quarter', 'month', 'week', 'day' or 'hour' and a positive integer interval (default 1). Period floor((stepIndex(time) - stepIndex(origin)) / stepsPerPeriod) holds a time, where stepIndex counts whole steps (year, year * 4 + quarter - 1, year * 12 + month - 1, days since 1970 for 'day' and 'week', hours since 1970 for 'hour') and a week is 7 days anchored to the origin day. origin is {year, month?, day?, hour?} in the local calendar of columns, with the unset fields at the start of the step. columns.year is always read; columns.month for every step but 'year'; columns.dayOfMonth for 'week', 'day' and 'hour'; columns.hour for 'hour'. Days are numbered with Hinnant's days_from_civil in i32 arithmetic, so leap days, quarter starts and years before 1970 are exact. The CPU twins getGPUPeriodIndexCalendarPeriod, getGPUPeriodIndexStepIndex and getGPUPeriodIndexDaysFromCivil return the same numbers.
  • Fixed axis: period floor((time - origin) / width) with width a positive integer below 2^63 (a number must be a safe integer; pass a bigint beyond 2^53) and origin signed Int64 ticks after the Unix epoch. The difference and the division run on the Int64 words, so they are exact for every time, including times before 1970 and beyond 2^53 ticks, and for widths past 32 bits.
  • Output periods holds one uint32 per row: the period, GPU_PERIOD_INDEX_OUT_OF_RANGE (0xfffffffe) for a valid time before the origin or past the last period, or GPU_PERIOD_INDEX_INVALID (0xffffffff) for a masked row or a time the calendar decode rejected. Rows are skipped, never clamped.
  • Status: output.status.invalidCount (optional) is the number of skipped rows, those with GPU_PERIOD_INDEX_OUT_OF_RANGE. Masked and undecodable rows are not counted. It is cleared on every encoding and counted with an integer atomicAdd.
  • Limits: periods.count is an integer in [1, GPU_PERIOD_INDEX_MAXIMUM_COUNT] (4294967293, the two sentinels are not periods). Each bound range must fit device.limits.maxStorageBufferBindingSize per chunk, including any prefix required for an aligned binding offset. At a 128 MiB binding limit with no prefix, a uint32 output or calendar column holds up to 33,554,432 rows per chunk, and Int64 timestamps hold up to 16,777,216 rows per chunk. Larger totals are supported by chunking, up to 4,294,967,295 total rows and subject to the command-node budget.
  • Row inputs and output.periods accept packed views or chunked GraphVectorViews with matching ordered chunk lengths across every active column, the optional mask and the output. Each chunk is packed; mixing mismatched row partitions is rejected. Status views remain packed. An optional mask (uint32, zero writes the invalid sentinel) must have one row per input row.

For example, the fixed-axis chunk fixture uses three rows partitioned as [1, 2]. Given caller-owned GPU vectors timestampVector, maskVector and periodVector with those same ordered chunk lengths:

graph.add(
  new GPUPeriodIndex({
    id: 'periods',
    temporalContext, // millisecond, Unix epoch, int64-words
    periods: {kind: 'fixed', origin: 0n, width: 1000, count: 12},
    timestamps: graph.importGPUVector('chunked-times', timestampVector),
    mask: graph.importGPUVector('chunked-mask', maskVector),
    output: {
      periods: graph.importGPUVector('chunked-periods', periodVector),
      status: {invalidCount} // one packed uint32 word
    }
  })
);

This declares periods-clear-invalid-count, periods-periods-chunk-0 and periods-periods-chunk-1. A combined timestamp length above one binding's row limit is accepted when each bound chunk range fits the device limit.

Calendar hour multiplication, step differences and division use exact 64-bit words, so indices at 2^31 - 1, 2^31 and above remain usable up to periods.count - 1. Calendar origins must have a whole-step index in [-2^31, 2^31 - 1]; steps per period (interval, times seven for weeks) must be in [1, 2^31 - 1]. These construction-time origin and divisor limits do not cap row indices or the unsigned period count. Row dates follow the supported GPUCalendarBuckets decoder range.

GPUCubeLayoutTranspose

Move a dense (cell, period) cube between the cell-major and period-major layouts.

The space-time hot spot cube is cell-major (cell * periodCount + period); Markov chains, spatial panels and per-period maps are period-major (period * cellCount + cell). The transpose converts one into the other on the GPU for uint32 counts or float32 values.

graph.add(
  new GPUCubeLayoutTranspose({
    values: cube, // GraphDataView<'uint32'> or <'float32'>, cellCount * periodCount values
    from: 'cell-major', // the layout of `values`; the output holds the other one
    cellCount,
    periodCount,
    output: periodMajorCube // same format and length
  })
);
  • Every value is copied bit for bit (counts, NaN payloads and signed zeros alike), and transposing back returns the original cube.
  • Limits: cellCount * periodCount is an integer at most 4294967295 and the cube must fit one storage binding, 33,554,432 values on a default device. Larger cubes are refused at declaration with the binding limit in the message.
  • The transpose is a scatter with one thread per element. cellCount and periodCount are overrides of the shader, so cubes of different shapes share one compiled module.

  • Per frame (no recompile): the contents of values and output.
  • Compile-time (needs a new graph): from, cellCount, periodCount and the value format.

GPUTimeWordsRelative

Convert Int64 word times to float32 ticks after an origin on the GPU.

Several contributors read relative float32 times (GPUKnoxTest, GPUMantelTest, GPUSpaceTimeVariogram, float-mode GPUTemporalReduction) while uploads keep exact Int64 words. This node connects them without a CPU pass.

const relative = new GPUTimeWordsRelative({
  timestamps, // GraphDataView<'uint32x2'>, Int64 words
  temporalContext, // 'int64-words', any unit and epoch
  origin: 1_700_000_000_000n, // ticks after the Unix epoch, in the context unit
  output: relativeTimes // GraphDataView<'float32'>, one row per timestamp
});
graph.add(relative);
relative.outputTemporalContext; // {...temporalContext, encoding: 'float32-relative', epoch: 1_700_000_000_000n}
  • The difference to the origin is taken on the words with the exact timeWordsDifferenceToF32 kernel and only then rounded, so it is exact below 2^24 ticks and has a relative error below 2^-23 beyond, with the right sign for every pair of Int64 values.
  • origin is an instant (signed Int64 ticks after the Unix epoch). When the input context counts from another epoch, the node subtracts that epoch first, so the result is always ticks after origin.
  • outputTemporalContext is {...temporalContext, encoding: 'float32-relative', epoch: origin}: the unit, time zone and axis are the input's. Nothing is converted between units.
  • Limit: the uint32x2 timestamps must fit one storage binding, 16,777,216 rows on a default device; larger inputs are refused at declaration.

GPUValueCube

Dense (cell, period) cube of count, sum and mean of a value column.

GPUTemporalReduction and the hot spot recipe bin counts, minima, maxima, first and last values but no sum or mean. GPUValueCube adds them in the cell-major layout cell * periodCount + period that GPUEmergingHotSpots reads, so GPUTimeWindowFilter (the mask), GPUPeriodIndex (the periods) and the cube chain to Gi*, trend, Markov chains and panels with no readback.

graph.add(
  new GPUValueCube({
    cellCount,
    periodCount,
    cells, // GraphDataView<'uint32'>, cell index per row
    periods: periodIndexOutput, // GraphDataView<'uint32'> from GPUPeriodIndex
    values, // GraphDataView<'float32'>
    mask: filterOutputMask, // optional, for example outputMask of GPUTimeWindowFilter
    output: {
      counts, // GraphDataView<'uint32'>, cellCount * periodCount rows
      sums, // GraphDataView<'float32'>
      means, // GraphDataView<'float32'>, NaN where a bin is empty
      status: {invalidCount} // optional
    }
  })
);
  • Sums are deterministic and independent of thread order. Each value is quantized to the shared 96-bit fixed-point accumulator (analysis-core/kernels/fixed-point-accumulator.ts) and added with integer atomics; the exact integer is rounded once to float32. There are no float atomics. A float32 running sum that cancels 1e8 + 1 - 1e8 loses the 1; the cube returns it exactly.
  • The unit is a power of two set by the largest magnitude among the rows that are binned and by the bit length of the row count. A value keeps all 24 significand bits while it is at least max * 2^(h - 71) (h the bit length of the row count; about 1e15 of dynamic range at a million rows); smaller values round to the nearest unit, so a sum of n terms is off by at most n / 2 units before the final rounding. Because the unit follows the binned rows, the rounding of a bin can change when another set of rows is binned, for example another time window.
  • means is the rounded sum divided by the count in float32. WGSL division is not correctly rounded (up to 2.5 ULP), so a mean is within a few units in the last place of the true mean; an empty bin is NaN, which GPUEmergingHotSpots treats as missing.
  • Not binned: masked rows (silent), rows whose period is 0xffffffff (GPU_PERIOD_INDEX_INVALID, excluded upstream, silent), and rows with a cell or period out of range (including GPU_PERIOD_INDEX_OUT_OF_RANGE) or a non-finite value. The last group is counted in status.invalidCount.
  • Limits: cellCount, periodCount, cellCount * periodCount and the row count at most 4294967294; the fixed-point words need 12 bytes per bin in one storage binding, so cellCount * periodCount is at most getGPUValueCubeMaximumBinCount(device), 11,184,810 on a default device. Larger cubes are refused at declaration with the binding limit in the message. Inputs and outputs are single packed views.

GPUValueCube parameters

  • Per frame (no recompile): the contents of cells, periods, values and mask.
  • Compile-time (needs a new graph): the row count, cellCount, periodCount, and which outputs and mask are present.
  • Packer: none.

GPUCellPeriodKeys

Packs a 64-bit H3, S2 or Quadbin cell key and a period into one group key for GPUGroupStatistics.

A dense cube needs a cell index below cellCount; a DGGS has billions of possible cells. GPUGroupStatistics already groups by uint32x2 keys and computes count, sum, mean, minimum, maximum, variance and percentiles in a capacity-bounded table sorted by key, so a sparse DGGS by period cube is one packing kernel away.

graph.add(
  new GPUCellPeriodKeys({
    cells: cellKeys, // GraphDataView<'uint32x2'>, little-endian (low, high) words
    periods: periodIndexOutput, // GraphDataView<'uint32'> from GPUPeriodIndex
    periodCount: 365,
    fill: 'ones', // 'ones' for H3 and Quadbin, 'zeros' for S2
    mask, // optional
    output: {keys: packedKeys, status: {invalidCount}}
  })
);
graph.add(
  new GPUGroupStatistics({
    keys: packedKeys,
    columns: [{values, statistics: ['count', 'sum', 'mean'], output: {counts, sumValues, means}}],
    output: {keys: groupKeys, counts: groupCounts, status: {count, overflow}}
  })
);

Which route builds a DGGS (cell, period) cube without readback? Two compose from the existing pieces: (a) this packing kernel and GPUGroupStatistics on the composite key, or (b) GPUCellAggregation once to get the distinct cells, GPUKeyJoin to map every row to its cell row, then row * periodCount + period as a key into GPUValueCube or GPUGroupStatistics in dense mode. Use (a) for DGGS cubes: it needs one sort and no cell-row lookup, its memory follows the number of occupied (cell, period) groups instead of cellCount * periodCount, and cells never need a table. Use (b), or GPUValueCube with a cell index you already have (a lattice, or a weights table), only when the consumer needs the dense cell-major cube, as GPUEmergingHotSpots and the layout transpose do.

  • Packing: with b = ceil(log2(periodCount)) period bits, the key is (cellKey & ~(2^b - 1)) | period. The period replaces the low b bits of the cell key, so the packed key sorts by cell and then period. A packed key is not a valid cell id: unpack the group table keys with unpackGPUCellPeriodKey(key, periodCount, fill).
  • What happens to the key bits: the cell key stays 64 bits, nothing is truncated to 32. The b replaced bits must hold the fill pattern. At the resolution of the cells they do: unused H3 digits are 7 (3 * (15 - resolution) low bits, all ones), the Quadbin footer is all ones (52 - 2 * zoom bits), an S2 id has a lone sentinel one above 60 - 2 * level zero bits. Within that many free bits the packing is lossless and injective. A cell with any other bits where the period goes (a finer cell) is not packed: its key becomes the reserved all-ones key, which GPUGroupStatistics skips, and it is counted in status.invalidCount; cells are never merged silently. A finer cell whose extra bits happen to equal the fill pattern is packed and unpacks to itself. getGPUCellKeyFreeBits('h3' | 'quadbin' | 's2', resolution) gives the free bits. 365 daily periods need 9 bits: H3 resolution 12 or coarser, Quadbin zoom 21 or coarser, S2 level 25 or coarser. Hourly periods over a year (8,760) need 14 bits: H3 resolution 10, Quadbin zoom 19, S2 level 23.
  • Rows are skipped silently when masked, when the cell is the all-ones "no cell" key, or when the period is 0xffffffff. A period at or above periodCount is skipped and counted.
  • Limits: periodCount at most 4294967293 (32 period bits); cells fit one storage binding, 16,777,216 rows on a default device. Downstream, GPUGroupStatistics keeps at most getGPUGroupStatisticsMaximumGroupCount (8,388,608 on a default device) distinct (cell, period) groups and keeps the smallest keys on overflow, and its sums words are fixed point with a resolution of 1 / sumScale (65536 by default); its sumValues and means use a unit that follows the data, as GPUValueCube does.

  • Per frame (no recompile): the contents of cells, periods and mask.
  • Compile-time (needs a new graph): the row count, periodCount, fill, and whether mask and status.invalidCount are present.
  • Packer: none.
