Cells (DGGS)

Cell system support

Shared cell operators support S2 topology, compaction, grid paths, center covering and outlines. The separate S2 compatibility API retains its own status words and unit-sphere units (steradians and radians, little-endian keys only). Aggregation/rollup still support H3 and Quadbin.

Use GPUCellAggregationFamily ('quadbin' | 'h3') for aggregation, rollup and pyramid inputs, and GPUCellTopologyFamily ('quadbin' | 'h3' | 's2') for topology, compaction, grid paths, covering and outlines. Both types are exported from @luma-contributors/analysis/gpu-spatial-analysis. GPUCellIndexFamily additionally includes 'quadkey' and 'geohash' for indexing. These capability types replace the two different types formerly named GPUCellFamily.

Quadbin 0–26 0–26, center, full or intersects At most 15 levels per input cell Sorted distinct keys
S2 0–30 0–15, center only At most 15 levels per input cell Sorted distinct keys, all at one level

GPUCellAggregation, GPUCellRollup, GPUCellPyramid, and GPUCellLevelSelection

GPUCellAggregation: Aligned chunked inputs use fixed tile sorting scratch controlled by scratchTileSize. Aggregate padded tile rows are at most 4,294,967,295; packed global aggregate outputs remain device-binding bounded.

GPUCellAggregation — Counts and sums rows per Quadbin or H3 cell into a sorted, capacity-bounded cell table.

::lens{scenario=gpu-spatial-analysis.cell-aggregation rung=result caption="Blue: Quadbin zoom-18 cells shaded by place count · grey: 1,275 Wicker Park places"}

GPUCellRollup — Reduces a cell table to a coarser resolution by summing child counts and sums, without re-reading the rows.

::lens{scenario=gpu-spatial-analysis.cell-rollup rung=result caption="Grey: 115 zoom-18 cells · blue: 12 zoom-16 parents shaded by summed place count"}

GPUCellPyramid — Aggregates rows once at the finest resolution, then rolls each level into the next coarser table.

::lens{scenario=gpu-spatial-analysis.cell-pyramid rung=result caption="Grey: zoom-18 level · blue: zoom-16 level of the same pyramid, shaded by place count"}

GPUCellLevelSelection — Publishes the cell count and first row of a pyramid level chosen by one per-frame index.

::lens{scenario=gpu-spatial-analysis.cell-level-selection rung=result caption="Blue: the selected zoom-17 level, shaded by place count · grey: places"}

Aggregates rows into discrete global grid cells (Quadbin or H3) and builds a zoom pyramid of cell tables. 64-bit cell keys are stored as two uint32 words in little-endian (low, high) order, which is the layout of Arrow Uint64 columns and of GPUH3CellProjection input. An H3 table therefore feeds the projection directly.

  • Inputs. positions (lng/lat degrees, Quadbin only) are keyed in WGSL. cells are pre-keyed rows, for example CARTO Quadbin or H3 columns, as uint32x2 (wordOrder: 'high-low' is also accepted). Pre-keyed rows finer than resolution are truncated to it. Invalid rows, and rows coarser than resolution, are skipped. H3 validity comes from gpu-dggs dggs_h3_is_valid_cell_id. Optional values and a mask can change every frame. Rows with a NaN coordinate or a non-finite value are skipped.
  • Coordinate space. spatialContext is checked at construction and exposed as a resolved field. positions are longitude/latitude degrees (default {coordinateSpace: 'longitude-latitude', metric: 'none'}); a planar context throws, because Quadbin keying is defined on degrees. Pre-keyed cells, GPUCellRollup and GPUCellPyramid use a discrete-grid context (default gridFamily is family): a given gridFamily must equal family, and a given gridResolution (the finest resolution of the input keys) must be at least resolution. Nothing is measured, so only metric 'none' is accepted.
  • Cell table (GPUCellTable). Capacity is cells.length. Rows [0, status.count) hold occupied cells in ascending key order. Later rows hold the empty key 0xffffffff in both words, count 0 and NaN extremes. Columns: counts, fixed-point sums (signed 64-bit words of roundHalfEven(fround(value * sumScale)), default scale 65536), sumValues (f32 sums / sumScale), minimums and maximums. On overflow the table keeps the smallest keys and sets status.overflow. That flag describes only this destination. Optional status.candidateOverflow reports source-table loss and is cleared to zero by raw aggregation. Rollup destinations and every coarser pyramid level must provide that scalar; a missing scalar is rejected at construction. Forward the whole status when reusing a table as input. Final overflow and candidateOverflow publish in separate dispatches, so their one-word views may occupy adjacent words (for example byte offsets 0 and 4) in one buffer. All output logical byte ranges must remain disjoint. Fields bound together, such as count, overflow and requiredCount, also need disjoint storage binding ranges after device-offset alignment. Rollup accumulation also binds counts and sums writable together: their aligned ranges must be disjoint, including at every coarser pyramid level. For one count at byte 0 and one sum at byte 8, the logical ranges are disjoint but a 256-byte device alignment makes the sum binding start at 0, overlapping the count binding; construction rejects that layout. Raw aggregation writes these columns in separate dispatches and accepts that layout. Aggregation, rollup, pyramid and comparison constructors capture declared props, table ports and status ports once, including inherited or getter-backed fields; unrelated metadata is ignored. Replacing caller fields afterwards does not change the declared graph. Buffer contents remain per-frame inputs.
  • Accuracy of sums. The integer sum is exact, order independent and equal under roll-up; the values are not: each row is rounded to the nearest multiple of 1 / sumScale before it is added. With the default 65536 that is an absolute error of up to 2^-17 (7.6e-6) per row, a value below it adds 0, and a column of constant 1e-4 sums 6.8% high (7 / 65536 per row). The default suits values of about 0.01 and above. For small or very large values pass sumScale: getGPUCellSumScale(maximumMagnitude, maximumRowCount) (exported beside GPU_CELL_DEFAULT_SUM_SCALE): the largest normal float32 power of two, clamped to [2^-126, 2^127], that keeps maximumRowCount rows of that magnitude at most 2^61 when that bound is representable. Positive finite magnitudes, including Number.MIN_VALUE, are accepted; tiny magnitudes select 2^127. When that upper cap does not constrain the scale, float32 rows within a factor of 32 of the maximum are added without rounding at the default row count of 2^31. When it does, even the maximum can be quantized: the normal float32 value 1.25 * 2^-126 scales to 2.5, rounds to even at 2, and decodes as 2^-126 (20% low). Use one sumScale for every table that is rolled up or compared together (GPUCellAggregation, GPUCellRollup, GPUCellPyramid, GPUCellTableCompare).
  • Roll-up. GPUCellRollup reduces a table to a coarser resolution without re-reading rows or sorting. Parent keys truncate the cell path (cellToParent), which preserves key order. Counts and sums are integer sums, so a roll-up equals direct aggregation bit for bit. The source table's overflow and inherited candidateOverflow are combined into the parent's candidateOverflow; its own overflow is set only when parent rows exceed its capacity. requiredCount counts parents formed from retained source cells, so it is a lower bound on the full parent requirement after source loss. Growing only the parent destination cannot recover cells already dropped by a finer stage.
  • Pyramid. GPUCellPyramid aggregates once at the finest of resolutions (listed finest first), rolls each level into the next, writes one table per level to output.levels and can write per-level counts to output.levelCounts. Intermediate sums and extremes that a coarser level needs become transients. Each level keeps final and inherited loss separate, and inherited loss propagates through all remaining coarser levels. Read both loss flags for every displayed level. Either flag means that level is incomplete; its levelCounts entry still reports the number of retained rows.
  • Level selection. GPUCellLevelSelection reads a per-frame activeLevel (one uint32) and writes that level's status.count, first row, and the instanceCount/firstInstance words of indirect draw arguments. Keep it in a small per-frame graph: switching levels rewrites one word and never re-runs the pyramid.
// Allocate every table with status: {count, overflow, candidateOverflow}.
// Read both loss flags after execution; either makes that level incomplete.
graph.add(new GPUCellPyramid({
  family: 'quadbin',
  positions, values, mask,                    // mask and values can change every frame
  resolutions: [18, 14, 10, 6, 2],
  output: {levels: tables, levelCounts}
}));
selectionGraph.add(new GPUCellLevelSelection({
  levelCounts, activeLevel: activeLevel.importToGraph(selectionGraph),
  output: {status: {count}, drawArguments}
}));
activeLevel.write(Uint32Array.of(levelForZoom(zoom)));   // no recompile
  • Determinism. Point keys use only integer arithmetic. The longitude column is exact. The latitude row is a fixed-point Mercator (ln(cos t) - ln(sin t), Q0.32 polynomials, exact long division), so every adapter and the CPU reference agree bit for bit. f32 polynomials would not agree, because WebGPU compilers may fuse a * b + c (Metal does). Sorting uses one stable GPUSort when the key path fits 31 bits (Quadbin ≤ 15, H3 ≤ 8) and two otherwise. Rows accumulate with u32 atomics only: counts, 64-bit sums as two words with a carry, and extremes as order-preserving keys.
  • Accuracy. Compared with the f64 quadbin-py formula, the fixed-point row differs for 0% of random points up to resolution 8, 0.01% at 12, 0.1% at 16, 1.1% at 20, 17% at 24 and 55% at 26. It is never off by more than 1 row up to resolution 22, 2 rows at 24 and 5 rows at 26 (f32 latitudes are not that precise). The column always matches.
  • Aligned chunked inputs use fixed tile scratch; packed aggregate outputs remain device-bound. Forward keying of points is Quadbin only.

GPUPointToCell and GPUCellGeometry

GPUPointToCell — Keys longitude/latitude points to 64-bit cell keys of a discrete global grid family at one resolution.

::lens{scenario=gpu-spatial-analysis.point-to-cell rung=result caption="Grey: every 4th Wicker Park place · blue: the H3 resolution-9 cell each falls in"}

GPUCellGeometry — Decodes cell keys to centres and boundary polygons in longitude/latitude degrees.

::lens{scenario=gpu-spatial-analysis.cell-geometry rung=result caption="Blue: H3 resolution-9 cell boundaries · grey: the places they were keyed from"}

Keys points to discrete global grid cells and turns cells back into centres and boundary polygons. This covers the most common Studio/CARTO preprocessing step ("lng/lat column to H3") and the geometry needed to draw any DGGS cell column. Keys are 64-bit uint32x2 little-endian (low, high) words, which is the Arrow Uint64 layout that GPUCellAggregation pre-keyed rows and GPUH3CellProjection read. The zero key means "no cell".

  • Families (GPUCellIndexFamily) and their resolutions:

    Family Resolutions Notes
    'quadbin' 0-26 integer keys, exact
    'h3' 0-15 f32 input: exact to res 4
    'quadkey' 1-29 packed: length in bits 58-63, base-4 digits
    'geohash' 1-12 packed: length in bits 60-63, base-32 characters, i.e. the lng/lat bit interleave
    's2' levels 0-30 standard S2CellId

    The quadkey and geohash packings are the layouts the shadertools dggs decoders read.

  • GPUPointToCell.

    • Input is positions (lng/lat float32x2) and an optional mask. Output is cells and an optional validity, one row per input row.
    • Masked and non-finite rows get the zero key. The resolution is compile-time.
    • Rewriting positions or the mask re-encodes without recompiling.
    • spatialContext (optional) must be longitude/latitude without a metric, which is also the default; planar contexts throw. GPUCellGeometry takes cell ids, so it has no spatialContext prop; its decoded centers and boundaries are described by outputSpatialContext.

  • GPUCellGeometry.

    • Input is cells (wordOrder option).
    • Outputs are centers (lng/lat) and optional boundaries with a fixed maximumVertexCount stride and vertexCounts. Families are the five above plus 'a5'.
    • An invalid key (the zero key included) gets a NaN centre, vertex count 0 and zero boundary rows. The optional validity output (uint32, 1 for a valid cell, 0 otherwise) follows luma.gl GPUDGGSCellProjection, which decodes H3 and A5 centres with the same shader functions but writes a zero centre for an invalid cell.
    • H3 boundaries follow h3-js cellToBoundary exactly in vertex count and order. That includes face-crossing distortion vertices (up to 10, so use stride 10) and pentagons.
    • Quadbin, quadkey, geohash and S2 have 4 vertices; A5 has 5.
    • edgeModel and outputSpatialContext.edgeModel are 'great-circle' for H3, S2 and A5, and 'linear' for quadbin, quadkey and geohash. Before linear polygon consumers, prepare great-circle boundaries with GPULonLatPolygonPreparation; see the H3 edge-deviation table below.
graph.add(new GPUPointToCell({family: 'h3', resolution: 8, positions, output: {cells}}));
graph.add(new GPUCellGeometry({
  family: 'h3', cells, maximumVertexCount: GPU_CELL_GEOMETRY_H3_MAXIMUM_VERTEX_COUNT,
  output: {centers, boundaries, vertexCounts}
}));
  • Exactness and accuracy.

    • Quadbin, quadkey and geohash keying is integer-only and equals the BigInt oracles bit for bit on every device.

    • S2 and H3 use f32 sphere math (polynomial sine/cosine, no trig builtins for H3) and are exact at coarse resolutions. A mismatch is an edge neighbour of the f64 answer:

      Family Uniform-point mismatch rate vs the f64 reference (f32 inputs) Usable limit
      H3 vs h3-js 0 at res 0-4, 1e-4-4e-4 at 5-8, 1e-3 at 9, 2e-3 at 10, 1.8% at 12, 28% at 15 res ≤ 12
      S2 0 at levels 0-10, 1e-4-3e-3 at 11-15, 1.8% at 18, 13% at 21 level ≤ 20

    • Geometry matches h3-js / oracles within about 3e-5 degrees.

GPUCellTopology and GPUCellCompaction

GPUCellCompaction: Supports H3, Quadbin and S2. S2 levels are 0–30; compaction expansion depth is at most 15. S2 covering uses level-15 center containment, rather than exact polygon intersection.

GPUCellTopology — Expands each cell key to its grid disk, ring, parent or children as a fixed-stride row.

::lens{scenario=gpu-spatial-analysis.cell-topology rung=result caption="Blue: the radius-4 disk around the central place, shaded by grid steps from its cell"}

GPUCellCompaction — Merges complete sibling sets of cells into parents (compact) or expands cells to descendants (uncompact).

::lens{scenario=gpu-spatial-analysis.cell-compaction rung=result caption="Grey: 49 resolution-9 cells, two masked out · blue: the merged set, resolutions 8 and 9"}

Cell topology for Quadbin, H3 and S2 keys stored as uint32x2 little-endian (low, high) words. GPUCellCompaction supports Quadbin, H3 and S2 (levels 0–30; expansion depth at most 15). This is the Arrow Uint64 layout used by GPUCellAggregation. Inputs also accept wordOrder: 'high-low'. A zero key means "no cell" in every output.

Both consume cell keys, not positions, so neither takes a spatialContext.

  • GPUCellTopology writes a fixed fan-out row per input cell, with stride from getCellTopologyStride(family, operation):
    • {type: 'disk', k}: gridDisk / gridDiskDistances, sorted by (distance, key). Optional distances column.
    • {type: 'ring', k}: gridRing, sorted by key.
    • {type: 'parent', resolution}: cellToParent.
    • {type: 'children', resolution, inputResolution}: cellToChildren, in ascending key order.
    • Rows are zero padded and an optional counts column gives the valid entries per row. k is at most 8 and the children stride at most 4096 (H3 depth 4, Quadbin/S2 depth 6). Invalid, masked or wrong-resolution rows give zero rows.
  • H3 neighbors are exact. H3_NEIGHBOR_WGSL ports H3's h3NeighborRotations: base-cell neighbor and rotation tables, class II/III digit carry tables and pentagon clockwise-offset faces. Disks and rings are a bounded breadth-first search per thread over the six neighbor steps. The search is integer-only and exact across icosahedron faces and pentagons. A pentagon's disk has fewer cells, and the rest of the row is zero padded.
  • Quadbin neighborhoods use Chebyshev distance on tile column and row (QUADBIN_KRING style). Columns wrap across the antimeridian. Rows are clipped at the poles. A tile that the wrap reaches twice at small zoom levels appears once.
  • S2 neighborhoods count steps across the four edge neighbors, including exact integer cube-face transitions through level 30. A diagonal contact is not a step. Disks have stride 2k(k+1)+1, rings 4k (both 1 at k = 0); these are flat square-grid upper bounds, so cube corners and small levels leave zero padding. Output order is (distance, key) for disks and key for rings. Parents accept mixed levels; children require the declared inputResolution and enumerate every descendant in ascending Hilbert-key order. GPUS2CellHierarchy remains available for its compatibility statuses, immediate children, edge-neighbor slots and leaf ranges.
  • GPUCellCompaction handles sets of cells:
    • {type: 'compact', minimumResolution?} (compactCells): input is cells at one resolution, which are sorted unless sorted: true and then deduplicated. It replaces every complete sibling set by its parent, recursively: 4 children for Quadbin, 7 for an H3 hexagon, and for an H3 pentagon 6 at depth 1, (5 * 7^d + 1) / 6 in general.
    • {type: 'uncompact', resolution, maximumDepth?} (uncompactCells): count, scan, then emit the descendants at resolution.
    • Both write a capacity-bounded {cells, status: {count, requiredCount?, overflow, droppedCount?}}. Compact output is in ascending canonical key order. Uncompact output is ascending when the input is in path order.
graph.add(new GPUCellTopology({
  family: 'h3', operation: {type: 'disk', k: 2},
  cells, output: {cells: diskCells, distances, counts}   // diskCells.length = rows * 19
}));
graph.add(new GPUCellCompaction({
  family: 'h3', operation: {type: 'compact', resolution: 9},
  cells: polyfillCells, output: {cells: compacted, status: {count, overflow}}
}));
  • Determinism. All operations are integer-only, with fixed sort orders. GPU results equal the CPU oracles (h3-js and BigInt Quadbin) bit for bit, including padding.

GPU/CPU parity specs require relative tolerances of 2e-5 for H3 and 3e-6 for S2/Quadbin. The CPU twin accepts either option and computes in binary64 for both. GPUCellCover

Supports H3, Quadbin and S2. S2 compaction/outline levels are 0–30 and compaction expansion depth is at most 15. S2 covering is limited to level-15 center containment, rather than exact polygon intersection.

Polyfills polygons into H3, Quadbin or S2 cells, emitting (feature id, cell) pairs.

::lens{scenario=gpu-spatial-analysis.cell-cover rung=result caption="Grey: 17 community areas · blue: 163 resolution-8 H3 cells whose centres fall inside"}

Polyfills polygons (with holes) into Quadbin, H3 or S2 cells, like CARTO QUADBIN_POLYFILL / H3_POLYFILL and h3-js polygonToCells. The result is (feature id, cell) pairs that feed GPUCellAggregation pre-keyed rows, GPUKeyJoin and GPUCellCompaction.

Maximum: candidateCapacity is at most getGPUCellCoverMaximumCandidateCapacity(device) (2^24 on a default device), and with the edge-slab index positions.length + edgeSlabEntryCapacity is at most getGPUCellCoverMaximumEdgeSlabEntryCount(device) (2^24).

  • Inputs. Polygon features use the four-level layout: positions (lng/lat float32x2), featureOffsets, polygonOffsets, ringOffsets, and optional featureIds. Geometry is planar in lng/lat degrees, as in h3-js and turf. Containment is even-odd over all rings, decided exactly (exact orientation signs, a cell centre exactly on an edge resolved by the shared Simulation-of-Simplicity tie rule of utils/exact-geometry-wgsl.ts). spatialContext defaults to, and must be, longitude/latitude without a metric and with linear edges (planar contexts and great-circle edges throw).
  • Antimeridian and poles. A feature with a non-pole edge whose raw longitude difference exceeds 180 degrees gets no cells and increments output.status.invalidCount; prepare it with GPULonLatPolygonPreparation first. Pre-split multipolygons and same-pole edges are accepted, including split Fiji and Natural-Earth Antarctica. Empty rings contribute no bounds. Full-width features enumerate full-width lattices; with candidateEnumeration: 'bounds', provision candidateCapacity accordingly and inspect candidateCount and candidateOverflow. A feature reaching past the cover's latitude limit (89 degrees for H3, 85.051129 for Quadbin) loses its polar cells and is counted in the optional output.status.uncertainCount. Both scalars are cleared on every encoding.
  • Containment.
    • 'center': the cell centre is inside the polygon.
    • 'full': the cell lies inside the polygon.
    • 'intersects': the cell interior meets the polygon.
    • Quadbin supports all three modes. A Quadbin tile is an axis-aligned lng/lat rectangle, so full and intersects are exact edge-versus-open-rectangle tests. H3 supports 'center' only.
  • Candidates. Quadbin tests the integer-exact tile range of each feature's bounding box. H3 lays a lng/lat lattice over the bounding box, with spacing below half the minimum H3 inradius at that resolution (measured from h3-js; the minimum sits next to a pentagon). The longitude spacing is taken at the feature's most equatorward latitude (0 when it spans the equator), so tall features are oversampled toward the pole rather than missing cells nearer the equator. Each lattice point indexes its cell with cellIndexH3FromLngLat. The cell is emitted only from the lattice point nearest its centre, so every cell whose centre lies in the polygon is emitted exactly once with no sort.
  • Sparse polygons (candidateEnumeration). A thin diagonal polygon (a river, a road buffer, a coastline strip) or a sparse multipolygon has a bounding box that is mostly empty, so testing every box cell is wasteful and can overflow candidateCapacity. Both lattices are axis aligned in degree space (Quadbin tile rows are latitude bands, H3 sample rows are constant-latitude lines), so per lattice row the cells that can be accepted lie in x intervals that are found by a boundary trace plus a scanline fill, and only cells in those intervals are candidates:
    • The boundary trace emits, for every edge and every row its y range touches, the x span of the edge part inside the row band. The scanline fill takes the crossings of every edge with the row's test line (half-open in y, so a vertex on the line counts once), sorts them by row and x (stable radix sorts) and pairs them even-odd over all rings, which gives the interior intervals.
    • Spans and interior intervals are swept per row, grown by a proven f32 slack (a few ulps of the crossing, plus half a column for H3, whose accepted centre rounds to the lattice point) and converted to disjoint column runs. The exact test, the cell order and the output are unchanged, bit for bit, because the intervals contain every cell the test can accept.
    • candidateEnumeration: 'bounds' | 'scanline' | 'auto' (compile-time, default 'auto'). With 'auto' the stage is built when candidateCapacity is at least 65536, and each feature picks the scanline runs on the GPU when its box has more than four times as many cells as the scanline work (twice the rows plus the edge-row slots). A feature that does not fit scanlineSlotCapacity (default min(candidateCapacity, 2^20, max(16 * vertices, 16384))), has a non-finite vertex or would enumerate 2^32 candidates keeps its bounding box. The built stage runs a fixed set of passes (two sorts and several scans over three events per slot) whether or not a feature uses it, so size scanlineSlotCapacity to the polygons at hand or use 'bounds' for compact polygons only.
    • candidateCapacity counts enumerated candidates, so with the stage it covers far larger bounding boxes of thin or sparse polygons. output.status.candidateCount (optional) reports the unclamped enumerated total.
  • Output. {featureIds, cells (uint32x2 little-endian), status: {count, requiredCount?, overflow, candidateOverflow, candidateCount?, invalidCount?, uncertainCount?}}. status.overflow means only that accepted cells exceeded the final cell capacity; status.candidateOverflow means candidateCapacity truncated enumeration, in which case requiredCount is not an exact full-cover requirement. Order is by feature, then candidate order. The pipeline is count, scan, test, scan, write, with no atomic append, so it is deterministic.
graph.add(new GPUCellCover({
  family: 'h3', resolution: 8, containment: 'center',
  positions, featureOffsets, polygonOffsets, ringOffsets,
  candidateCapacity: 1 << 22,
  output: {featureIds, cells, status: {count, overflow, candidateOverflow}}
}));
  • Accuracy.
    • Quadbin results equal an f32-faithful CPU oracle at resolutions 3-10 in all modes. Compared with an independent f64 centre test there were 0 disagreements.
    • H3 center matches h3-js polygonToCells exactly at resolutions 3-7. At 8-10 it differs on 12 of about 75,000 cells. Each of those cells has its centre within 5e-5 degrees of a polygon edge, where the f32 centre differs from the f64 one.
    • An f64 simulation of the lattice rule matches h3-js exactly, so the spacing never misses a cell.

output.core is an optional uint32 column parallel to output.featureIds (the same length): 1 for a core cell (a Mosaic chip, provably inside the feature) and 0 for a border cell. It works for every containment and both families. It is conservative: a cell is core only when its center is inside and no polygon edge enters the cell (for H3, its boundary bounding box) grown by 2e-4 degrees plus 0.1% of the cell size. Border cells can still lie entirely inside. A join can skip the exact point-in-polygon test for points whose cell is core.

Supports H3, Quadbin and S2. S2 compaction/outline levels are 0–30 and compaction expansion depth is at most 15. S2 covering is limited to level-15 center containment, rather than exact polygon intersection.

Finds the boundary edges of a sorted H3, Quadbin or S2 cell set and chains them into closed rings.

::lens{scenario=gpu-spatial-analysis.cell-set-outline rung=result caption="Grey: 163 covering H3 cells · blue: one closed ring chained from 140 exposed edges"}

The boundary edges of a set of H3, Quadbin or S2 cells, the cellsToMultiPolygon outline. Set rings to chain the edges into closed rings with shells and holes on the GPU (GPUSegmentRingAssembly).

It consumes cell keys, so it takes no spatialContext; the segments and rings it produces are longitude/latitude degrees. edgeModel and outputSpatialContext.edgeModel are 'great-circle' for H3 and 'linear' for Quadbin; outputSpatialContext.metric is 'none'.

graph.add(new GPUCellSetOutline({
  family: 'h3',
  cells, // uint32x2 little-endian keys, sorted ascending and distinct, e.g. a GPUCellAggregation table
  count: tableCount, // optional one-row valid row count
  groups, // optional uint32 label per row: also emit edges between different groups
  output: {rows, cells: segmentCells, edgeIndices, endpoints, groups: segmentGroups, status: {count, overflow, requiredCount}},
  rings: {normalizeWinding: true, output: ringOutput} // optional, see below
}));
  • The output columns share one capacity: rows (the input row, also the compact ID column), cells, edgeIndices, endpoints (float32x4: lng0, lat0, lng1, lat1), optional groups and status with count (clamped), overflow and optional requiredCount.
  • An edge is emitted when the neighbor across it is absent, or has a different group label. With groups, a border between two groups is emitted from both sides, tagged with each side's group.
  • Order is by (input row, edge index): classify, inclusive scan, write, with no atomics, so it is deterministic.
  • H3: edge e is the e-th edge of cellToBoundary (up to 10 slots with distortion vertices, so such an edge appears as two segments). The neighbor across it is the H3 neighbor whose center is nearest the edge midpoint, a geometric rule validated against h3-js on hexagons, a pentagon disk and distortion cells. Quadbin: 0 north, 1 east, 2 south, 3 west; columns wrap, and rows beyond the poles are absent, so the map edge is an outline edge.
  • Membership is a binary search, so the input must be sorted and distinct. Invalid keys never emit.
  • Endpoints are f32. H3 cells that straddle the antimeridian keep their cellToBoundary longitudes, so a segment can span more than 180 degrees. Other families (quadkey, geohash, S2, A5) are not supported.
  • Segments are directed with the cell interior on a fixed side: outline.interiorSide is 'left' for H3 (counter-clockwise shells) and 'right' for Quadbin (clockwise shells).
  • rings: {vertexTolerance?, normalizeWinding?, output: GPUSegmentRingAssemblyOutput} composes GPUSegmentRingAssembly after the outline, with output.endpoints, output.status.count and output.groups as its inputs, outputSpatialContext as its context and interiorSide taken from the family. Use normalizeWinding: true for counter-clockwise shells and clockwise holes in both families. Without rings, hole detection and ring orientation are left to the caller.

GPUSegmentRingAssembly

vertexTolerance must round to positive finite float32 (at least 2^-149); caller and scratch bindings are checked before graph declarations.

Chains directed boundary segments into closed rings with shell and hole classification.

::lens{scenario=gpu-spatial-analysis.segment-ring-assembly rung=result caption="Grey: 17 community areas · blue: one outer shell from 3,184 edges once shared borders cancel"}

Chains directed boundary segments into closed rings on the GPU, the ring-assembly step of cellsToMultiPolygon. It consumes GPUCellSetOutline output, or any float32x4 segment list whose vertices meet within a tolerance.

spatialContext replaces the former geographic flag. It defaults to native planar coordinates (behavior change: geographic defaulted to true). A longitude-latitude context with metric 'none' scales x differences by cos(latitude) (clamped at 0.01) when comparing turns at shared vertices; great-circle and other metrics are rejected because ring assembly measures nothing, and vertexTolerance stays in position units. Hole detection uses the exact orientation of the turn at each ring's lowest vertex (smallest y, then x; the f32 area sign only when that turn is zero), so a sliver ring whose f32 shoelace sum cancels is still classified correctly.

The resolved spatialContext describes both input and output. For longitude/latitude it preserves the input edgeModel, including omission; both 'linear' and 'great-circle' edges are accepted with metric 'none'. Pass outline.outputSpatialContext when assembling cell outline segments. Prepare global or antimeridian-crossing rings with GPULonLatPolygonPreparation before polygon consumers, and prepare great-circle rings before consumers that require linear edges.

graph.add(new GPUSegmentRingAssembly({
  endpoints, // float32x4 (x0, y0, x1, y1), e.g. GPUCellSetOutline output.endpoints
  count, // optional one-row valid segment count
  groups, // optional uint32 per segment: rings never mix groups
  vertexTolerance: 5e-5, // compile-time Chebyshev matching distance, input units
  interiorSide: 'left', // side of each segment that is filled ('left': counter-clockwise shells)
  normalizeWinding: true, // shells counter-clockwise, holes clockwise (RFC 7946)
  splitTouchingRings: true, // default
  spatialContext: {coordinateSpace: 'longitude-latitude', metric: 'none'}, // cos(lat) in turn comparisons; omit for planar
  output: {
    ringOffsets, // uint32, ringCapacity + 1
    positions, // float32x2, vertex capacity
    ringAreas, ringIsHole, ringShells, ringGroups, // optional, ringCapacity rows
    segmentRings, segmentVertices, segmentFlags, // optional, one row per input segment
    polygons: {kind: 'polygons', positions: polygonPositions, ringOffsets: polygonRingOffsets,
      polygonOffsets, featureOffsets}, // optional four-level polygon port
    status: {count, overflow, requiredCount, openSegmentCount, touchingSegmentCount}
  }
}));
  • Layout. GeoArrow style: ring r is positions[ringOffsets[r] .. ringOffsets[r + 1]), closed (the last vertex repeats the first). Rings are ordered by their lowest input segment index; a ring starts at that segment and follows its direction (or is reversed by normalizeWinding). Offsets past status.count repeat the final offset.
  • Matching. Each segment end is matched to segments that start within vertexTolerance in the same group, through a sort of quantized vertex hashes and a 3 x 3 neighborhood lookup. Quadbin vertices are bit-exact; H3 vertices of neighboring cells agree within f32 round-off (below 5e-5 degrees). Pick a tolerance of at least four times the f32 spacing of the coordinates and well below the shortest segment. Without vertexTolerance the tolerance is four f32 ulps of the frame extent (extent * 2^-21, measured on the GPU), so only separately rounded copies of one vertex match (behavior change: the default was an absolute 5e-5). GPUCellSetOutline keeps 5e-5 degrees as its own preset (GPU_CELL_SET_OUTLINE_VERTEX_TOLERANCE), valid up to H3 resolution 12 and Quadbin zoom 22; pass about a quarter of the shortest edge for finer cells. Vertices are hashed relative to the first segment's start vertex into unsigned cells of size max(vertexTolerance, extent * 2^-22) (with a small slack), where extent is the largest coordinate offset from that origin, measured on the GPU. Projected coordinates (UTM, Web Mercator) therefore never collide at any tolerance, and candidates are still compared by their true distance against vertexTolerance. status.overflow is also set when a valid segment has a non-finite coordinate.
  • Shells and holes. The signed area (shoelace, relative to the first vertex) is compared with interiorSide: with 'left' shells are counter-clockwise. ringIsHole flags holes. ringShells assigns every hole to its innermost enclosing shell (same group), a shell to itself, and a hole without a shell to GPU_SEGMENT_RING_ASSEMBLY_NONE. Of two shells that contain the hole, the inner one is the one whose bounding box lies inside the other's, which is exact for a planar boundary; float32 areas order only shells whose boxes are equal or do not nest (smaller first, lowest index on ties). Until 2026-11-11 the choice was the smallest float32 area among shells larger than the hole, which left a hole unowned, or gave it to an outer shell, when a thin shell and its hole had areas that rounded to the wrong order. A BVH over shell boxes rejects whole subtrees whose bounds cannot contain the hole box. Its two-word Morton key interleaves every bit of the ordered float32 centers, avoiding global-extent quantization: a distant shell cannot collapse nearby shells into an unresolved key tie. The index reuses the four-float ring bounds and stores area, ring kind and group in a separate three-word record. At 8,388,608 rings these bindings use 128 MiB and 96 MiB respectively, retaining the default device's ring capacity and eight-storage-binding traversal limit. Only candidate shells receive a vertex walk; equal-area ties still select the lowest ring index, independently of BVH order. Containment is exact: the probe is the symbolic point infinitesimally beside the midpoint of the hole's first edge, on the side away from the hole, classified with the exact point-in-ring rule of utils/exact-geometry-wgsl.ts, so a hole whose edge runs along another ring is still assigned correctly. A ring of area 0 is an empty walk and is left out of polygons; a face thinner than one float32 step, whose float32 area sums to exactly 0 although it has an exact non-zero turn at a lowest vertex it passes once, reports 1.17549435e-38 with the sign of that turn in ringAreas and is kept.
  • Touching vertices. When more than one segment starts at a segment's end vertex (Quadbin cells that meet at a corner; H3 hexagons never do), the continuation is the outgoing segment that turns tightest toward the interior, so regions that touch at a point stay separate rings. The turns are ordered exactly: at the shared vertex when every candidate starts on it, and otherwise (a candidate matched within vertexTolerance but not equal) by the exact signs of the cross products of the segment directions end - start, computed from the four endpoints. Until 2026-11-11 those signs were taken from the float32 differences, which round when the two ends of a segment differ in magnitude; with edges about 1e-7 radians apart at a matched vertex that lost rings. Longitude/latitude input is ordered by the same exact tests: its turns are measured with longitude differences scaled by the cosine of the latitude, a positive scale of one axis, which changes no orientation sign and so no order. It used a float32 turn key before, which sent near-parallel candidates to the lowest index. Only non-finite coordinates still fall back to that key. A candidate that exactly reverses the incoming segment (and is not removed as its paired or cancelled twin) is the tightest turn for either interiorSide, so a scene and its mirror image with the interior on the other side give the same rings; until 2026-11-11 it was the first choice for 'left' and the last for 'right', and a square with a zero-width spike came back as two rings with the interior on the left and as one ring with two open segments when mirrored. With splitTouchingRings a second tracing pass swaps the continuations of segment pairs that end at one vertex and lie on one ring, so two holes meeting at a corner, or a hole pinched to its shell, become simple rings. Choices taken twice resolve to the lowest segment index. status.touchingSegmentCount and segmentFlags (GPU_SEGMENT_RING_ASSEMBLY_FLAG_TOUCHING 1, _DANGLING 2, _CONFLICT 4) expose the ambiguity.
  • Open chains (dangling ends, tolerance misses, truncated input) emit no ring and are counted in status.openSegmentCount.
  • Cancelling pairs. cancelOpposingSegments removes exact a -> b and b -> a pairs within a group before tracing (they are flagged GPU_SEGMENT_RING_ASSEMBLY_FLAG_CANCELLED, 8, and not counted as open). GPUIsobandRings uses it for the edges shared by two cells. output.polygons.sourceIds gives the group of each polygon's shell.
  • H3 pentagons. Rings of three mid-latitude pentagons (resolutions 2, 3 and 5, alone, in disks, as holes and open rings) equal h3-js cellsToMultiPolygon. The two polar pentagons enclose a pole, so their rings have no planar lng/lat orientation.
  • Bounded output. Rings are written whole, as a prefix: status.count is the number written, status.overflow is 1 when ring or vertex capacity dropped rings, and status.requiredCount is the full ring count.
  • Polygon layout. output.polygons regroups the rings as GeoArrow polygons (a shell, then its holes; the closing vertex dropped; holes without a shell dropped) with GPU-written, flat-padded offsets over fixed-length views. Every polygon is one feature, featureOffsets is an identity prefix padded with polygonCount, and optional sourceIds carries its shell group. It plugs into the polygons port of GPUPointInPolygonJoin (positions, featureOffsets, polygonOffsets, ringOffsets): the join's compile-time topology is the ring capacity and unused polygons and rings are empty.
  • Deterministic (integer atomics only). The cost is two pointer-jumping phases of ceil(log2(rows)) dispatches each (plus the second tracing pass), a sort and scans. Rings that cross the antimeridian keep the input longitudes; use GPULonLatPolygonPreparation for global or antimeridian-crossing rings. Turn comparison uses a monotone pseudo angle, not atan2. Ring areas are f32.

Such input sets candidateOverflow; increasing final segment capacity cannot repair it. GPULineSplit reports the same incomplete split input in pieces.status.overflow.
  • GPUPolygonize expands each noded segment into two directed edges, assigns deterministic left-face ownership, omits the unbounded and zero-area faces, and emits canonical polygon features. It emits every bounded face (shapely polygonize semantics): the hole of a holed ring comes back as its own polygon. Its diagnostics classify source edges as closed-ring, open-chain, cut, dangle, and unused.
  • GPUMakeValid applies the same pipeline independently to every input polygon feature, then keeps a face only when the feature's source rings cover it an odd number of times. The fill rule is source parity (even-odd), the GEOS make_valid linework method that shapely uses: a valid polygon with a hole returns the annulus only (no second polygon filling the hole), an island inside a hole is kept as its own polygon, and the doubly covered lens of mutually crossing rings is dropped. It repairs self-crossing and mutually crossing rings into bounded polygon faces; dimensional collapse remains available through diagnostics rather than being converted to mixed geometry. Parity is probed exactly at the symbolic point infinitesimally left of the midpoint of the first edge of each face shell (the shared probe of utils/exact-geometry-wgsl.ts; strictly inside the face, no rounded sample point: the ray's height is the exact midpoint of the edge's two heights, so an edge one float32 step tall is handled), one thread per face. Stable sorts order segments by height, then exact uint32 source group. Each face binary-searches its group's contiguous leaf range before traversing the height BVH; node ranges outside that group are pruned before testing segments. Group ID gaps, outliers and float32 collisions therefore do not broaden the candidate search. Inclusive height bounds retain edges on the symbolic ray. Candidates on both sides of the probe are retained to preserve the uncertainty fallback. A face whose orientation cannot be certified is kept. status.count is the number of kept polygons. Rings close implicitly: the edge from a ring's last vertex back to its first is always part of the boundary, whether or not the ring repeats its first vertex. GPULineNoding emits no zero-length row for a repeated vertex.

All three require an explicit GPUTopologyPrecisionPolicy. The current policy uses the shared exact orientation predicates with an uncertainty counter, float32 coordinate storage, and a caller-chosen Chebyshev vertex tolerance. For GPULineNoding, requiredCount is exact when candidateOverflow is zero. For GPUPolygonize and GPUMakeValid, status.requiredRingCount is the unclamped ring-assembly requirement (every directed face ring, including holes and unbounded walks), for sizing ring capacity when noding is complete. status.count counts written features, after parity filtering for make-valid. There is no status.requiredCount: an exact feature requirement is unknown after ring loss. Breaking (2026-11-17): rename the former ring-valued status.requiredCount to requiredRingCount. Every supplied final status view is packed uint32 with at least one row; final status ranges must be disjoint, including count and requiredRingCount. overflow always describes the current port's final capacity: segments for noding, directed edges for the directed port, and rings/vertices for polygon publication. Directed requirements are twice the noded segment requirement, so a full directed buffer can still overflow. candidateOverflow reports intermediate loss or uncertainty separately. At polygon publication it includes noded segment truncation as well as incomplete intersection/snap-rounding candidates. Check both flags before using geometry or trusting requirements. Every supplied uncertainCount destination (top-level, noded and directed) receives the same count on every submission, including zero. Make-valid groups internally by feature row and maps retained rows to caller sourceIds only at publication; all uint32 identities, including 0xffffffff, are accepted in the active prefix. No CPU readback or compatibility adapter is involved.

Maximum: positions has at most getGPUSegmentIntersectionMaximumVertexCount(device) (4194304 on a default device: the 32-byte segment-table row per vertex must fit one storage binding) rows, and the line (or ring) count plus four times intersectionCapacity is at most getGPULineSplitMaximumPieceBound(device) (4194304 on a default device, the 32-byte piece-table row). Each contributor validates both under its own ID.

Planar only: spatialContext defaults to native planar coordinates and a longitude-latitude context throws; project to a planar frame first (createGPULocalFrame, GPULocalFrameProjection). The resolved context is passed on to the noding and ring-assembly stages.

GPUCellTableCompare

Outer-joins two sorted cell tables into one union table of before, after, delta, ratio and z-score columns.

::lens{scenario=gpu-spatial-analysis.cell-table-compare rung=result caption="35 zoom-17 union cells coloured by shops minus restaurants · grey: the places counted"}

GPUCellTableCompare outer-joins two sorted cell tables (the outputs of GPUCellAggregation or GPUCellRollup) into one union table for period-over-period or A-versus-B compare maps. Both tables must use the same grid family and resolution; the contributor cannot check that.

It compares tables keyed by cell, so it takes no spatialContext.

graph.add(new GPUCellTableCompare({
  before: lastMonth, after: thisMonth,
  measure: 'sum', sumScale: 65536,
  output: {cells, presence, before, after, delta, ratio, percentChange, zScore, status: {count, overflow, candidateOverflow}}
}));
  • output.cells holds the union keys ascending (uint32x2, little-endian (low, high)); its length is the capacity. When the retained-input union is larger, the smallest keys are kept, status.count is clamped and status.overflow is 1. Required status.candidateOverflow receives the OR of both inputs' final and inherited loss; it is separate from destination overflow and is rewritten on every submission. Optional status.requiredCount receives the retained-input union requirement, a lower bound on the full union when input cells were lost. For one retained before-cell, an empty after-table and four union slots, source loss gives count = requiredCount = 1, overflow = 0, candidateOverflow = 1. Increase the source capacity to recover the missing cell.
  • presence: bit 1 (GPU_CELL_COMPARE_PRESENT_BEFORE) when the cell is in before, bit 2 (GPU_CELL_COMPARE_PRESENT_AFTER) when in after.
  • The two loss flags publish separately and may share a buffer at adjacent word offsets. Mapping both flags to the same word is rejected. count, overflow and requiredCount publish together and must have nonoverlapping aligned storage binding ranges.
  • before / after: the measure ('count', or 'sum' decoded from the fixed-point sums), 0 when absent.
  • delta = after - before, computed with an exact sign and unsigned 64-bit magnitude from the signed integer measures, then rounded once to nearest f32 (ties to even) and divided by sumScale for sums. Guard and sticky bits from both integer words decide rounding. Differences outside the signed 64-bit range retain their sign, and large sums with small differences are not lost to f32 cancellation. For example, sums of -2^62 and +2^62 at scale 1 produce +2^63.
  • ratio = after / before and percentChange = 100 * (after - before) / before, NaN when before is 0.
  • zScore: 'poisson' (default for counts) is delta / sqrt(before + after), 0 when both are 0. It is a statistic of counts: with measure: 'sum' use it only for sums of non-negative values, and a row where before + after is negative, or is 0 while the sums differ, gets NaN. 'standardized' (default for sums) is (delta - mean) / sd over the union rows with the population standard deviation, 0 when sd is 0. A published extent reduction supplies one common power-of-two normalization for all finite deltas before computing mean, squared deviations and scores. This prevents squared-delta overflow and preserves scores across sum scales. The three subsequent fixed-order stages compute partial sums, partial squared deviations and the combined statistics, so a re-encode is bitwise identical.
  • Rows past status.count hold the empty key (all ones), presence 0, before/after 0, and NaN in delta, ratio, percentChange and zScore.

The merge is a binary-search merge path with an exclusive scan of matched rows, so every union row is written by exactly one invocation and no atomics are used. Cost is O((n + m) log(n + m)). Table contents are per-frame (re-encode without recompiling); capacities, columns, measure and zScore are topology.
