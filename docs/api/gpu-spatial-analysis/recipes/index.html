Recipes

See Geospatial workflow recipes for zonal distributions, network and facility scenarios, interpolation diagnostics, exposure, raster change, drainage, track quality, local variability, cell flows and surface preparation.

The local-variability recipe retains every declared bounded-status view on its intermediate weights port and named weights stage, including approximation, uncertainty and iteration diagnostics.

Recipes are plain functions, not classes: addXRecipe(graph, props) constructs the contributors, calls graph.add in chain order, wires outputs to inputs and returns a GPURecipeResult: {contributors, outputs, intermediates, status}. outputs holds the named terminal views, intermediates the named ports between stages and status the GPU-resident completeness and convergence views, grouped by stage. contributors lists every stage the recipe added, in order: composed contributors, and each raw glue kernel as one named stage. Published calibration stages and drive-time road/time/band adapters are included in that same declaration-order list. Status counts over rows or cells (invalid rows, unresolved cells) run as a row-parallel kernel plus a published GPUReduction sum, never as one invocation looping over the rows. Views you pass in (zScores, bins, colors, ...) are caller-owned and readable; every other intermediate is a graph transient. Inference recipes (hot spot, rate cluster, space-time hot spots, spatial regression) take one settings object and GPUParameterBuffers they fill themselves, derive result.inference from the same object and repack it with result.setSettings(settings); the other recipes pass per-frame parameter views (getGPU...ParameterValues) through. Neither rebuilds the graph. Geometry inputs are the shared ports: GPUPointGeometryPort, GPUPolygonGeometryPort (four-level layout, one row per feature) and GPUPackedGeometryPort<GPUTrajectoryGeometryPort>.

All 24 add…Recipe functions exported by the spatial recipes entry point and all four exported by the network recipes entry point prepare their complete graph declaration before changing the caller's graph. Contributor constructors and cross-stage checks finish before the builders expand and schedule contributors. Preparation uses a separate, uncompiled graph with the same device limits, preserving buffer aliases, view offsets, texture subresources and vector chunks. Nested recipes share their enclosing preparation. If validation or contributor expansion fails, the caller's nodes, resources and parameter-buffer contents stay unchanged: correct the configuration and retry with the same recipe ID. Temporary contributors that own resources are destroyed even when a later stage fails. Parameter writes are validated without upload and applied only after successful scheduling; frozen GPUParameterBuffer wrappers are supported. Later setSettings calls still write immediately. Contributors and interleaved adapter kernels retain their declaration order when scheduling is deferred.

Auxiliary luma resources and devices carried alongside a recipe's ports keep their identities and ownership. Preparation treats them as opaque references and does not inspect their native state; graph views are mirrored separately. Each consumed configuration field, including inherited getters and JavaScript Proxy reads, is captured once and shared by both declarations. Unrelated fields are not evaluated. Configuration records returned in metadata are captured facades; caller graph views, parameter buffers and declared prepared-join handles retain their original identities. Retained committed metadata is detached from the temporary preparation graph after preflight. The every-stage rollback matrix covers the 28 functions in the two recipes barrels; the public family inventory also lists 13 domain recipes outside that matrix, with their own family contracts.

Preparation repeats host declaration work once and never compiles, encodes, submits or reads data. Use unused recipe/resource IDs on a mutable graph. The published graph has no mutable node-ID inspection or transaction API, so this configuration guarantee cannot cover collisions with pre-existing caller node IDs, externally overridden scheduling methods, a graph already frozen by compilation, or allocation/device failure during final declaration. Successful recipes retain the same concrete command nodes, outputs and status meanings.

Recipe implementation form and result compatibility are checked separately. Population support alignment returns an empty intermediates map and three named diagnostic substages under status.stages; their scalar invalidCount views alias its missing-target, ambiguous-target and excluded-source words. Use result.packedStatus for the original four-word certificate. The contributor and both operation forms retain their packed output.status contract.

The hot-spot, rate-cluster, space-time, fleet (both variants), period-comparison, change-of-support, cluster-and-outline, spatial-regression, points-in-polygons and straight-line-catchment results type their outputs and intermediates maps. The exported GPU<Name>RecipeOutputs and, where present, GPU<Name>RecipeIntermediates types describe those maps; the top-level convenience fields remain available. For example, spaceTime.outputs.cube feeds GPUEmergingHotSpotsProps.values, and fleet.outputs.stops.centroids is a typed float32x2 view. Optional stages remain optional in both paths, so check for hotSpots.outputs.permutation or spaceTime.outputs.colors before using them.

const hotSpots = addHotSpotAnalysisRecipe(graph, {
  source: {kind: 'points', positions, family: 'quadbin', resolution: 8, cellCapacity: 4096,
    studyArea: {kind: 'polygons', positions: studyPositions, featureOffsets, polygonOffsets, ringOffsets,
      candidateCapacity: 16384}},
  settings: {significanceLevel: 0.05, seed: 7, permutationCount: 199},
  parameters: autocorrelationParameters, // GPUParameterBuffers the recipe fills from settings
  outputs: {zScores, bins},
  permutation: {parameters: permutationParameters, maximumPermutations: 199},
  color: {classBreaksParameters, maximumClassCount: 5, colorScaleParameters, palette, maximumPaletteCount: 5}
});

Notes:

  • Rate-cluster weights publish weightsCandidateOverflow for pairCapacity loss and weightsOverflow for final neighborCapacity loss. Inspect both flags. Grow pairCapacity first when the candidate flag is set; weightsRequiredCount is then only a lower bound for neighbor slots. The Kepler rate-cluster binding refuses either loss flag and uses its CPU fallback. Explorer and showcase readouts distinguish pair loss from final neighbor loss and mark dependent results unavailable.

  • Spatial regression diagnostics suppress statistics and p-values with status code 3 on either weights-loss flag; specification selection returns 4 (undetermined). Clean reuse restores inference. Caller-provided regression writes cannot alias either weights-loss input; rejection precedes all resource registration so correcting the output permits a same-ID retry.

  • All caller-provided fleet stop outputs, including durations, row indices and status words, must have logical byte ranges disjoint from scratch.stopMask. Adjacent views that share an aligned storage binding remain supported through separate adapter dispatches.

  • Fleet zone-event lenses and website readouts distinguish final event overflow, combined event candidate loss (scratch or per-track), and scratch-only loss. Either event-loss flag makes crossing counts incomplete; only scratch loss makes dense dwell totals incomplete. Pending readbacks are labelled pending. Truncated per-track event lists can retain complete dwell totals. Crossing counts require the count and zone-column readbacks; positions are needed only for drawing dots. Missing numeric readbacks are pending or unavailable, including missing dwell totals, never zero.

  • The space-time recipe counts events into a dense cell * sliceCount + slice cube with integer atomics, because GPUCellAggregation keys must be valid Quadbin or H3 cells. Passing the sorted-path scratch views or outputs.status.groupOverflow selects the GPUGroupStatistics path instead. Group status views need at least one packed uint32 word; spare words are untouched. On the supplied-cell-ID route, the weights status stage preserves both overflow and candidateOverflow; a nonzero flag means neighborhood inference is incomplete. These input words cannot alias recipe writes. The slice interval, including seven days per week, must fit the period index's signed divisor limit of 2^31 - 1 before recipe resources are registered. The origin's whole calendar-step index must fit [-2^31, 2^31 - 1] too; hourly indices count hours from the Unix epoch. This check also precedes allocation. Every declared writable port and every published weights status word (including invalidCount) participates in alias validation. Declared fields, including inherited/getter-backed status fields, are captured once for validation and scheduling. slices.count is at most 256; trend autocorrelation correction has the lower limit documented by GPUEmergingHotSpots. Every contributor, settings object and glue binding is validated before any recipe command nodes are scheduled. contributors includes GPUPeriodIndex and every glue stage in execution order on both counting paths. Event positions must be packed float32x2, and event cell IDs packed uint32, with exactly one row per timestamp. Strided positions are rejected; pack them before construction. Caller-view ownership, shape and binding conflicts, parameter length, settings and palette preconditions are checked before registering recipe resources, so correcting those props permits retry on the same graph and recipe ID. Settings are packed on the host first and written to the caller's parameter buffer only after scheduling succeeds; a rejected second recipe cannot change an existing recipe's settings through a shared parameter buffer. Initial packing preserves all classification settings, including persistentFraction, minimumTrendSliceCount and sporadicRequiresFinalSlice; an identical setSettings call writes identical parameter words. A six-slice series can carry a trend when its requested minimum is three.

  • The drive-time catchment recipe classifies demand in network space (the minimum over the snapped edge ends) and also returns the isochrone triangles for drawing. It assumes both directions are in the CSR. Supplied demandTimes and demandBands must each have exactly one logical row per demand point, regardless of backing-buffer capacity or byte offset. Caller output/scratch buffers must be distinct from original routing inputs and independently retained results, including separate imports of the same physical buffer. Rejection leaves the graph unchanged for a corrected same-ID retry. isochrones takes raster and/or cellOutline (at least one). cellOutline.rings returns closed isochrone rings in result.isochroneRings. isochrones.joinDemand (candidateCapacity and the optional pointFeatureIds, overflow, uncertainCount) joins the demand points to the ring polygon (it needs cellOutline.rings.output.polygons) with GPUPointInPolygonJoin, and result.isochroneDemand.pointFeatureIds is 0 inside and GPU_SPATIAL_JOIN_NO_FEATURE outside. That answers "inside the isochrone at cellCostLimit" at cell resolution (the union of cells that hold reached nodes), where the band classification stays exact at the snapped edge. Isoband triangles cannot feed the join, because their topology is GPU-written and has no ring structure; the cell rings can. Sparse networks drop cells, so the polygon join is coarser than the network-space bands. With candidateCapacity, each snapping reports BVH candidate overflow in result.snapping and the snap-facilities and snap-demand status stages, so a facility or demand point snapped past a dropped candidate is never silent. The other stages are service-areas, the caller-owned isochrone outputs (isochrone-bands, isochrone-band-edges, isochrone-band-rings on the raster path; isochrone-cells, isochrone-outline, isochrone-rings on the cell path) and band-statistics (count, overflow, required count). The service-area assignments are passed to GPUNetworkIsochrones, so raster.output.pixelFacilities, triangleFacilities and cellOutline.byFacility work through the recipe; facility rows are seed rows (2 * facility + endpoint).

  • Every recipe reports each inner contributor's status as a status.stages entry (rule 10): the cluster recipe ends with hull-measures (invalidCount), the straight-line recipe has zonal-statistics (overflow), and the table, join and rasterization stages also carry requiredCount or uncertainCount where the inner contributor computes them. Result-level status words sit in result.status next to stages (for example status.weightsOverflow, status.invalidCount, status.rasterOverflow), sub-results own a status (result.permutation.status.overflow, result.table.status.count), and the outputs overrides mirror those paths (outputs.status.weightsOverflow).

  • The drive-time, straight-line catchment and fleet dwell recipes take an optional spatialContext and return the resolved one as result.spatialContext. The straight-line recipe and both fleet dwell recipes are planar only (longitude/latitude throws; the join and zone edges are straight lines in the plane, and the distance field is Euclidean). The drive-time recipe also accepts longitude/latitude (metric 'none' or 'great-circle'; the cell-outline isochrones need degrees). Both of its snappings then run great-circle: edges are ranked by great-circle distance and maximumSnapDistance is in meters, with no east-west bias at any latitude. Drive times stay in the units of network.weights (the snapped fraction splits the edge cost). For the other recipes, project with createGPULocalFrame and pass its spatialContext (planar, meters), so the distance-field parameters and the straight-line distances output are in meters. The fleet dwell recipes used to hand the trajectory stage a native planar context whatever the data; they now resolve one context and pass it to the metrics, join and zone stages.

  • The rate cluster map recipe runs GPULocalMoran with quadrantGating: 'none' when permutation is given and keeps the quadrant where the permutation significant mask is set; without permutation the quadrant is gated by the analytic p-value. analyticQuadrants returns the local Moran quadrants (gated analytically without permutation, ungated with it).

  • The points-in-polygons choropleth recipe's 'group' back-end uses dense GPUGroupStatistics (keyCount: featureCount, so empty polygons keep a row), writing featureValues directly. For statistic: 'count', featureValues is the uint32 counts view, which GPUClassBreaks and GPUColorScale read as numbers (integerValues: 'numeric'); the featureValues prop is rejected for 'count', and the result type is float32 or uint32.

  • The spatial regression recipe requires a finite residual on every row; the weights pattern may be asymmetric. Optional local fits pass their spatialContext to GPUGeographicallyWeightedRegression; omitted means native planar, and fixed bandwidths use the context's length unit. Its settings.significanceLevel (default 0.05) is packed once into the autocorrelation parameters buffer and read per frame by both the specification search and the residual GPULocalMoran (it used to be a compile-time constant of the search kernel); result.inference and result.setSettings follow it.

  • The fleet dwell recipes take trajectories (GPUPackedGeometryPort<GPUTrajectoryGeometryPort>) and polygon zones (GPUPolygonGeometryPort, sourceIds as stable zone IDs); the zone events variant passes the zones to GPUZoneEvents directly (no edge lists) with trackEventCapacity events kept per track. The straight-line catchments recipe takes grid, parameters and facilities (GPUPointGeometryPort, sourceIds as zone IDs); the cluster recipe takes points (GPUPointGeometryPort).

  • For addFleetDwellZoneEventsRecipe, inspect both events.status.overflow (final capacity) and events.status.candidateOverflow (scratch or per-track loss) before treating the crossing list as complete. The separate recipe status.candidateOverflow identifies scratch loss affecting zone dwell totals and visits; per-track event-list truncation alone leaves those totals intact.

  • The cluster recipe's optional spatialContext defaults to native planar and is returned as result.spatialContext. It is planar only because group summaries and convex hulls are planar: longitude/latitude throws, so project first. Clustering measures distance and rejects local-lambert-equal-area frames; epsilon uses the context's length unit.

  • The cluster recipe drops clusters at or above maximumClusterCount, and the caller supplies the geometry parameters. The change-of-support recipe's status.overflow covers the overlap list only; the raster flags are returned as status.rasterOverflow and status.rasterRequiredCount (stages source-rasterization and target-rasterization).

addHotSpotAnalysisRecipe

Bins observations onto Quadbin cells inside a study area and returns Getis-Ord Gi* z-scores and confidence bins per cell.

::lens{scenario=gpu-spatial-analysis.hot-spot-analysis-recipe rung=result caption="2,344 observations over 13 community areas; each analysed cell is coloured by its Gi* z-score."}

Points on a study area, or a raster, to Getis-Ord Gi* hot and cold spots.

Points source (breaking change from the occupied-cells design):

  • Recipe spatialContext describes study-area polygons (default longitude/latitude, metric 'none', linear edges). For antimeridian crossings or great-circle edges, set prepare: true or prepare with GPULonLatPolygonPreparation. Preparation requires preparedPositionCapacity and a per-frame preparationParameters view from getGPULonLatPolygonPreparationParameterValues(edgeModel, settings). It runs before cell cover and preserves feature rows; status.stages adds study-area-preparation with overflow, requiredCount, invalidCount and approximation. Preparation requires a points source and a longitude/latitude context. The cover's invalidCount counts features with unsplit non-pole antimeridian-crossing edges, not wide bounding boxes.
  • studyArea (a GPUPolygonGeometryPort plus candidateCapacity, optional coverCapacity) and cellCapacity are required. The recipe covers the polygons with GPUCellCover ('center' containment), deduplicates and sorts the cells with GPUCellAggregation, aggregates the points the same way and joins them by binary search of each 64-bit key. Every study cell is a row, with value 0 when it holds no point, so the null mean is not inflated and clusters of empty cells can be cold spots. Points outside the study area are excluded; result.status.pointsOutsideStudyArea counts them. result.table.cells are the sorted study cells and table.counts / table.sumValues the joined values.
  • Neighbors are topological: the cells within neighborRings grid steps (GPUCellTopology disk) that are also study cells, self excluded, binary weights, rows ascending. The defaults are 1 ring for Quadbin (8 neighbors) and 2 for H3 (18 neighbors), the smallest disks that reach minimumNeighbors: 8. This replaces the degree radius and the neighborSearchParameters, gridSize and tableCapacity props. neighborCapacity is optional (defaults to the largest disk); truncation sets the weights status overflow.
  • distanceBand (optional, exclusive with neighborRings) uses a metric band instead: GPUNeighborSearch in radius mode over the cell centers with spatialContext: {coordinateSpace: 'longitude-latitude', metric: 'great-circle'}, so the radius in neighborSearchParameters is in meters (the context's units). Any other context throws: a radius in degrees is an ellipse that narrows east-west with latitude. minimumNeighbors still applies. distanceBand.rowStandardize (default false, classic binary Gi*) row-standardizes the band through the search's compile-time rowStandardize, overriding the per-frame field of neighborSearchParameters. The described weights (information.transform 'row' or 'binary', and the search status) feed GPUHotSpotAnalysis. Every source publishes the unclamped neighbor total as the weights stage requiredCount (the grid-disk adapter included), for getGPUSpatialWeightsCapacityPlan.
  • analyze: 'density' (default) analyses value (or count) per square kilometer. Web Mercator tiles shrink with the cosine of latitude, so raw Quadbin counts compare cells of different area; 'count' is allowed for H3 only (cells are approximately equal area) and throws for Quadbin. Quadbin area is the exact spherical rectangle R^2 dLon (sin(lat1) - sin(lat2)) and H3 area comes from GPUCellMeasures, both on the authalic sphere (GPU_EARTH_AUTHALIC_RADIUS_METERS, which is H3's own radius), so the families share one model. Quadbin areas are within f32 rounding (about 1e-6 relative); H3 pentagons and edge cells above resolution 5 are unreliable (see GPUCellMeasures).

Statistics and legend (both sources):

  • minimumNeighbors defaults to 8 (ArcGIS guidance for analytic Gi*). Rows with fewer neighbors other than themselves get NaN zScores and pValues, bin 0, and are outside the multiple-testing family; status stage minimum-neighbors reports invalidCount. Quadbin with one ring has exactly 8 neighbors at most, so the cells on the study-area border are NaN; use neighborRings: 2 or a lower minimum for them.
  • multipleTesting defaults to 'benjamini-hochberg' (it replaces falseDiscoveryRate). Legend contract, stable under any setting: bins +-1, +-2, +-3 are 90%, 95% and 99% confidence hot (+) or cold (-) spots; without correction that is |z| >= 1.645, 1.960, 2.576, with Benjamini-Hochberg the step-up test at q = 0.10, 0.05, 0.01. result.inference is a GPUInferenceMetadata (alternative 'two-sided', analytic so permutationCount: 0, the method, and testedRowsDefinition, for example 'included rows with at least 8 active neighbors (islands excluded) and a defined z-score'); result.permutationInference describes the optional permutation confirmation. Both come from the contributors' getInferenceMetadata of the one settings object (GPUHotSpotAnalysisRecipeSettings: significanceLevel, optional fixed moments, seed, permutationCount) that the recipe packs into its parameters and permutation.parameters GPUParameterBuffers; result.setSettings repacks them per frame.
  • The lattice source keeps its queen/rook weights and gets the same guard and metadata. Values 0 and 1 of minimumNeighbors both use an effective minimum of one: masked rows, islands and undefined scores stay outside the analytic family. The contributor's full eligibility description is preserved when settings change.
  • Permutation confirmation does not apply minimumNeighbors. Its family contains included finite-value rows with 1 to permutation.maximumNeighbors positive-weight neighbors (default maximum 32), as stated by result.permutationInference.testedRowsDefinition. The analytic family has its own description in result.inference.testedRowsDefinition; on a 5×5 queen lattice at the default minimum these families contain 25 and 9 rows respectively. Multiple-testing correction uses each stage's actual family.
  • The permutation confirms the statistic the Gi stage maps. GPULocalPermutationTest has a fixed focal weight (1 for 'localGStar', none for 'localG'), so permutation.statistic defaults to 'localGStar', or to 'localG' when selfWeight is 0. 'localGStar' with a selfWeight other than 1, or 'localG' with a selfWeight other than 0, throws at construction. outputs.permutation.observed (optional, float32 per row) receives the permutation test's observed statistic in esda scaling, so the two stages can be compared.

addRateClusterMapRecipe

Turns bird and total observation counts per tract into smoothed rates and significant local Moran clusters.

::lens{scenario=gpu-spatial-analysis.rate-cluster-map-recipe rung=result caption="Bird observations over all observations in 199 tracts; quadrants mark significant clusters."}

Event counts and populations per polygon to significant local Moran clusters of empirical-Bayes rates (esda Moran_Local_Rate).

  • analyze is 'standardized' (default, Assuncao-Reis) or 'smoothed' (global empirical-Bayes rate). clampPriorVariance (default true) is passed to GPUEmpiricalBayesRates and only changes the 'smoothed' path: the prior variance is clamped at zero (Marshall), so counts no more dispersed than Poisson shrink fully to the pooled rate. false reproduces esda Empirical_Bayes. The standardized path is unaffected.
  • multipleTesting defaults to 'benjamini-hochberg' (it replaces permutation.falseDiscoveryRate) and applies to whichever inference runs: the analytic GPULocalMoran p-values without permutation, or the permutation pseudo p-values with it. The family is every polygon with a valid rate and at least one neighbor, never a viewport.
  • Analytic inference is a preview (two-sided normal approximation of the conditional-randomization moments). Permutation inference is the reference; esda uses 999 permutations and so should you. The alternative defaults to 'two-sided'. Analytic p-values are exposed as result.analytic, permutation ones as result.permutation (pseudoPValues, and adjustedPValues after the correction).
  • Islands and polygons with a NaN rate (zero population, masked) end at quadrant 0 and have NaN p-values: they are outside the test family, not counted as tested but not significant.
  • Legend contract, stable under any setting: palette index 0 is "not significant" and 1, 2, 3, 4 are high-high, low-high, low-low, high-low. The correction changes which polygons reach significance, never what a color means.
  • palette must contain at least five packed uint32 entries. Supplied outputs.colors and outputs.quadrants must each have exactly one logical row per polygon feature, even when their backing buffers have spare capacity. Independent outputs must use separate buffers and must not alias any original input, including the palette and parameter buffers. Active scratch is checked with the retained outputs too: for example, scratch.spatialLag cannot overwrite smoothedRates. Invalid ports are rejected before scheduling, so corrected views can reuse the same recipe ID.
  • events and populations accept float32 or uint32 (for example the counts of addPointsInPolygonsChoroplethRecipe); uint32 columns are converted by one node (exact below 2^24).
  • Rows are features: polygons is a GPUPolygonGeometryPort (four-level layout, one packed positions view), so multipart features get one row and the counts of addPointsInPolygonsChoroplethRecipe on the same features chain in directly. The weights stage publishes requiredCount for getGPUSpatialWeightsCapacityPlan.
  • Settings have one source of truth. Pass GPUParameterBuffers as parameters and permutation.parameters plus settings: {significanceLevel?, seed?, permutationCount?}: the recipe packs the settings into both buffers and builds result.inference from the same object, and result.setSettings(settings) repacks them per frame (an invalid setting throws and writes nothing). Caller-packed views are not accepted.
  • result.inference is the getInferenceMetadata of the GPULocalPermutationTest the recipe built (or of GPULocalMoran without permutation). It holds the alternative, permutationCount (0 for analytic), seed, significanceLevel (default 0.05), multipleTesting and testedRowsDefinition. An invalid permutation count or seed throws when the recipe is built.

addPeriodComparisonRecipe

Counts two periods of observations per Quadbin cell and returns the classified, coloured change.

::lens{scenario=gpu-spatial-analysis.period-comparison-recipe rung=result caption="655 spring and 566 autumn observations compared per cell; classes diverge from no change."}

Two periods of events to a classified, colored change map.

For measure: 'sum', pass one sumScale (default 65536) for both aggregation stages and the comparison. For example, sumScale: 2 ** 18 preserves a one-cell change from 0 to 2 ** -18; the default scale rounds that value to zero. Choose a scale with getGPUCellSumScale using the largest magnitude and group row count across both periods.

The comparison stage separates destination overflow from candidateOverflow inherited from either aggregation table. Its requiredCount is the retained-input union requirement and becomes a lower bound after source loss. Inspect status.stages to find the capacity that needs growing; adding union slots cannot recover an earlier aggregation's dropped cells.

  • delta (after minus before) is always defined. ratio and percentChange are NaN, not 0, for cells whose earlier value is 0; NaN rows are skipped by GPUClassBreaks and take the palette no-data color.
  • zScore is a descriptive score of the change ('poisson': delta / sqrt(before + after), or 'standardized' deltas). It has no null distribution and no multiple-testing correction, so a threshold on it is not a significance level; use addHotSpotAnalysisRecipe or addRateClusterMapRecipe for inference. With measure: 'count' every union cell has before + after > 0, so the Poisson denominator is never zero.

addChangeOfSupportRecipe

Moves tract observation counts onto community areas by raster overlap area and reports what each tract could not transfer.

::lens{scenario=gpu-spatial-analysis.change-of-support-recipe rung=result caption="199 census tracts rasterized with 13 community areas; counts are redistributed by overlap area."}

Transfers values between two polygon zone systems by area: both systems are rasterized to one grid (GPUPolygonRasterization), GPUArealInterpolation builds the overlap areas and both weight sets, and GPUSpatialLag moves sourceValues to the targets as extensiveValues and intensiveValues.

  • Props: grid (GPURasterMetadata), parameters (getGPUPolygonRasterizationParameterValues(grid)), source and target zone systems (GPUPolygonGeometryPort plus crossingCapacity), pairCapacity, optional cellWeights, sourceValues and columnCount, categories, denominator, sourceAnchorCells, spatialContext and outputs / scratch overrides.
  • Denominators (default change): extensive 'zone', intensive 'overlap', so a target only partly covered by sources is the mean of what covers it. Pass denominator: 'zone' for the old intensive result.
  • Conservation: the result always carries sourceAreas, sourceTransferredFractions and status.invalidCount; the last one is also in the areal-interpolation stage status. A source entirely outside the targets, or smaller than a cell, shows up there instead of silently losing mass; sourceAnchorCells rescues the latter.
  • Coordinates: spatialContext omitted is native planar (cell counts are areas). longitude-latitude requires metric 'great-circle' and declares a longitude/latitude raster whose parameters are in degrees. The areal stage weights each cell by its area on the authalic sphere in the context's length unit squared (square meters by default; square kilometers with units: 'kilometers'). It measures area, so local-azimuthal-equidistant frames throw. Rasterization itself only tests cell centers with straight polygon edges in degrees. For antimeridian crossings or great-circle edges, set prepare: true or prepare with GPULonLatPolygonPreparation. The resolved context is returned as result.spatialContext.
  • prepare defaults to false and requires a longitude/latitude context, preparedPositionCapacity (applied separately to each zone system), and a per-frame preparationParameters view from getGPULonLatPolygonPreparationParameterValues(edgeModel, settings). Preparation runs before each rasterization and preserves zone IDs. Stages source-preparation and target-preparation expose overflow, requiredCount, invalidCount and approximation.
  • Accuracy is bounded by the raster resolution (cell centers decide membership), never an exact polygon intersection.

addFleetDwellRecipe

Finds where vessels stop and totals the dwell time per anchorage zone.

The stops variant forwards trajectories.temporalContext, timestamps and optional timestampsLow to GPUTrajectoryMetrics. Float32-relative, Int64 words and double-single times are supported; the declared encoding must match the bound views. Durations use the declared tick unit. The zone-events variant takes GPUFleetDwellZoneEventsTrajectories: float32-relative or Int64 words only. It rejects timestampsLow and incompatible declarations before scheduling nodes, and forwards supported contexts to GPUZoneEvents. Both variants reject incompatible time declarations before registering their recipe outputs, so the caller can correct the declaration and retry on the same graph with the same recipe ID.

Only the GPU-written stops.status.count prefix enters the zone join. A private adapter view gives unused slots nonfinite coordinates, which the join excludes before counting candidates; the public centroids keep the metrics contributor's zero-filled padding. An empty stop list therefore cannot consume zones.candidateCapacity or set status.joinOverflow because of spare stop slots. joinOverflow still reports capacity loss among real stop candidates, and joinUncertainCount reports unresolved containment among them. Check those words and the metrics stage's overflow before using a per-zone summary as complete. When caller-owned centroids and a stop mask occupy disjoint subviews whose aligned storage bindings overlap, the recipe produces the mask and private join positions in separate dispatches. For example, two centroids at bytes 0–15 and two mask values at bytes 16–23 of one buffer remain supported.

Dasymetric redistribution combines fractional source-cell coverage, an ancillary raster and explicit whole-cell target ownership.
