Parallel building blocks

No kernel loops over every row. Scan, scatter, sort and a grid index do the work a loop would.

In short
  • A kernel runs one invocation per row, all at once, so no invocation can keep a running count.
  • Totals come from a reduction, write positions from a scan, packed outputs from compaction, groups from a sort, neighbours from a grid index.
  • Each is a few kernels you can see in the recorded graphs; the contributor contract forbids the loop.

One row each

A loop over rows carries state: to pack the kept rows it keeps a counter n and writes each kept row at n++. A kernel has no such counter. Its invocations run together and each sees only its own row, so a kept row cannot know how many kept rows came before it.

The library's rule is that no single invocation loops over all rows (contributor contract, rule 2). Counting, totals and packing go through four published luma.gl blocks instead.

Reduce to a total

A reduction adds values in pairs, then pairs of pairs. Sixteen values need four steps, a million need twenty, and every step runs in parallel.

Scan and scatter

A scan (prefix sum) gives each row the sum of everything before it. Scan the 0 or 1 flags and every kept row learns its slot; then each writes itself there in one parallel scatter. That is compaction.

Sort by digits

A radix sort is count, scan and scatter repeated, once per digit from the lowest. The scatter is stable, so each pass keeps the order the earlier passes made.

A grid index

Testing every pair of points costs rows squared. A grid index counts points per cell, scans the counts into cell offsets and scatters the point ids into cell order. A query then reads only the cells near it, and each grid row of that neighbourhood is one contiguous range.

Which block when

Most operators combine several blocks. Rows of uneven length, such as neighbour lists, are split evenly over invocations with a merge-path loop built on a scan.
