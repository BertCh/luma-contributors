The command graph

Kernels declare what they read and write. The compiler orders them from that alone.

  2. Build
  3. Compile
  4. Encode

  6. Read back
In short
  • Each kernel lists the buffers it reads and the buffers it writes. Nothing else.
  • Where two kernels touch one buffer and one of them writes, the graph adds a hazard: an edge that fixes their order.
  • Compile turns those edges into one order. You never write an edge.

Declare, never order

A command graph is a list of kernels and the buffers each one touches. The time window filter below keeps the rows of 1,500 timestamps that fall inside a window and packs their ids in 9 kernels, recorded on a real GPU.

This is how the filter adds those kernels. Each binding says read or read_write; that becomes a storage-read or storage-read-write use, and luma.gl infers the edges from those uses.

Three hazards

A hazard appears wherever two kernels touch one buffer and at least one of them writes it. There are three kinds; each card shows the first one in a real record.

A real analysis

Local Moran on census tracts chains three operations. The code adds them one after another; the only link between them is that one operation's output view is the next one's input.

What compile does

Compile walks the same read and write sets, collects the hazards and sorts the kernels into an order that respects every one. Kernels that do not depend on each other keep the order they were added in; the graph then freezes and compiles only once.

The order is not the order of the code. multiple-testing-counters belongs to local Moran, added last, yet it sits among the contiguity-weights kernels: nothing it touches is written before it, so it does not have to wait.

What that order costs per frame, and what changes without compiling again, is the next page.
